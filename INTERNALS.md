# Pepper compiler internals

A map of the compiler for people and agents about to change it: where each
stage lives, how a program travels from source text to an executable, and the
patterns the code follows. It complements two other files:

- [Building Pepper from source](docs/src/contributing/building.md): setting
  up LLVM, building and testing. Not repeated here.
- [AGENTS.md](AGENTS.md): the rules (workflow, CLI string handling, CI
  hygiene, the reference-counting model, the diagnostic standard, the
  library documentation standard). This file links to them and does not
  restate them.

The language itself is described in the book under [`docs/src/`](docs/src/introduction.md)
(tutorials, language guide, and the generated standard library reference).

Pepper is self-hosted. The compiler, `pep-build`, is the Pepper program in
`tools/compiler` (called pepc in code and commit messages), built by the
previous release's `pep-build` and then by itself (`scripts/release-build.sh`).
A note on history: pepc is a port, stage by stage, of an earlier compiler
written in Rust, which was itself a port of a C++ implementation
. Both are deleted. The pass names and the pass order come from the C++
implementation, and the curated test expectations (`expected_outcomes.pep`)
were recorded when pepc matched the Rust compiler byte for byte.

Paths below are relative to `tools/compiler/` unless they start with
`tools/`, `runtime/`, `docs/` or `scripts/`. A name `Type.member` is a
member of a Pepper type, and `module.name` a function of a module or file.

## 2. The pipeline end to end

```text
pep-build main.pep [-I dir] [--import name] [-l lib] [-o out] [--build dir]   (pepper build ...)
  │  main.pep: the options → link.Setup, driver.BuildOptions
  │
  ├─ --emit-ast[=json] ─→ parse.parse(entry) → print the tree (entry file only)
  ├─ --emit-linked / --emit-checked / --emit-model[-step N] / --emit-llvm
  │                    ─→ stop after that stage and print it
  ▼
link.load_program(entry, setup)                                   (link/program.pep)
    runtime discovery              PEPPER_RUNTIME, else runtime/ near cwd or exe
    project                        pep.toml above the root (outside .pep): its
                                   [build] include dirs follow -I, its deps resolve
    search paths                   -I dirs, then runtime dirs
    forced imports                 --import NAME → prelude, ahead of the runtime
    features                       Packages.turn_on_features: --features (Target.features)
                                   and each package's default, unified over the graph;
                                   each feature on defines -D <package>_<feature> in the
                                   target, and turns on the optional dependencies it lists
    the import walk                parse every reachable file; resolve imports
                                   (a dependency through Packages, else the search paths;
                                   the root project's dev-dependencies only in a TEST
                                   build or for a root file under its examples/; a
                                   [target.'<condition>'.dependencies] entry only when
                                   the condition, read as [Target(...)]'s, holds; an
                                   optional dependency only once a feature turns it on)
    link.link                      bind imports/exports; rewrite m.x, aliases; mangle
                                   private names (helper@io/file) → FileScope
  Program.check()                  linking errors, then visibility
  Program.warnings()               parser warnings + deprecation uses
  ▼
driver.build(program, options)                                    (driver/build.pep)
  Keys, cache.is_built             the program's key: unchanged → stop before sema
  compilation_units(...)           checked compilation units (§8.1): load each
                                   one's record, or check it (in workers,
                                   side by side)
  otherwise sema.merge             builder.build_file for each file → one sema Module
            sema.run_steps_with    the platform filters, struct synthesis,
                                   then every pass in order (section 3)
  ▼
  codegen.generate                 declare every struct, method, extern and
                                   function, then globals and bodies  (codegen/generator.pep)
  codegen.prepare                  split the module into parts, one or more per unit
                                   (codegen/partition.pep)
  compile_parts                    each part: from the cache, or optimized and emitted,
                                   in `pepc --compile-part` children    (driver/parts.pep)
  → <build>/<name>.<pid>/…, the objects stored in the cache
link_inputs ([Link]) + -l/-L + $PEPPER_LIBRARY_PATH + runtime/*.a
linker.link → clang -o <out> <objs> -L… -l… (+ kernel32 user32 shell32 on Windows, m on Linux)
```

The CLI produces an executable and never runs it.

**Checked compilation units** (§8.1). Most of a program does not change between builds,
so the driver checks it a compilation unit at a time (the runtime first) and keeps
each compilation unit's checked result in the build cache as a record. A build checks
only the compilation units an edit reaches and loads the rest; the passes then read
the loaded declarations as checked and leave them alone
(`checked.stash_bodies` keeps their bodies out of the passes that walk
bodies until the checks that read callee bodies run). A program that
overrides a runtime generic (`hash<int>`) changes the runtime's own
instances, so its compilation units are checked whole.

### 2.1 CLI options (`main.pep`)

`main.pep` declares the command line with the runtime's `cli` module,
which writes `pep-build --help` and the usage errors (exit status 2) from
the declarations; `docs/src/tools/pep-build.md` documents every option, and
`pep-doc check` checks it against `pep-build --help`, the trace channels
(`TRACE_CHANNELS`) and the environment variables the compiler reads. The
entry file is the first file named (the rest are ignored, except under
`--test`); with none, the `pep.toml` project in the current folder or above
is built (`driver/project.pep`: its entry, output and `[build]` options).
Besides the build options (`-I`, `--import`, `-l`, `-L`, `-D`, `-o`,
`--build`, `-O<n>`, `--no-runtime-checks=<list>`, `--target`, `--sysroot`,
`--frame-pointers`, `--no-runtime`, `--cache`, `--no-cache`):

- `--test` builds a test program: it defines the build option `TEST`, loads
  the runtime's `testing` module into every file
  (`test_main.TESTING_MODULE`), and appends to the entry file's text, after
  its last line, a `[TestMain] main(args: String[])` that registers each of
  the file's `[Test]` functions that the target keeps (`Target.keeps`)
  with a `TestRunner` and calls `run(args)`;
  being in the entry file, it can name the file's private functions (see
  `entry_point.pep` for how it replaces the file's `main`). Given several
  files of one folder, `test_program` instead appends to each file an
  exported `_pep_register_tests_<n>(TestRunner)` and roots the program at a
  generated `_pep_test_main.pep` in that folder that imports each file and
  calls them; the files' amended text reaches the loader through
  `Setup.sources`, in place of what is on disk.
- `--no-runtime-checks=<list>` removes kinds of runtime check from `-O1` up
  (every check stays on at `-O0`, with a warning); the checks a build keeps
  are part of every object's cache key.
- `-T time` (or `--Tall`) prints each stage's time on standard error (keys,
  reuse, sema, codegen, objects, link); `-T cache` prints how the cache
  supplied each unit's object. Other channels are accepted and ignored.
  `PEPC_TRACE_STEPS=1` prints the time of each sema step
  (`sema/passes.pep`), and `PEPC_TRACE_COMPILATION_UNITS` each compilation unit's reads and
  interface hash.
- `--emit-ast[=json]`, `--emit-linked`, `--emit-checked`, `--emit-model`
  (with `--emit-model-step N`) and `--emit-llvm` stop after a stage and print
  its result, to diff a program by hand and for the compiler's tests.
- `--compile-part <dir> --part <N>=<object>...` is internal: the children
  `driver/parts.pep` starts to compile parts side by side
  (`driver.compile_part`), run before anything else is read.
  `--compilation-unit-worker <dir>` is the other internal option, for the
  children that check and compile compilation units.

The output defaults to `<cwd>/<entry stem>` with no extension.

### 2.2 Program loading and linking (`link/`)

- **Runtime discovery** (`Runtime.discover`, `link/files.pep`). When the
  `PEPPER_RUNTIME` environment variable is set and non-empty, it names the
  runtime directory and nothing else is searched. Otherwise the candidates
  are `<cwd>/runtime`, `<cwd>/.pep/runtime`, and `../runtime` up to five
  levels above the current directory, then `runtime` beside the running
  executable and up to five levels above it (so a `pep-build` built into the
  checkout finds its `runtime/` from anywhere, and an installed one finds
  the install's). The **first** directory
  containing `.pep` files wins. Only that directory's top-level `.pep` files
  join the prelude (`runtime/io/` does not). Any `.a` files there are
  linked. Every directory scanned before the winner is also returned, and
  those become import search paths. `load_program` fails with `cannot find
  the Pepper runtime` when no runtime is found (unless `--no-runtime`).
- **`load_program(root, setup)`** (`link/program.pep`) is the single loader.
  The compiler, its tests, pep-doc and the language server all call it.
  `Setup` holds `import_dirs` (`-I`), `forced_imports` (`--import`),
  `runtime`, the `target`, and `sources`, texts that stand in for files on
  disk (an editor's unsaved buffer, a test build's amended entry file).
- **`load`** walks a stack: the root is `files[0]`, then the files its
  imports reach, then the prelude. Each file goes through
  `parse.parse`. For each import, `platform.keep` evaluates its
  `[Target]` attributes first; an import that is dropped is never resolved.
  A file's identity is its `ProgramFile.key`, its canonical path
  (`files.path_key`); `ModuleRoots.key` canonicalizes each path once per
  load, and `files.canonical_path` joins a relative path onto the working
  directory first, since `realpath` of a relative path on macOS lists every
  folder above the working directory. `load_program` records the
  runtime's folders as keys (`Program.runtime_dirs`) for
  `Program.in_runtime`, which the build's compilation units also read.
  - `import "x"` (`Import.is_local`) goes through `files.resolve_local`,
    which tries `x.pep` beside the file and then `x/module.pep`. A file
    target must be in the same module (`ModuleRoots.placement`); otherwise
    the import is reported as belonging to another module, or as outside
    this module or folder.
  - `import m` goes through `files.resolve_module`, which returns the
    first `<search path>/m/module.pep`.
  - Files reached from prelude files through local imports are marked
    `prelude_part`, which exempts their functions from duplicate-export
    checks (types and variables never are: two prelude files exporting one
    is a `redefinition`).
- **`link.link`** binds every file's imports and `export x as y`
  re-exports, then **rewrites each imported spelling in the AST**
  (`m.sqrt`, an alias `power`, a qualified type `m.Point`) to the name of the
  declaration it denotes. The type arguments of a generic method call
  (`b.run<S>(...)`), which the parser keeps in the member name as source
  writes them (`pass<(a: int, b: int)>`), are read back
  (`ast.parse_type_text`) and rewritten the same way (`_member_type`); the
  builder spells them as sema types (`_Builder.member_name`). It also gives each file's
  **private** top-level declarations, and every reference to them, a
  mangled name
  (`names.mangle`: `helper@io/file`), keyed on the
  file's `ProgramFile.namespace`, which `load` computes with
  `ModuleRoots.namespace_of` (module name plus path inside the module;
  outside any module, the path from the project directory, the one the
  compiler runs in, such as `tests/util`; the file stem only for a file
  outside both, made unique with `#2`, `#3` in load order). A namespace
  depends only on the file's path, so a file's symbols are the same in
  every program that loads it, which the build cache relies on. Exports are
  mangled the same way, so two modules may export one name, except
  those of the root file and the prelude (`prelude` or `prelude_part`;
  `exports_keep_names`), which every file reaches by their bare names. A
  reference to another file's mangled export that no import binds stays
  unrenamed, and the visibility check reports it as not imported. Externs
  and concrete overrides keep their names; so do
  the root file's private names, unless another file keeps the same name
  (so `main` stays findable). `_Linker.keeps_name` and
  `_Linker.compute_own_names` decide
  this. Which generic functions are concrete overrides (`hash<int>`, and
  `hash<Point>` of a visible `hash<T>`) is decided by `_Linker.compute_overrides`,
  the same rule sema's `overloads.concrete_overrides` applies: every
  type parameter names a primitive, `String`, or a struct, and either all
  are primitives or `String`, or a generic of that name and arity exists.
  A constrained parameter (`describe<Point: Shape>`) is always a parameter,
  so a function with one is never an override, and counts as a base.
  "A type" and "a base" mean ones the declaring file can name: its own,
  the exports of the files it imports (a module's are its `module.pep`'s,
  re-exports included), the prelude's, under import-list aliases too
  (`_Linker.visible_names`, iterated until re-exports settle). Linking marks an
  override's parameters (`GenericParam.is_argument`) and resolves them
  like type references to the structs they denote, mangled or imported,
  binding no names (`_Rewriter.visit_function_generics`); a type alias there is an
  error. Linking then applies the orphan rule (`_Rewriter._check_orphan`): the override's file must share a home (`_Linker.home`:
  its module, the prelude for the runtime's top-level files and built-in
  types, else itself) with the generic or one of its type arguments
  (`_Linker.declared_at`), so a unit's inputs never need another unit's
  overrides. Sema (`concrete_overrides`) and the visibility check follow the
  mark; sema's own program-wide rule applies only to an unlinked module
  (`Module.linked`). A file's own function of a name hides the imported
  generics of that name. Several functions of one name in one file are an
  overload set, which sema resolves (`overloads`); linking reports
  only a generic beside another function of its name with the same
  parameters (`_parameter_shape`), or a generic whose type parameters all
  name structs the file sees (an override of a generic the file's own
  functions hide). The
  visibility check applies the same override rule (`_Decl.is_override`).
  A file's overloads of a name take one name whatever their visibility, so
  an import binds the whole set.
  **Files of one module see each other's declarations**: `_Linker.compute_mates`
  groups the files of the program by `module_root`, and `_Linker.compute_module_names`
  gives each file `_Bindings.module`, every name its module's other files
  declare (exported or not) -> the name it takes in the merged program.
  Functions of one name declared by several files of a module form one
  union (`_Unions.merge`), which the declaring files see too (it seeds the
  union an import of that name joins); externs keep their names; any other
  name two files declare is the first's here, and the visibility check
  reports the second (`redefinition of 'x'`, a note at the first). Lookup
  of an unqualified name (`_resolve_imported`) is the file's own, then its
  imports, then `_Bindings.module` (which a hidden extension method
  captures like an import), then the prelude; `_Rewriter._denote` records the
  reference in `FileScope.imported`, so the visibility check, the LSP
  (go to definition, hover) and the deprecation check follow it like an
  import. `_Linker.compute_overrides` counts the module's other files' types and
  generic bases as the file's own (`_Linker._with_mates`); `FileScope.extensions` includes the
  module's other files (so `Program.unit_inputs` hashes them into the
  file's build-cache key), and their extensions are visible whether or not
  exported (`_Linker.mates`, `_Checker._same_module`,
  `Overloads._same_module`, also used by `Overloads._set` for a
  set's private members). `load` queues a module file's `module.pep`,
  so a file of a module never loads without the files its module imports.
  A **`private` declaration** (`Declaration.is_private`) stays out
  of all of that: `_Linker.compute_module_names` binds it for no other file (and a file
  whose only declarations of a name are private joins no union of it),
  `_Linker._bases_of` leaves it out of what the module's other files see, the
  extension checks (`_Rewriter.is_member`, `_Checker._sees_extension`,
  `Overloads._sees`) see a private extension only in its file,
  `Overloads._set` offers a private function only to its own file
  (`Module.file_private_functions`), and the visibility check skips it
  when comparing a module's names and reports a reference to one from
  another file of its module as `FilePrivate`.
  Files outside any module, and the runtime's top-level prelude files, keep
  per-file visibility. Where an import or re-export would bind
  one name to functions of two files (of one module or of several), or a
  file's own functions of a name meet an import of it, it binds a union
  instead (`_Unions.merge`, a name like `f@geo/a#set1`). The prelude's
  functions are one module (`_PRELUDE_HOME`) that a prelude file's own
  bindings never join, but whatever functions a non-prelude file's name
  denotes join the prelude's of that name once binding settles
  (`_Linker.join_prelude`), so `print(p: Point)` beside the runtime's
  `print` makes one set; `link` returns them grouped by module
  (`Linked.overload_unions`, carried to `Module.overload_unions`), and
  `name_overloads` records each as a set of every member, reporting two
  members of one module with the same parameters as a redefinition (two
  modules' such members only make a call ambiguous, except a member with a
  prelude member's parameters, an error whatever its return type,
  `_repeated_prelude_member`). Sema hides a mixed
  set's private members (`Module.private_functions`) from calls in other
  files, and an imported member with the same parameters as one of the
  calling file's own (`Overloads._set`, by the call's location).
  Codegen gives every mangled declaration internal linkage
  (`set_private_linkage`): no other object can name it, and ELF linkers
  read the `@` of a global symbol as a version. After this step every reference is spelled the way the merged
  model resolves it, with no two files' private names alike. Runtime
  functions the compiler calls by name (`_pep_malloc`, `_pep_format*`) must
  therefore be exported. For each file it records a
  `FileScope`: `imported` (span start → declaration, used by visibility),
  `named` (used by the LSP), and `extensions` (`visible_extensions`: the
  prelude and forced-module files, the files it imports, and every file of
  a module it imports, whose exported extensions it may use; `load` records
  each file's `module_root` for this). Errors are `ModuleError { file, span, message,
  unresolved }`.
- **`link/walk.pep`** is the traversal linking, visibility, and the
  deprecation check share: it
  tracks the names bound at each point (parameters, locals, generic
  parameters, the members of the struct being defined or extended), which
  hide top-level names; a bare generic call `m<T>(...)` whose `m` is such
  a member is the member, so only its type arguments resolve as types. It
  is one trait, `ScopeWalk`, whose default methods
  return each expression and statement rebuilt (an enum's payload cannot
  change in place); linking's `Rewriter` rebuilds the tree, and
  visibility's and deprecation's walks only read it. Each implements the
  hooks for references, member names, type names, visible members, and
  `extend` parameters. `enter_declaration`/`exit_declaration`
  bracket every declaration (and field, and function body) with its
  attributes. In `extend Box<T>`, a name equal to `Box`'s own parameter at
  that position is always the parameter, even when the program also declares
  a struct `T` (a runtime `extend ArrayIterator<T>` must not see a user's
  `struct T`).
- **`Program.check`** reports link errors first and then
  `visibility.check_visibility`. That check covers private symbols (a
  reference linking left unrenamed is matched against other files' mangled
  names by its demangled spelling), symbols that were not imported,
  extension methods of a private extension or of an exported one in a file
  the referencing file does not import (`FileScope.extensions`), a bare
  call in a method, or in a trait's default method, that such an invisible
  extension would capture (sema binds it to any extension's method;
  `visit_callee`). A member access is accepted when a trait the file
  can see declares the method (`_VisibilityMembers.in_traits`: a call may go through
  a trait value), or when its receiver's type is unknown here (`this` in a
  trait default, or a chain starting from a parameter, local, or closure
  parameter whose type is a generic parameter in scope, or that is
  initialized from such a value: `visit_binding` marks the binding in
  `Scopes`, and `Scopes.is_marked_value` finds the innermost binding),
  and when the trait is declared by a file the checking file's imports
  bind, spelled or not (`FileScope.bound`),
  duplicate
  exports, concrete overrides declared in several files, and a type or
  variable declared twice in one file or exported by two prelude files, or
  declared by two files of one module (compared demangled). A private
  symbol of a file in a module is reported as `internal to module 'm'`.
  Extern redeclarations are exempt.

### 2.3 Parsing (`tools/syntax`, `parse/`, `desugar/`, `ast/`)

- **Tokens.** `tools/syntax` is the lexer (`lexer.pep`, `token.pep`): an
  interpolated string `$"..."` is one `TokenKind.String` token, and each
  comment hangs off the token next to it (see section 8). `>` is always its
  own token; the parser joins adjacent ones into `>>`, `>=` and `>>=` where
  the grammar reads those operators.
- **Entry points** (`parse/parser.pep`). `parse.parse(source)` returns the
  desugared `compiler.ast.Module`, or a `ParseError`; it is what the
  compiler and the language server load. `parse.parse_written` returns the
  tree as the source writes it, with every token and its comments (what
  pep-fmt lays out; see below). `parse.parse_recovering` reads on past
  syntax errors for the language server (section 8). After a successful
  parse, `parse/checks.pep` checks the finished tree: `T*` is legal only in
  `extern` declarations (elsewhere the message suggests `__ptr<T>`), and
  imports come before every declaration (`check_import_order`). A second
  destructor in one struct is a syntax error (`redefinition of the
  destructor of 'S'`); several constructors are an overload set (see
  `overloads`).
- **Grammar.** A recursive descent over the tokens, one method of `Parser`
  per rule, with the precedence ladder `_ternary` → `_binary_level` (the
  binary levels, with `_range` between the shift and `is` levels) →
  `_postfix` → the atoms; `as` casts bind like postfix operators. A rule
  that may read two ways tries one and abandons it through a `Mark`
  (`_mark` / `_restore`), which also cuts back everything the abandoned
  reading added. A failure records what was expected (`_expect`,
  `_expect_name`, `_fail`), and the error reported is the one furthest into
  the source, unless a `;` is missing first. An error in a node that parses
  (a literal too large, an escape, a hole that is no expression, a format)
  goes in `Parser._problems` and is reported only when the file has no
  syntax error.
- **Semicolons.** Simple statements and non-block declarations end with
  `;` (`docs/src/language/statements.md`); line breaks are whitespace
  everywhere, so an expression runs on across lines for as long as a token
  extends it. A missing `;` fails the parse with `expected ';'` right after
  the statement's last token, with a fix inserting it (the language
  server's quick fix). A C-style declaration (`Box b = f()`) followed by a
  line break is still reported as a declaration missing its `;`, rather
  than reparsed as an expression.
- **Generic method calls.** In postfix position, `.name<types>(` is a call
  with type arguments only when `<` follows the name and `(` follows `>`
  with no whitespace; the method name becomes the string `"map<long>"`.
  Otherwise `a.b < c, d > (e)` stays two comparisons. Struct and trait
  methods accept their own type parameters (`map<U>(…)`) through a probe
  (`_probe_type`).
- **Comments.** The only comment form is `#` to end of line. A doc comment
  is a run of consecutive `##` lines directly above a declaration.
  Attributes and `export`/`static` may sit between the comment and the
  declaration; a blank line may not. `compiler.doc` parses these comments
  into a `DocComment` (description and tags: `@param`, `@typeParam`,
  `@returns`, `@panics`, `@example`, `@see`, `@note`), and its
  `check_documented` enforces the runtime documentation standard.
- **Interpolated strings.** `parse_written` keeps `$"a{x}b"` as an
  `Expression.Interpolated` (`_interpolated_string`, each hole read by a
  `Parser` of its own over the hole's text, `_parse_hole`), and
  `compiler.desugar` lowers it to `"a" + _pep_interpolate(x) + "b"` (the
  call located at the braces, the expression at itself), so linking,
  visibility, the language server and sema see ordinary references and
  calls; `parse` applies the same rewrite as it builds each node
  (`desugar_interpolated`). `{{`/`}}` are literal braces. Where a hole ends
  is decided first by `interpolation_end`, a byte scan that nests brackets
  and skips string, character and nested interpolated literals whole, and
  stops at a line break or `#` (so a hole is one line with no comment);
  `tools/syntax/lexer.pep` scans the same way to find the end of the
  string token. An assignment, compound assignment, `++` or `--` anywhere
  in a hole but inside a closure's body is an error at the operator; so
  are a lone `}`, an empty hole, a `#`, and a missing `}` (with a note at
  the `{`), except after a line break inside the literal, where the error
  is `missing terminating '"' character` at the opening quote.
  The runtime's `_pep_interpolate<T>` resolves `to_string(value)` in
  `string.pep`, so neither a struct's own `to_string()` method nor a file's
  own `to_string` functions capture it.
  A `:` after the hole's expression starts a format specification
  (`_format_spec` → `FormatSpec`, `[[fill]align][+][0][width][.precision][type]`);
  the value is lowered to `_pep_format(value, fill, align, width)` when it
  only pads, to `_pep_format_float(value, precision, plus, fill, align,
  width, zero)` when it has a precision, or to `_pep_format_integer(value,
  base, upper, plus, fill, align, width, zero)` otherwise, each located at
  the specification's character that asks for it. The `interpolation`
  pass reports a value with no text conversion at the braces, a
  non-integer given to `_pep_format_integer`, and a value other than a
  `float` or `double` given to `_pep_format_float`. The shortest text of a
  `float` or `double` (`_float_text`, in `runtime/float_text.pep`) comes
  from a Pepper implementation of the Ryu algorithm; text with a precision
  comes from C's `snprintf` with `%.1075f`; on Windows the UCRT defines
  `snprintf` inline, so `_print_double` calls `__stdio_common_vsprintf`
  with a hand-built `va_list`.
- **`String.format`** is an intrinsic. `parse_written` keeps the format of
  `String.format(...)` and `print(...)` as the call's first argument, an
  `Expression.FormatString` (`_format_call`); `desugar_format_call` lowers
  it. Its first argument must be a string literal, whose braces hold an
  argument index and an optional specification; an index out of range and
  an argument no brace names are errors. When the braces name every
  argument once, in order, the arguments replace the placeholders and it
  lowers like an interpolated string; otherwise it lowers to a `match` over
  a tuple of the arguments whose one arm binds `_pep_format_0`,
  `_pep_format_1`, ... (a lone argument is paired with `false`), so each is
  evaluated once, left to right. `print("{0}", x)` lowers to
  `print(String.format("{0}", x))`; `print` itself is the runtime's
  `print(text: String)`, and `print<T>(value)` prints `to_string(value)`.
- **Module `static` blocks and parentheses.** `parse_written` keeps a
  module-scope `static` block alone and parentheses as an
  `Expression.Parenthesized`; desugaring declares each `const` at the top
  of the block beside it (`static_constants`) and drops the parentheses.
  The spans the parser derives from a child expression use
  `desugar.desugared_span`, so both trees carry the same spans.
- **AST** (`ast/ast.pep`): `Module { imports, exports, declarations }`. An
  `export * from source` or `export [...] from source` is an `Import` with
  `reexport` set (`symbols` empty for `*`): the loader resolves it like an
  import, but linking binds no name from it; linking adds the source's
  exports (all of them, or the listed ones) to the file's, and reports a
  name published twice for different declarations at the `export ... from`
  that adds the second, with a note at the first. `Declaration` is
  `Variable | Function | Struct | Trait | Extend | TypeAlias | Static`.
  The file also defines `Statement`, `Expression`, `TypeName`,
  `Attribute`, `Import` and `ExportAlias`. Every node carries a byte `Span`;
  named nodes also carry `name_span`. Externs are `FunctionDecl`s with
  `external` set. Every node has a `to_json()` (externally tagged, as
  `--emit-ast=json` prints it).
  A `GenericParam` carries its `bounds` (`T: Shape & Named`) before its
  default. An `extend` target may restate its struct's constraints
  (`extend Box<T: Shape>`), kept per argument in `ExtendDecl.target_bounds`.
  An extension with a `with` clause may end in `;` instead of a body
  (`extend X with Trait;`), which pep-fmt writes for an empty body.
  Function types `(P…) => R` are parsed directly into
  `__function<R, P…>`, thread-safe ones `shared (P…) => R` into
  `__shared_function<R, P…>` (`shared` is a contextual keyword), and C
  function pointer types `extern (P…) => R` into
  `__extern_function<R, P…>`, whose parameter and return types parse like
  an extern's (`void*`); `extern (` at the start of a declaration or struct
  member starts a variable or field rather than an extern function. C's
  `T*` becomes `__ptr<T>` (`int**` is `__ptr<__ptr<int>>`), each layer the
  parser made marked `c_pointer` for the check that keeps C syntax in
  `extern` declarations, so `__ptr<T>` is the only pointer type sema and
  codegen see (`TypeName.is_pointer`, `pointee`, `without_pointers`).
  A `?` suffix wraps the type as `Optional<T>` (after any `[]`). While an
  expression is probed for a type, `?` counts only where
  `_optional_suffix_in_probe` rules out a ternary: before `>`/`,`, or before
  a name that ends a declaration.
- **Tokens and comments** (for pep-fmt). `parse_written` keeps every token
  in `Module.tokens` (`ast.SourceTokens`: the source and the
  `syntax.Token`s, `>`s joined as the parser joined them, ending with
  `End`), each with the comments and line breaks the lexer attached to it.
  A node's spans locate its tokens, so `leading(span)`, `trailing(span)` and
  `blank_before(span)` read a node's comments; a comment on a token that
  starts or ends no node (a `,`, a `)`, a `}`) is inside the innermost node
  around it. `parse` keeps no tokens and lexes without comment text.

### 2.4 Building the sema model (`sema/builder.pep`, `sema/model.pep`)

- `build_file(module, file)` builds one file's model; the builder's `loc`
  stamps every `Loc` with the file being built.
- **Type uses.** `type_name_from` records every generic type written with
  arguments (`Gallery<Circle>`, the callee of `total<Circle>(...)`) in
  `Module.type_uses` (`TypeUse`: the type and each argument's `Loc`), so
  `constraints` can report an unmet constraint at the argument.
  Each use points into `Module.use_contexts` (`UseContext`: the generic
  parameters in scope, the extended type inside `extend`, and the
  attributes of the enclosing declarations and blocks), which the uses of
  one declaration share; `program._join` offsets the indices. The builder
  keeps the current context in `CONTEXT` (`in_generic_scope` adds a
  declaration's parameters, `with_attributes` its attributes) and records
  it once per change. `check_constraints` skips a use whose context a
  `[Target(...)]` removes on this platform (`platform.keep`), as the
  platform filters remove its code. A concrete override records its own
  arguments as a use of the generic it overrides.
- **Literal arguments.** A model literal (`IntLiteral`, ...) carries no
  `Loc`, so the builder records where each literal argument of a call is
  written in `Module.literal_args` (call location, position, literal
  location), where the passes that report an error about an argument
  look up a literal's own location (constraint errors at an inferred call,
  `check_bounds`). Each generic parameter keeps the `Loc`
  of its name, of each constraint (`Bound`), and of its default.
- `type_name_from` lowers `T[]` to `Array<T>`.
- `variable_def` gives a variable or field of type `Optional<T>` with no
  initializer the default `Optional<T>()`, so it starts as Empty, not null.
- Lowering highlights:
  - A `for (var x in e)` loop becomes a block holding a hidden
    `__for_iterator_N` local (initialized with `Expression.ForIterator(e)`)
    and a `while (it.next()) { var x = it.current(); { body } }`. The model
    has no `for` statement.
  - A `with (var x = scope) { body } else { other }` block becomes a block
    holding a hidden `__with_scope_N` local (the scope), `var x =
    __with_scope_N.enter()` (`__with_value_N` when unnamed), and `if
    (Expression.WithEntered(x)) { body } else { other }`. The model has no
    `with` statement; `lower_with_blocks` resolves the condition.
  - A tuple literal `(a, b)` becomes `FunctionCall { function: "__tuple" }`;
    `resolve_implicit_types` renames it to its type (`__tuple<int, String>`)
    once its arguments are typed. The tuple type `(A, B)` is
    `TypeName { name: "__tuple", sub_types }` (`type_name.TUPLE`,
    `is_tuple`), displayed as `(A, B)`; `t.0` is a `MemberRef` named `"0"`.
    `Tuple<A, B>` builds the same type. Labels (`(line: int, column: int)`)
    ride on `TypeName.labels`, which equality, hashing and `Display` ignore
    (`display()` shows them, and names each number type as programs
    commonly do, `int` for the `i32` a literal is typed, through
    `common_number_name`; `display_stored()` keeps the stored spelling for
    `reflect.name`, which gives a type as written); `check_labels` rejects a partly labeled or
    duplicate set, and `lower_destructures` renames `p.line` to `p.0`
    (`tuple_index`). A labeled literal `(line: 3, column: 7)` is built as
    a call to `__tuple(line,column)` (`tuple_literals.tuple_constructor_labels`
    reads them back), so `resolve_implicit_types` gives an inferred `var` the labeled type
    (`labeled_tuple_literal_type`) before the rename drops the labels; the builder's
    `check_literal_labels` rejects labels that differ from a declared type's.
    One specialization serves every labeling of its arguments, so its
    members' types carry none: a field or method result read through a
    receiver whose type arguments have labels is the member's type in the
    generic declaration (the struct's or trait's own `T`, `T[]`, `T?`) with
    the receiver's arguments, labels included, put in
    (`TypeName.labeled_through`; `StructTable.generics` and
    `_TypeScopes._generic` find the declaration), so a same-shape tuple the
    declaration does not write as a parameter stays unlabeled. A call that
    names a type spells it without labels, so the builder keeps the type
    as written on the call (`FunctionCallExpression.labeled`, set only
    when it has labels), and both tables type the call as that type
    (`TypeName.as_written`): `var a = Array<(name: String, count: int)>()`
    and the receiver of `Optional<(left: int, right: int)>.Value(...)` or
    `Box<(p: int, q: int)>.make(...)`, whose result then takes the labels
    back like any member. A generic function call's result is its declared
    return type with the call's type arguments put in the same way
    (`StructTable.labeled_call`, `_TypeScopes._labeled_call`); type
    arguments that `resolve_implicit_types` infers or completes go in
    `FunctionCallExpression.labeled` too when they have labels. A generic
    method call keeps them in `MethodCallExpression.labeled`, and its
    result is the method's declared return type with them put in
    (`StructTable.labeled_method_call`, `_TypeScopes._labeled_method_call`).
  - An array literal `[a, b, c]` becomes the chain
    `_array_literal(a)._literal_append(b)._literal_append(c)`, and a map
    literal `[k: v, k2: v2]` becomes `_map_literal(k, v)._literal_insert(k2,
    v2)` (`array_literal`, `map_literal`; the helpers are in
    `runtime/array.pep` and `runtime/hash.pep`). With no other type, the
    generic start function infers the element types from the first entry.
    Every pass and codegen recurse down a chain, so a literal of more than
    `_LITERAL_CHUNK` (16) steps is a balanced tree of short chains over
    one collection instead: a `WithSubject` whose subject is the start
    call and whose body joins chains on the `Subject` with
    `_literal_then` (`sema/builder.pep`), keeping the
    depth logarithmic whatever the length.
    A variable declared as `Array<T>`, `HashSet<T>` or `HashMap<K, V>`
    types its literal in the builder (`typed_expression`), which also lets
    `[]` and `[:]` build an empty collection. Any other typed slot
    (argument, return, assignment) is handled by
    `convert_to_traits.convert_array_literal` / `convert_map_literal`,
    which rebuild the literal from `Array<T>()` / `HashMap<K, V>()` and
    convert each element to the slot's element type. A `HashSet` slot takes
    an array through its `[Implicit]` constructor.
  - A range `a..b` or `a..>b` (parsed by `range`, between the shift and
    `is` levels, as a `Binary` with op `..` / `..>`) becomes
    `_range(a, b, inclusive)` (`runtime/range.pep`), which returns a
    `[Value]` `Range<T>`, so a `for` loop over it drives a value in place
    and allocates nothing. `ranges.check_ranges` reports non-integer
    bounds (section 3).
  - `var (a, b: T, _) = e;` becomes a hidden `__tuple_N` local initialized
    with `Expression.Destructure { value: e, count }` followed by
    `var a = __tuple_N.0; var b: T = __tuple_N.1;` in the enclosing block
    (`destructure`). `(a, p.x) = e;` becomes a block holding the hidden
    local and one assignment per place (`destructuring_assignment`), so the
    right side is evaluated first. `destructures.lower_destructures` checks the
    count and removes the `Destructure` node. A nested pattern
    (`DestructureBinding.nested`) gets its own hidden local bound from the
    outer one's element (`bind_elements`, `assign_elements`), and
    `for (var (k, v) in e)` (`For.pattern`) binds the loop's element to a
    hidden variable and destructures it at the top of the body.
  - An `enum` is an `ast.StructDecl` whose `enumeration` is set, so
    linking, visibility, exports and name mangling treat it as a struct.
    When no case carries values, `enum_def` builds an `EnumDef` in
    `module.enums` instead (cases with their values folded, checked for
    range and duplicates); such an enum is not a struct in the model. Each
    method becomes a free function named `E::m` (`enum_method`,
    `enum_method_name`); an instance method gets a first parameter
    `this: E`, passed by value like any integer. A property's getter
    becomes `E::__get_p` the same way (`PropertyOwner.Enum`), and
    `properties` reads a bare `p` in those functions as `this.p`.
    Any enum's properties must be computed and have no `set`
    (`enum_property_error`).
    An operator or indexer method is the function `E::<` (with `<` and `>`
    spelled `{` and `}` in the name, as for value types), and
    `resolve_operators` and `unary_operators.dispatch_unary` turn `a < b`, `-a`
    and `a[i]` on such an enum into calls of it
    (`_declares_enum_operator`, `_enum_operator_call`).
  - An enum with a case that carries values (a reference enum) *is* a
    struct in the model (`reference_enum_def`): `StructDef.enum_cases`
    lists its cases (`EnumCaseDef.payload` names each case's values, and
    its `value` is the case's tag, its position). Its fields are `__tag`
    (`builder.TAG_FIELD`) and every case's values as `const` fields named
    `Case.value` (`builder.payload_field`; the dot keeps source code from
    naming them). One constructor takes every field (`this.field`
    parameters); each case is a static method named after it that calls it
    with the case's tag, its values, and `Default` for the other cases'
    fields, or, for a case that carries nothing, returns
    `Expression.StaticCase`, one immortal object per enum type and case.
    The built-in `name()` is a method that tests `__tag`. Declared methods
    stay ordinary methods, so generics, `[Shared]`, `extend` and trait
    conformance work as for any struct.
  - A `match (e) { arms }` becomes a block holding a hidden `__match_N`
    local (`e`) and an `if`/`else if` chain whose conditions are
    `Expression.MatchArm` (the subject, the arm's `CasePattern`s, and a
    `MatchSite` shared by the arms of one `match`); the `else` arm is the
    chain's last `else`. The model has no `match` statement;
    `enums.lower_matches` turns each test into `==` comparisons. Each name
    an arm's patterns bind (`match_bindings`) is a `const` local at the top
    of the arm whose value is `Expression.CaseValue` (the subject, and per
    pattern the case and the binding's position), which
    `resolve_implicit_types` types from the payload field and checks
    (`enums.case_value_type`), and `lower_matches` replaces with the field.
    A literal pattern (`1`, `"import"`) carries the test `subject ==
    literal` in `CasePattern.literal`, so the passes type and resolve it
    like any `==` (a `String`'s `==` included); its `case` is the literal as
    written, for duplicate checks.
  - A tuple pattern `(Circle, 0, r)` is a `CasePattern` with `elements`,
    each over its path from the subject (`__match_N.0`, built by
    `_element_path`), so a literal element carries `__match_N.1 == 0`. A bare
    name in a tuple pattern (`r`) is kept as a case pattern with no
    bindings; only its element's type says whether it is a case or binds
    the element. `match_bindings` declares it as a local reading its path
    when every pattern of the arm has it once at the same element
    (`ElementName.declared`), and lists every bare name in
    `MatchArmTest.element_names`. A case's binding inside a tuple pattern
    is a `CaseValue` whose subject is the element's path.
  - A case's values are patterns too (`CasePattern.bindings`,
    `Value(Text(t))`): each is built over its value's path, a `CaseValue`
    with one choice (`case_path`), so a nested literal carries
    `CaseValue(...) == ""` and a nested case's bindings read `CaseValue`s
    of that path. A bare name there is a binding (a `_Leaf` with `payload` set) that is
    also listed in `element_names`, since the value's enum may have a case
    of that name (`Value(Empty)`); one repeated in a pattern must be a case.
  - `if (x is P(a))` and `while (x is P(a))` become the same `match`
    statement with one arm (`is_branch`, `is_loop`; the loop is `while
    (true)` whose `else` breaks), its `MatchSite` marked `partial` so it
    need not handle every case; `a` is a local of the block.
  - Every case pattern also carries its name read as a type
    (`ast.Pattern.ty`, `CasePattern.ty`, `CaseChoice.ty`: `Circle`,
    `shapes.Circle`, `Box<int>`, the parser taking type arguments right
    after the name), which module linking resolves like any type
    (`visit_case_type`; a qualifier that is not a module is an enum's).
    It is what the pattern tests for when the subject is a trait value
    (§4.2); an enum ignores it.
  - `x as? T` (`ast.Expression.Cast.optional`) becomes the `match`
    expression `match (x) { T(__cast_value) => Optional<T>.some(...), else
    => Optional<T>.none() }` (`builder.pep`).
  - `e?` (`ast.Expression.Unary` with op `?`, postfix; the parser's
    `propagates` tells it from a ternary's `?` by the token after it, and
    probes for `expression :` when that token could start either) is
    lowered per statement by `sema/builder.pep` (`lift`, called from
    `block_in_context`): each `?` in the statement's head expression (an
    expression statement, a `var` initializer, a condition, a `return`
    value, a `for` iterable, a `with` scope, a `match` subject), in
    evaluation order, becomes a hidden `__try_N` local holding its operand
    and `if (__try_N._propagates()) { return
    R._from_residual(__try_N._residual()); }`, where `R` is the declared
    return type (`RETURN_TYPE`); the `?` reads `__try_N.value()`. The
    `_propagates`, `_residual` and `_from_residual` members of `Result`
    and `Optional` (runtime) make this work without types, and an error
    converts as `_from_residual`'s argument (`[Implicit]`). A non-
    declaration statement is wrapped in a block with its locals. `lift`
    reports a `?` after a call in the same statement (hoisting would run
    it first), one that might not run (right of `&&`/`||`, a `?:` branch,
    a `match` arm), and a function with no declared, non-`void` return
    type; a `while` whose condition uses `?` becomes `while (true) { if
    (c) { body } else { break; } }`. Any other `?` (a global, a default)
    is an error in `expression`. `check_tries` checks the types.
  - A `match` expression becomes `Expression.WithSubject` (evaluate the
    subject once, then the body) around a `?:` chain of `MatchArm` tests
    over `Expression.Subject` (the value, by the site's id). A name an arm
    binds is replaced in the arm's value by its `CaseValue`
    (`bind_in_expression`; a closure there may not use one). Without an
    `else`, the chain ends in `Expression.NoMatch`. An `is` test anywhere
    else is a `WithSubject` around a single test, and may not bind.
  - A range pattern (`1..9`, `ast.Pattern.range`) carries the test
    `subject >= start && subject < end` (`<=` for `..>`) in
    `CasePattern.literal`, with `range` set. A bare pattern name that module
    linking resolved to a module-scope variable (`_Rewriter.visit_pattern_name`,
    the scope walk's `visit_pattern_values` hook, sets
    `ast.Pattern.constant` to its linked name) carries `subject == NAME`.
    `CasePattern.values` holds the integers a literal or range covers when
    its bounds are literals; `lower_matches` collects them per `match`
    (`_Coverage.intervals`, `_covers`) to report a covered pattern and to
    accept an integer `match` whose patterns cover its type without `else`.
  - An arm's guard (`Circle(r) if r > 10`) makes its test
    `MatchArm(...) && guard` (`arm_test`), the `MatchArmTest` marked
    `guarded`; the guard reads the arm's names as `CaseValue`s, as a `match`
    expression's value does (`bind_in_expression`). `matches._arm_test` finds
    the test in either form, and `lower_matches` lowers the guard's
    `CaseValue`s and leaves a guarded arm's patterns out of the coverage.
  - A character literal (`ast.Literal.Char`) becomes
    `Cast { IntLiteral(byte), byte }` (`CastKind.Synthesized`), so it is
    typed `byte` where nothing else gives it a type and widens like any
    `byte` value.
  - A decimal literal past `long`'s range (`ast.Literal.Unsigned`, which
    the parser makes for 2^63 to 2^64-1; `-9223372036854775808` it reads
    as one `Integer`) becomes `Cast { IntLiteral(bits), ulong }`
    (`CastKind.Synthesized`, located; `literals.make_unsigned_literal`), so
    it is typed `ulong`. `convert_to_traits` reports it flowing into a
    narrower integer slot (`literals.unsigned_literal` finds it).
  - `x as T` becomes `Cast` with `CastKind.Static`, located at the `as`
    keyword (`ast.Expression.Cast.keyword_span`), and the intrinsic
    `unsafe_cast<T>(x)` becomes `Cast` with `CastKind.Unsafe`, located at
    the name (`build_unsafe_cast`, which reports a missing or extra type
    argument or value). Every cast sema inserts is `Synthesized`. What each
    kind may convert is `casts.check` (`sema/casts.pep`): `as` is a
    `static_cast` (numbers, `bool`, enum to integer, pointer to and from
    `__ptr<void>`, struct to a trait it conforms to, identity), and
    `unsafe_cast` a `reinterpret_cast` (pointer to pointer or integer and
    back, a number to another of the same width), never of a refcounted
    value.
  - A closure literal becomes `Expression.ClosureLiteral` (parameters,
    return type and body, types `auto` where not written); an expression
    body is lowered to `{ return expr; }`. `lift_closures` removes it
    (§2.6).
  - `t.m(args)` becomes `MethodCall`, and a named callee becomes
    `FunctionCall { function }`. A type literal callee (`Box<int>(…)`)
    becomes a constructor call named `"Box<int>"`. Any other callee becomes
    `Invoke`.
  - `[Implicit]` is accepted only on a constructor callable with one
    argument whose parameter is neither the struct nor a bare type
    parameter (`check_implicit_constructor`); anywhere else,
    `reject_implicit` reports it at the attribute.
  - Member names that start with `__` are rejected, except `__acquire` and
    `__release`, which source code may call. Codegen makes either a no-op
    on plain data (`__is_pod`), and on a buffer slot (`_data[i].__release()`)
    steps the count of the reference the slot holds without writing the
    slot: Array's destructor releases its elements that way.
  - An operator the builder has no mapping for is reported (`unsupported
    binary operator '…'`), and a comparison overload (`==`, `<`, …) whose
    declared return type is not `bool` is rejected, as is a `!` or `!!`
    (the truth test) not returning `bool` and a `!`, `~` or `!!` with
    parameters.
  - Structs get `constructors` (at least one: an empty one when none is
    declared; several are named `Point$1`, `Point$2`, … and at most one may
    be `[Implicit]`), `destructor` (`__dtor`), and empty `acquire` and
    `release` shells. Top-level `var`s go to `module.globals`. Externs
    go to `module.externs`.
- **Model** (`sema/model.pep`): `Module { structs, traits, extensions, functions,
  externs, globals, type_aliases, struct_specs, func_specs, trait_types,
  imports, sources }`. Nodes are enum trees (each variant with named
  fields a struct of its own, §8); passes change the `Module` in place. The main node types are `StructDef`
  (a method with type parameters of its own, `map<U>`, sits in
  `generic_methods` rather than `method_members` until specialized),
  `FunctionDef` (methods have `parent: Some(struct)`), `ExternDef` (its
  C symbol is codegen's `extern_symbol`), `VariableDef { kind: Variable|Field|Param, loc, type_loc
  }`, `Expression` (includes intrinsic nodes: `SizeOf`, `Default`, `IsPod`,
  `RefCount`, `Address`, `Atomic*`, `FunctionRef`, `Invoke`,
  `ForIterator`, `WithEntered`, `Destructure`, `Move`, `ToTrait`, `ClosureLiteral`, `MakeClosure`,
  `NamedArgument`, `DefaultArgument`,
  `MethodAddress`, `CallPointer`), and `Statement`. Each node that names something has a
  `Loc`; `Expression.loc()` returns it (`Loc.none()` for literals and
  synthesized nodes).
- **Types**: `TypeName { name, sub_types, flags, labels }` (`model.pep`,
  its methods in `type_name.pep`), with constants `AUTO` (`__auto`),
  `VOID`, and `FUNCTION` (`__function`), and `replace_map` (generic
  substitution); `arithmetic.result_type` gives the type two numbers
  promote to. `static_type_of` gives a best-effort static type for
  operator resolution and print conversion. A method's result on a
  generic instance with no specialization yet comes from the base, its
  parameters replaced by the instance's (`StructTable.method_return`),
  and a call to a generic function whose result names its own parameters
  has no static type until its type arguments are inferred.
- `merge` (`sema/program.pep`, through `_join`) concatenates vectors into
  one namespace. Modules exist only up to `link.link`, which has already
  made every private name unique by mangling it. `sort_globals`
  then orders `module.globals` by `initialization_order`: the
  prelude first (in reverse load order, so the runtime precedes the forced
  imports built on it), then every file after the files it imports. Globals
  are initialized in that order, so an initializer may use an imported
  file's globals, and the runtime's (`_pep_live_allocs_slot`, which every
  allocation counts into) exist before any other initializer runs.

### 2.5 Platform filters (`sema/platform.pep`)

`apply_platform_filters` evaluates every `[Target(<bool expr>)]` against the
**target**: the host, or the platform `--target <triple>` names, with the
build options `-D` defines (`Target.build_options`). The grammar is `OS(Windows|Mac|MacOS|Linux|Wasi|IOS|Android)`, `Arch(x64|aarch64|wasm32)`,
`BuildOption(NAME)`, a `BuildOption(NAME)` compared with a literal (`compare`:
the literal's type says how the value is read), `!`, `&&`/`and`, and
`||`/`or`. `[BuildOption("NAME")]` is `[Target(BuildOption(NAME))]`. Errors
are `Invalid { message, span }`, located at the token (older ones at the
attribute). A comparison with an undefined option is false; the parser
lists every attribute that tests an option in `ast.Module.build_option_tests`,
and `Program.warnings` warns at each such comparison
(`undefined_build_option_comparisons`), once per site. The options are in
the cache key (`cache.Build.name`'s `-D<hash>`, and the checked
runtime's key), `static` blocks read them (`reflect.build_option`,
`has_build_option`), and the language server takes them from its
`buildOptions` initialization option (`build_options` in
`tools/pep-lsp/server.pep`; the analysis worker analyzes with them). The pass drops top-level declarations,
struct/trait/extension members, and attributed blocks whose predicate is
false. Every predicate is validated before anything is dropped, so a typo in
code that another platform would compile is still reported. Attributes other
than `Target` are ignored here, except two: `[Test]` drops a function
unless the build option `TEST` is defined (`pep-build --test` defines it),
and `_check_tests`, run first, reports a `[Test]` that is not a free function
taking nothing and returning nothing, and a `[ShouldPanic]` without `[Test]`.
`keep(&attrs)` is the reusable evaluator;
the loader, linking, and visibility all call it. It is also false for
`[__BuiltIn]` (`ast.is_built_in`), which marks a runtime declaration of a
compiler built-in (`runtime/reflect.pep`): the builder skips such a
top-level declaration (`build_module`), so it declares, links and generates
nothing, while pep-doc, `doc.check_documented` and the language server
read it under the built-in's name (`ast.built_in_name`, `reflect.name`).
`Program.built_in_errors` rejects the attribute outside the runtime
(`Program.in_runtime`). Its functions and methods end in `;` after their
parameter list (`Parser._function_body`); the builder's `function_def` rejects a bodyless function
anywhere else, since only a trait method may lack one.
The target is a `link.Target` (`os`, `arch`, the build options, and the
LLVM triple, or none for the host's own): `Target.parse` reads a
`--target` triple (the supported ones are `supported_triples()`; an iOS or
Android triple is normalized to carry its OS version,
`DEFAULT_IOS_VERSION` or `DEFAULT_ANDROID_API` when it has none, and the
version is dropped again to name the sysroot variable). The loader's
`Setup.target` carries it to linking (`Target.keep`), the `PassState`
carries it through sema, and codegen's `target_triple` reads it, so the
machine, data layout, struct sizes and the context-switch assembly all
follow the target. The language server analyzes a file for another OS by
handing the loader a `Target` of that OS (§8).

### 2.6 Struct bodies (`sema/synthesize.pep`)

The steps after the platform filters prepare struct bodies
(`sema/passes.pep`). First `equatable.derive_equatable` gives each
`[Equatable]` struct (or reference enum) a synthesized `==(other: T): bool`
comparing the tuples of its fields (`(this.a, this.b) == (other.a,
other.b)`, a lone field paired with `true`) and `__hash(): u64` returning
`hash` of the same tuple, leaving out a field marked `[Equatable(exclude =
true)]` or `[Equatable(include = false)]` (`equatable.pep`); codegen's
`__address<T>` and `tuple_hash` call `T.__hash` for a non-null `T`, and
`tuple_hash` leaves out an object element whose `==` is declared but whose
hash would be its address (an `Array`), since equal elements would hash
apart (codegen's `hash_overrides` tells a program's `hash<T>` override from
the generic's specialization). It reports `[Equatable]` on a value type or
a payload-free enum, an `[Equatable]` struct's own `==`, arguments on the
struct's `[Equatable]`, a field's `[Equatable]` outside an `[Equatable]`
struct, and a contradicting `include`/`exclude`.
Then `closures.lift_closures`
turns every closure literal into a synthesized struct
`__closure_N@<namespace>`, numbered within its file (see §4.3) and generic
over the enclosing code's type parameters, and a `MakeClosure` creation
expression, so the new structs get their bodies below like any other.
A closure in a trait's default method is generic over the trait's
parameters and `closures.TRAIT_SELF` (`__This`), the type of its `__this`;
`apply_extensions` (and `value_types` for numbers and enums) maps
`__This` to the conforming type along with `this` when it copies the
method, so each conformer specializes its own closure.
Closures that passes make later (`function_references`, `shared_functions`'
adapters) are named after the declaration whose code makes them instead
(`function_references._owned_closure_name`: `__closure_<escaped owner>_<k>@<namespace>`,
the owner's name escaped so no two owners share a name), so a
specialization makes the same closures whenever it is created.
`strip_bodies` runs next, dropping the bodies of units the build
cache reuses (§4.3). The
struct's fields are `__invoke` and `__destroy` (defaults `MethodAddress`
of `__call` and `__dtor`), so its head matches the function type struct,
then one field per captured local, then `__this` when the body uses `this`
or a bare member of the enclosing struct (rewritten to `__this.member`; a
bare method name, a value, to `__this.m`, or `S.m` when static). The
body becomes the `__call` method; bare captured names become fields through
`convert_member_refs`. Each capture field is located at the closure's first
use of the value, with the captured local's declaration as its `type_loc`
(`shared_functions` reports a capture that is not thread-safe there). The
lift reports an assignment to a captured local
anywhere in the enclosing function, and a method storing a closure that
captures `this` in a field of `this`. Types the literal left out are filled
by `closure_sites.sync_closures`, which `resolve_implicit_types` runs in its
fixpoint loop: parameter and return types from the function type of the slot
the closure flows into, capture field types from the constructor arguments,
and each `MakeClosure`'s type from its `__call`. A slot returning a trait whose type arguments the body binds (`(x) => [x].iterate()` for `(T) => Iterator<U>`) lets the body's struct type the `__call` first, so `U` binds through its conformance (a body naming no parameter may be typed before the slot's trait is known, or after); `PassState.trait_return_closures` keeps the closure in the learning set until the slot is known, and then the `__call` returns the trait. `closures.check_closures`
reports what is still `auto` before `check_function_types`. Methods, constructors and
generic function specializations used as values become closure structs too,
late, in `function_references` (see the pass table).

Then `type_aliases.resolve_type_aliases` runs, so no alias
survives into later stages. Then `synthesize` (`sema/synthesize.pep`),
for each struct:

- `apply_synthesized` inserts the two head fields: `u32 __refcount`
  (default 0) and `u32 __weakcount` (default 1: weak references plus one
  held by all strong references together, as in a C++ control block). It
  fills the `__acquire` body (null check, `++__refcount`, `trace_*` calls)
  and the `__release` body (null check, `--`, and at 0 a call to `__dtor`,
  then `--__weakcount` and `_pep_free(this)` if that reached 0; codegen
  generates a recursive struct's `__release` itself, see §5). Each step
  is an `Expression.CountStep` node, which evaluates to the new count and
  is atomic when the struct is `[Shared]` or a `shared` function type (as
  codegen's `atomic_counts` decides too). Everything else, plain function
  types included, uses a plain load/add/store.
- `finish` builds each constructor. A hidden `size` local is patched with the
  real ABI size in codegen by `Generator.patched_ctors`. The constructor calls `this =
  _pep_malloc(size)` (`patched_ctor` makes the size a literal), initializes each field (explicit default or zero),
  assigns `this.field` constructor parameters (renamed `__init_<field>`),
  runs the user body, and ends with `return this`. The destructor does not
  free the object; `__release` does. The pass appends `__release`, `__acquire`, and `__dtor`
  to `method_members`.

### 2.7 Properties (`sema/builder.pep` `property_members`, `sema/properties.pep`)

A property (`var name: T { get; set; } = init;`, `ast.PropertyDecl`) is
lowered to ordinary members; nothing after sema knows about it.

- **Parser.** `Parser._member` reads a member variable followed by `{`
  (in a struct, trait or extension) as a property, and `_property` builds the
  `PropertyDecl`. Each `ast.Accessor` carries the method it compiles to as
  a `FunctionDecl` (`__get_P(): T`, `__set_P(value: T)`; `body` is `None`
  for `get;` / `set;`), so tools that walk methods, such as the language
  server, see accessor bodies (`PropertyDecl.accessors`).
- **Builder.** `property_members` turns each property into the getter
  method `__get_P`, the setter `__set_P` when there is a `set`, and, when
  the storage is implied (a default accessor, or `field` in a body), the
  storage field: named `P` when `get` is default, else `__field_P`. `field`
  in a body becomes `this.<storage>` (`_FieldReplacer`); default bodies read
  and write the storage. A trait property becomes trait methods; an
  extension property must be computed. Each property is recorded in
  `Module.properties` (`PropertyDef`: owner, accessor kinds, storage,
  `[Shared]`), which the rest of sema reads. `ScopeWalk.walk_property`
  binds `field` and `value` for the visibility checks.
- **Reads and writes** are rewritten by `properties.lower_property`, which
  `resolve_implicit_types` calls first on every expression it walks
  (pre-order), once the receiver's type is known: `x.P` becomes
  `x.__get_P()`, `x.P = v` becomes `x.__set_P(v)`, and `x.P op= v` / `x.P++`
  become a read-modify-write whose receiver, when it is not a plain name,
  is evaluated once through a `WithSubject` (its id comes from the access's
  `Loc`, so builds are deterministic). A default accessor becomes direct
  storage access; inside its own accessors `this.P` is the storage
  (`_is_own_storage`). Assigning a get-only property is allowed only in
  the owning struct's constructors and methods (not its extensions:
  `Properties.extension_methods`), and assigning a `[Shared]` struct's
  property only in its constructors. `P()` on a property that is not a
  function type is an error. Assignments sema synthesizes (`Loc.none()`:
  field initializers, `__copy`) are left alone, except a constructor's
  `this.P` parameter.
- **Typing.** `resolve_implicit_types` (`_TypeScopes.type_of`) gives `x.P` (and a bare `P` in a method) the
  getter's return type; `convert_member_refs` treats a property without a
  same-named field as a member, so a bare name becomes `this.P`.
- **Traits.** `apply_extensions` meets a trait property with the struct's
  property, or with a plain field through a synthesized accessor
  (`_field_accessor`), and reports `'S' does not implement property 'P'`.

### 2.8 Static blocks and reflection (`sema/builder.pep`, `sema/static_blocks.pep`)

`static (captures) { ... }` (`ast.StaticBlock`, parsed by `Parser._static_block`)
is compile-time work; docs/src/language/reflection.md describes the
language side.

- **Parser.** Inside a static block, each `for` loop's variable is added to
  `Parser._qualifiers` until the block ends, so `field.Type` and
  `parse<field.Type>(s)` parse as types the way `module.Type` does
  (`_static_depth`). The scope walk binds `reflect` like a local
  (`ScopeKind.Static`), and linking leaves a type qualified by a value in
  scope alone (`Scopes.in_static_block`).
- **Builder.** `build_static_block` sorts the statements by name:
  one that uses a capture or a runtime local of the block (or calls `get`,
  `set` or `call`) is emitted, the rest is compile-time. The result is a
  `model.StaticBlock` of `StaticItem`s: `For`, `While`, `If`, `Var` and `Evaluate`
  keep their compile-time expressions as the AST; `Emit` holds a model
  statement, built normally except that a sub-expression of only
  compile-time names becomes `Expression.StaticValue` and `x.get(v)` /
  `x.set(v, y)` / `x.call(...)` become `Expression.StaticMember`
  (`static_placeholder`, through the builder's compile-time names, which
  `expression` checks first); `EmitIf` is a runtime `if` whose branches
  hold items. `break`/`continue` in a compile-time loop is a `Jump`; one
  under a runtime `if`, or outside any compile-time loop, is an error
  (`_StaticNames.loops`, `_StaticNames.in_runtime_if`).
- **Module scope.** A module-scope `static { ... }` is
  `ast.Declaration.Static`. The parser also declares each `const` at the
  top of the block as a module-scope variable (`static_constants`, with
  the block's attributes and `export`) whose initializer is its own name,
  so linking, visibility and mangling see an ordinary constant.
  `module_static_block` builds the block with
  `_StaticNames.module_scope` (nothing may be emitted; `case.get()` is
  evaluated) into `Module.static_blocks`, and
  `static_blocks.expand_module_blocks`, first among the passes after
  `check_attributes`, runs each and gives each constant the value it
  computed, matched by the location of its name.
- **Generic code.** The walks in `sema/passes.pep` reach the emitted
  statements, so the early passes lower them with the rest of a generic
  base; passes with their own statement walks skip `Statement.Static`.
  Specialization records its type arguments in the block
  (`replace_types._substitute`, from `replace_statement_types`) and
  substitutes them in the emitted statements.
- **Expansion.** `static_blocks.expand` replaces each block in concrete
  code (non-generic functions, methods of structs that are not generic
  bases) with a block of what it emits: it evaluates the compile-time items
  (`_Expander.evaluate`, a small interpreter over `_CtValue`s: numbers, `bool`,
  strings, enum cases, members, functions, lists and attribute values),
  unrolls each `For` into one block per element and each `While` into one
  per iteration (at most `MAX_ITERATIONS`; a `Jump` sets
  `_Expander.jump`, which skips the rest of the pass), starts each pass
  that emits anything, and the branch a compile-time `If` kept, with a
  `Statement.StaticPass` at the header holding the compile-time variables
  in scope (`_Expander.debug_values`, as `StaticConstant`s; see §4.4),
  and fills in the emitted
  statements: `x.Type` types first (`replace_body_types`), then each
  placeholder (`_Expander.fill`). The passes call it at the start (concrete
  code, `lowered = false`), after the first specialization, inside the
  specialization loop after `specialize_functions` and after
  `specialize_methods` (an expansion forces `resolve_implicit_types` and
  another round, since emitted calls ask for new specializations), and
  after the loop's `apply_extensions`. `remove_from_generic_code` then
  empties the blocks left in generic bases. Errors carry a note per `for`
  pass, one naming the specialization, and one per `Module.spec_requests`
  entry back to the non-generic code that asked for it
  (`instantiation.with_requests`), so an error inside `json`'s converters ends
  at the user's `json.encode(job)`.
- **`--emit-static`** (`sema/static_source.pep`, `driver/emit_static.pep`).
  `emit_static.check_recording` runs the passes with `PassState.static_recording`
  set, and while it is set the expander renders each block it expands as
  source beside the statements it builds: an emitted statement is its
  source as written (its span, widened over parentheses), with each
  placeholder `fill` replaces given an edit: a literal for a static value
  (`_CtValue.source`, inlined into an interpolated string's text), and
  for a static member the source of what it became (`value.x`, `f(args)`,
  `value is Shape.Rect`, a `match` reading a case's value), with its
  arguments rendered the same way; each `x.Type` and type parameter outside
  strings and comments becomes the type. A pass, a kept branch and a nested
  block are `{ ... }`; a runtime `if` is written around its branches. Each
  finished block is an expansion (its span, its specialization's type
  arguments, the lines); module-scope blocks are not recorded. The driver
  copies the program's files under the entry's folder into `-o`, replacing
  a concrete block with its expansion between `# static (...) expanded
  from` and `# end static`; a generic free function stays and is followed
  by one concrete override per specialization (`describe<Point>(value:
  Point)`, its text with the type arguments substituted and its blocks
  expanded); a block in other generic code stays, with its expansions
  above it as comments. `pep-fmt`, beside the compiler or on `PATH`,
  formats the copies.
- **`-g --debug-static=expanded`** points the debug info at that copy. The
  build records the passes too (`PassState.static_recording`), and
  `write_debug_sources` writes each user file with an expansion,
  unformatted, as `<name>.static.pep` beside the output, appends its text
  to `PassState.sources`, and fills `Generator.static_locations`: while
  recording, each emitted statement, runtime `if` and pass header gets an
  id; the rendered parts carry it, and the driver tracks where each lands
  in the copy, so each pass lists its statements by source `Loc` and id.
  Codegen resolves them when it enters the pass's block, and
  `DebugInfo.place` moves any location inside such a statement to the same
  relative line in the copy (§4.4). The option builds without the cache: a
  cached unit's sema, and so its expansions, would be skipped.
- **Cases.** A case of a reference or `[Value]` enum lists its `values` as
  members whose `field` is the payload field (`Circle.radius`), so `get`
  reads it; `case.matches(v)` emits a `__tag` comparison (a comparison with
  the value for an integer enum), and `case.get(args)` the case's static
  method `Shape.Circle(args)`. A compile-time `var` in a static block is a
  parser qualifier like a `for` variable, so `first.Type` parses, and
  `generics._contains_param` leaves any `x.Type` to the
  specialization that expands the block.
- **Reflection.** `reflect.properties<T>()` lists the public fields and the
  properties of a struct, in source order; `fields<T>()` every field but
  synthesized ones, only in `T`'s file. A member's attributes are its
  field's, or its getter's for a property.
- **Attributes.** A struct marked `[Attribute]` is an attribute.
  `check_attributes` (first among the passes) reports an attribute that
  is neither one the compiler knows (`_is_built_in_name`) nor an `[Attribute]` struct
  (`unknown attribute 'X'`, at the name), an argument that is not a
  constant of its field's type, and an attribute field of another type.
  `_attribute_value` binds the arguments to the struct's `_slots`: the
  constructor's parameters (`this.f`, or assigned to a field in its body)
  or, without one, the fields in order. The built-in attributes are also
  declared as `[Attribute]` structs in `runtime/attributes.pep`
  (`_is_built_in_name`: a struct named like one); `check_attributes` leaves their
  arguments to the compiler's own checks, and `_built_in_value` reads a
  value through the same binding, except `Target`, which holds its
  condition as written, and `BuildOption`, which holds its option's name.

## 3. Sema transform passes (`sema/`)

`run_steps_with(module, state, limit)` (`sema/passes.pep`) runs the steps
below in order, one `_step` per pass run, and stops after the first pass
that reported an error (`state.report`); `run_passes` runs them all. The
first `PORTED_STEPS` run once each, then the specialization loop runs its
steps for as many rounds as the program needs, then the passes after it.
`PEPC_TRACE_STEPS=1` prints each step's time, and
`pep-build --emit-model --emit-model-step N` prints the model after the
first N steps. The order came from the C++ implementation, and several
passes run more than once on purpose. What the passes share between steps
(the first error reported, closure numbers, enum representations and
methods, reference enums, value structs, `reflect.print`'s notes and
deprecation warnings, the next `WithSubject` id) is the `PassState`
(`state.pep`); where the table below says "thread-local" or "registry", it
is a field of the `PassState`.

The passes share the walks in `sema/walk.pep`: a `Rewriter` sees every
expression of a block before its sub-expressions and may replace it
(`rewrite_block`, `rewrite_statement`, `rewrite_expression`), and
`rewrite_children` visits a node's direct sub-expressions, for a walk that
decides per node whether to descend. **Where code lives** is listed once,
in `sema/places.pep`: `for_each_place` hands a `PlaceVisitor` each `Place`
(a field's or global's initializer, or a function's parameter defaults and
body: a member, generic method, free function, extension method or trait
default method, with its owner and `this` type), optionally only the
compilation unit's own (`unit`), without the extensions' copies, or with
the templates (generic methods, trait defaults). `rewrite_places`,
`rewrite_concrete_places` (skipping generic bases) and
`closure_sites.rewrite_module` apply a `Rewriter` to them;
`resolve_injected`, `gather_generics`, `specialize_used_methods`, `check_interpolations`,
`check_ranges`, `resolve_operators`, `verify_injected` and the site walks
of `closure_sites` (`for_each_site`, `select_sites`, `sync_closures`) walk
them, so each reaches defaults and initializers too. **A new kind of place
is added to `for_each_place`**; a pass that walks code itself should use it.
`closure_sites.expression_children` lists a node's direct sub-expressions.
**When you add a model `Expression` variant, add it to
`rewrite_children`.**

`resolve_implicit_types` runs eight times and loops inside each run, so its
helpers skip work that cannot change anything: `sync_closures` learns
nothing once no closure struct has an `auto` capture, `__call` parameter or
return type, and otherwise walks only the functions that create such a
closure (a creation's expected type comes from its own function); its table
holds generic bases' fields too, so a closure created in a generic closure's
method can type what it captures from `this`, and learning stops once it
has; `bind_function_values` types expressions only when some name could
still bind to an overload, and `bind_generic_function_values` only when an
untyped name of a generic function appears; `_ImplicitResolver._infer_type_arguments` and
`_resolve_method_overload` check that a name is a generic function, a generic
method or a method overload set before typing the receiver or the
arguments, and `_TypeScopes.overload_call` checks that a call names a set
(`Overloads.call_set_name`) before parsing its type arguments; and
`traits.used_trait_types` prints and parses only types that spell a
trait's name as a whole word (`ArrayIterator` does not mention
`Iterator`). `specialize_methods` builds its `StructTable` only once a call
names a generic method. Between its runs it keeps, in
`PassState.implicit` (`ImplicitMemo`), what each callable looked up and its
fingerprint (`_Worklist`), so a run walks only the callables whose code or
lookups changed since; the declarations as the last round that took them
saw them, so the next run announces what changed since, this run's own
changes included, without taking them again at the end; and which
callables' last walk left a call settling by arity could pick, the only
ones the settling run walks for that reason. A round that binds nothing
hands the overloads `bind_function_values` built to the walk.

`resolve_type_aliases` also expands aliases in constraints, in the arguments
of each `TypeUse` (not its head, whose own constraints are checked), and in
restated extension constraints, and keeps the aliases that constrain a
parameter in `Module.constrained_aliases` so their uses can be checked.

`resolve_type_aliases` reports a recursive alias
at the alias's name (`type alias 'A' refers to itself`, with a note at each
alias the cycle passes through). Because `check_function_types` is a
transform step, the driver and the LSP both run it.

Error reporting inside passes goes through `state.report(diag)`, which
keeps only the **first** diagnostic of a run. Other per-run state is in
the `PassState` too, the target among it. No counter that numbers synthesized
names is process-wide: closure structs are numbered in
`PassState.closure_counts`, and the builder's counters (`_Builder.for_loops`,
`with_blocks`, `tuples`, `matches`, `tries`) belong to the builder of one
file. This lets tests compile
concurrently on separate threads. `resolve_operators` numbers its
`_idx_tmp_N` temporaries within each function, after any that function
already declares, so they do not depend on the order functions are
resolved in. Since the builder's counters start over for
each file (`build_file`), the hidden locals of one file, and the bitcode
of its build cache unit, do not depend on which files the program built
before it.

**Output is deterministic**: the same program compiles to the same IR and
object bytes on any thread, after any other programs, in any process. So
never let a `HashMap`/`HashSet` iteration order decide what is emitted or in
what order (`gather_generics` keeps the uses it finds in a sorted `Map`),
and never number synthesized names with a process-wide or never-reset
counter. The build cache, which reuses per-file objects and checked
compilation units, depends on this.

`resolve_implicit_types` builds its program-wide lookup tables (`ImplicitTables`:
struct fields and methods, function return types, function values,
generic signatures, globals) once per call, as hash maps, and every
function's `_TypeScopes` shares them; the struct being resolved overrides its
own entries through `_TypeScopes.own`. `TypeName.is_auto` tests for `auto` without building a string.

## 4. Codegen (`codegen/`)

`codegen.generate(module, state, ...)` makes a `Generator` (`generator.pep`)
for the target's data layout and runs it over the checked model, through
the `pepper-llvm` bindings to LLVM's C API. It generates the whole program
as one module, recording in `owners` the file that declares each symbol;
`partition.pep` then splits it into parts (§4.3).

1. **Instantiation.** Every concrete struct is registered as an opaque type
   first (a field may name a struct declared later). Then:
   `instantiate_struct` (LLVM struct body, in which a struct-typed field is
   a `ptr` slot, so a struct may hold its own type) → ABI sizes via
   the target machine's `size_of` → `instantiate_methods` → `instantiate_ctor`
   → `instantiate_extern` → `instantiate_function`. Generic bases (`st.name
   == st.ty.name` with generic `ty`, or `is_generic_func`) are skipped;
   sema has already cloned the concrete specializations.
2. **`emit_globals`.** Module-scope variables become LLVM globals. A
   constant initializer is set directly, a string constant's included
   (`const X = "text";`, `string_constant_value`), so nothing reaches an
   unread one and the linker drops it. Other initializers go into
   `__pep_global_init`, registered in `llvm.global_ctors`, in the order of
   `module.globals` (see `initialization_order`, `sema/program.pep`). A `[ThreadLocal]`
   global (`is_thread_local`; `codegen/globals.pep`) is an LLVM
   `thread_local` in the initial-exec model, with the constant initializer
   `shared_type_checks.thread_local_constant` folds and no debug info. The
   program module then defines `_pep_release_thread_locals` (a cached unit
   only sees the runtime's `extern` for it; `partition.prepare` leaves the
   name unspelled and external): for each thread-local holding references,
   last declared first and in four passes, it stores the default and
   releases the old value. `async`'s `_async_thread_main` calls it after the
   thread's body. There is no operating-system exit hook (a pthread key,
   `__cxa_thread_atexit`): the main thread and threads C started never
   release their thread-locals.
3. **Codegen.** `codegen_struct` (patched ctor plus methods, mangled as
   `Struct.method` with an implicit `this` parameter 0; static methods have
   no `this`) and `codegen_function`. Then the module is verified
   (`ir.verify()`, in `Generator.generate_items`). IR it rejects is a type check sema missed; `verification_error` locates the
   error at the first function the verifier rejects, and names it.

How the language lowers:

- **Structs are references.** A struct-typed local, field, parameter, or
  return value is an LLVM pointer to a heap object allocated with
  `_pep_malloc` (zeroed). `sizeof(StructType)` is
  pointer-sized, because a struct occupies a pointer-sized slot. The
  object's ABI size is used only inside the constructor and by
  `Expression.Allocate` (the synthesized copies' allocation: zeroed, both
  head counts 1, an owned rvalue like a constructor result). They, and a
  trait value's box (`box_value`), pass it
  as a constant, and `call_function_result` lowers a `_pep_malloc` of a
  constant size to `_pep_malloc_uninit` plus an inline `llvm.memset`
  (`build_zeroed_allocation`): the object is as zero as before, but
  LLVM deletes the bytes the constructor's field stores overwrite and folds
  the loads of their old values, so no runtime `memset` runs.
- **Stores are type-checked** (`codegen/address.pep`). LLVM accepts a store of any
  type through an opaque pointer, so a value wider than its slot silently
  overwrites the next field or the next heap object. `Address.store`, and
  the raw `builder.store`s into a local, the return slot, or an array element,
  first call `check_store_type`. It fails with `internal error: storing a
  value of LLVM type 'X' into 'name' ('T', LLVM type 'Y')`, located at the
  node being generated, whenever the two LLVM types differ, except into a
  slot still typed `__auto` (a `var` sema never inferred, an `i32` slot):
  that is `cannot infer the type of 'name'; write its type in place of
  'var'`, the user's workaround for an inference gap. A field's
  `Address` takes its LLVM type from the object's layout
  (the struct type's `field(index)`), so a struct-typed field is a `ptr` slot
  there, not the struct body. A new store into a typed slot goes through
  the same check.
- **Types** (`codegen/types.pep`): `Types.get(name)` maps primitive aliases (`int`
  and `i32`, `ulong` and `u64`, `char` and `i8`, …) to LLVM types. Any
  `T*` maps to an opaque pointer. Registered structs map to their struct
  type. A specialization name falls back to its base struct when it is not
  registered itself.
- **Generics**: none reach codegen. Sema monomorphizes them, and codegen
  looks up `Array<int>` by its full name.
- **Externs**: declared with the C prototype. Variadic externs use C default
  promotions. Narrow integer arguments get `signext`/`zeroext`.
  `[Link(name = "sym")]` changes the symbol (`extern_symbol`). A string
  literal passed to an extern is passed as its raw NUL-terminated global.
  A call to an extern whose C symbol is `memcpy`, `memmove` or `memset`
  lowers to the LLVM intrinsic (`build_memory_intrinsic`), since a `void`
  extern is declared returning `i32` and LLVM would not recognize the
  builtin; so a constant-size copy optimizes to loads and stores.
  An extern whose symbol starts with `llvm.` (`[Link(name = "llvm.ctpop")]`)
  is an LLVM intrinsic (`codegen/globals.pep`): `instantiate_extern` declares
  it with the prototype as its signature (a `void` return is `void`), picking
  an overloaded intrinsic's mangled name from the prototype (return type,
  first parameter, or both) and checking each candidate by calling it in a
  scratch module and running the verifier, so a mismatch is an error at the
  extern. `codegen_call` checks each argument the intrinsic marks `immarg`
  is a constant (`check_intrinsic_argument`), located at the argument.
  `partition.prepare` leaves `llvm.*` symbols alone. The runtime's integer
  bit methods, float functions (`runtime/number.pep`) and the `hint` module
  are written with these.
- **Branch hints**: `[Likely]` or `[Unlikely]` above an `if` or a `match`
  arm is parsed into that block's attributes (`Parser`, where it reads an
  `if` and a `match` arm); the builder checks them
  (`check_branch_hints`), and a `match` lowers to branches whose blocks
  are the arms' blocks, so they arrive on `Branch.if_block` or
  `else_block`. `weigh_branch` turns them into `!prof` branch weights
  (`branch_hint`).
- **Cold functions**: `[Cold]` on a function, method or constructor
  marks it rarely called, as `T.__last_release` is (`cold` and
  `noinline`, `codegen/refs.pep`); the allocator's slow paths use it so
  `_pep_malloc` and `_pep_free` stay small enough to inline. `Cold` is a
  built-in attribute name (`static_blocks._is_built_in_name`);
  `platform._check_cold` rejects arguments and a target that is not a
  function, and `functions.mark_cold` gives the LLVM function `cold` and
  `noinline`.
- **Builtins resolved by name in `codegen_call`**: `release<T>(v)`,
  `__is_pod`, and `__default<T>`. `__caller_location()` is handled in
  `codegen_expr`: a constant C string `file:line:col`
  (`location_text`, null when unknown) for its own `Loc`, or, while a call's
  default arguments are generated (`codegen_default` sets
  `in_default_argument`), for the call's (`call_loc`, which `codegen_expr`
  sets for each `FunctionCall` and `MethodCall`). So `assert`, `panic`,
  `_pep_assert`, `_pep_check_bounds` and the runtime's checking methods take
  `location: __ptr<char> = __caller_location()` and report their caller;
  the null checks codegen emits pass their own location
  (`located_assert`). Without the `bounds` or `null` runtime
  check, a call to `_pep_check_bounds` (the runtime's index check) or
  `_pep_assert` (the null checks) is dropped, arguments and all.
- **Runtime checks** (`codegen/checks.pep`): `codegen_binary` and
  `codegen_unary` send integer `+ - * / % ** << >>`, unary `-`, `++` and
  `--` through `checked_int_binary` / `checked_arithmetic`, which use
  `llvm.{s,u}{add,sub,mul}.with.overflow` and `panic_if`: a branch to a
  `check.fail` block calling `_pep_panic("integer overflow in 'int'
  addition", "file:line:col")` (`llvm.trap` without the runtime). Two constant operands
  are checked at compile time instead, an error at the operator.
  `Generator.runtime_checks` turns kinds off: overflow then wraps, a
  shift count is masked, a division is plain `sdiv`/`udiv`. The struct,
  `RuntimeChecks`, lives in `codegen/checks.pep`, which also reads
  `[Unsafe("overflow,bounds")]` (`function_checks`; a list it cannot read
  keeps every check).
  `codegen_function` narrows `runtime_checks` to the function's own for its
  body, and `sema/closures.pep` copies `[Unsafe]` onto the closures lifted
  out of it. A per-function `bounds` reaches into the runtime's indexers
  through the caller location: in such a function a `__caller_location()`
  default argument starts with `UNCHECKED_BOUNDS_MARK` (byte 1), and
  `_pep_check_bounds` passes such a location (`_pep_panic` prints it
  without the mark); with the location a constant, the inlined check folds
  away. Narrow types
  compute at `int` (C promotion), so only `int` and wider overflow.
  The arithmetic intrinsics `__wrapping_add/sub/mul(a, b)` and
  `__add/sub/mul_overflows(a, b)` are `BinaryOp` variants that the builder
  makes from those calls (`builder._intrinsic`); the overflow tests work at
  the lhs's own width and give `bool`. The integer types' `wrapping_`,
  `checked_`, `saturating_` and `overflowing_` methods (`runtime/number.pep`)
  are written with them. `call_function` declares unknown
  runtime helpers such as `_pep_malloc` on demand.
- **Intrinsic nodes** in `codegen_expr_unlocated`: `SizeOf`, `Default` (zero
  or null), `IsPod` (true unless the type is a reference or a tuple holding
  one, `is_pod_name`), `RefCount` (an atomic load), `CountStep` (an
  `atomicrmw` on the head count at byte offset 0 or 4, monotonic up and
  acq_rel down, or a plain load/add/store), `FunctionPointer` (the LLVM
  function's address; a static method is `Owner.name`), `Address` (FNV-folds POD values),
  `AtomicLoad` (acquire), `AtomicStore` (release, via `xchg`),
  `AtomicCmpXchg` (acq_rel/monotonic; floats are bitcast), `AtomicFetch`
  (`atomicrmw` acq_rel); their operands are converted to a numeric `T` as
  arguments to a `T` parameter are (`atomic_operand`), so a literal fills
  the whole slot; and `ConstructAt` (`__construct_at(p[i], v)`, an
  element store into a slot the runtime knows is empty:
  `codegen_assignment` with `construct`, which acquires through
  `construct_refcount_ops` and never loads or releases the old occupant).
- **`match` expressions and `is` tests**: `WithSubject` (`with_subject`)
  evaluates the subject once, panics on a null reference enum, keeps the
  value in `subjects` by id for `Subject` to read, then evaluates the body
  (a `?:` chain). An owned subject is a deferred temporary, released at the
  end of the full expression, so an arm may yield one of its fields. A `?:`
  with one owned arm is owned: `codegen_ternary` acquires the other arm's
  read (`copy_arm`), as C++ yields a prvalue copy there. Numeric arms of
  different types convert, each in its own block before the branch, to
  `arithmetic.conditional_result` of the two (`convert_arm`), the type
  sema's `static_type_of` and codegen's `value_sema_type` report for the
  `?:`, so a `return`, initializer, argument or assignment converts from it.
- **Enum cases that carry nothing**: `StaticCase` (`static_case`) is the
  global `<Enum>.case<tag>`, the enum's struct with its counts at
  `STATIC_REFCOUNT` and 1, its `__tag` set and every other field zero. It
  is emitted with external linkage, like a function, and
  `partition.prepare` makes it `linkonce_odr` (in a comdat), so the units
  that use it share one object and `===` holds across files. A reference enum with such a case
  gets the same guard as a plain function type (`skip_static_objects`,
  added by `synthesize.apply_synthesized`): its `__acquire` and
  `__release` leave a count at or above `STATIC_REFCOUNT` alone, so the
  object any thread may reach is only ever read.
- **Shared string literals**: `StaticString` (`static_string`) is one
  private constant global per literal and unit, `{ String, [n x i8] }`:
  the `String` object, its counts at `STATIC_REFCOUNT` and 1, `_size` and
  `_length` set and `_data` pointing at the NUL-terminated bytes that
  follow it. Named `str.object` so `partition.prepare` orders it with the
  other string constants. pepc names it `str.object.<hash of its text>`
  (`codegen/calls.pep`): `partition.prepare` makes it `linkonce_odr`, and
  a numbered name would let an object kept in the build cache meet a
  different literal under its name. It is only ever an argument to a parameter whose
  copy the caller makes (`copy_argument` makes none for it) or a receiver,
  so no count step reaches it, and it can be constant.
- **Function values**: `FunctionRef` produces a static function object
  (`__function_object.<name>`, or `__function_object.shared.<name>` for a
  `shared` function type) whose `__invoke` points at a thunk
  (`__function_thunk.<name>`, one per function; for an `extern` function,
  which `resolve_implicit_types._referenceable_functions` lists unless it is
  variadic, the thunk calls the C function). Its strong count starts at
  `STATIC_REFCOUNT`, so it is never freed. `codegen_invoke` loads `__invoke` and calls
  it with the signature of the static type. A callee of C function pointer
  type goes to `codegen_call_c_function` instead: an indirect call to the
  address itself with the C signature, after a null check. `MakeClosure` is its closure
  struct's constructor call, used as the function value: the constructor
  stores `MethodAddress("__call")` (the method itself, whose `this` is the
  object) in `__invoke` and `MethodAddress("__dtor")` in `__destroy`.
- **Default arguments**: `param_defaults` stores each callable's default
  expressions. `missing_args` pads trailing arguments at the call site and
  reports `too many/too few arguments to 'f'`.
- **Control flow**: nested blocks, branches, and loops get their own basic
  blocks. `Frame.exited` suppresses dead code after
  `return`/`break`/`continue`. Every unterminated block is patched to branch
  to the function's return block. Return values go through a `retval`
  alloca in the entry block. Locals get their slots there too
  (`entry_alloca`), so a `var` inside a loop does not grow the stack.
- **Errors**: codegen functions return a `Result`. A node that can fail
  and has a `Loc` passes its result through `locate(result, node.loc)`,
  which keeps the innermost located node's place (`error_loc`); `generate`
  turns the error into a `Diagnostic` there.
- **Target** (`codegen/target.pep`): `initialize_backends` registers the
  x86, AArch64 and WebAssembly backends on every host, so `--target` can
  name any, and `target_triple` names the target's triple (`--target`'s,
  else LLVM's default), for which the driver makes the machine
  (`llvm.TargetMachine.create`). Every call site shares these. Read that
  file's header before touching backend registration. For
  `wasm32-wasip1`, the driver's `place_constructors` renames `main` to
  `__main_void` (`use_wasi_main`), which wasi-libc's `_start` calls.
- **32-bit targets** (wasm32): an extern's `long` and
  `ulong` are declared as C's pointer-sized `i32` (`c_abi_type`) and the
  result widened back (`widen_c_result`, recorded in
  `extern_narrow_results`), in direct calls, extern function values and
  calls through C function pointers; a void extern is declared `void`.
  WebAssembly traps on any signature mismatch, so every declaration and
  call must agree exactly. A Pepper function whose address goes to C
  (`Expression.FunctionPointer`: `__function_pointer`, an `extern`
  function value) with a `long`/`ulong` parameter or result is reached
  through `__c_abi.<name>` (`c_abi_adapter`), which has C's signature.
  `sizeof` of a struct slot is the target's pointer size. Vtable type ids fold to 32 bits there
  (`type_id_value`), since a vtable slot is pointer-sized.
- **Runtime on WASI.** Each platform module (`os`, `io`, `async`,
  `process`, `tls`) has a `*_wasi.pep` beside its `*_posix.pep`, whose
  POSIX-only files target `OS(Linux) || OS(Mac)`. `io/sys_posix.pep`
  stays `!OS(Windows)` and picks wasi-libc's flag values, errno codes and
  `stat`/`dirent` layouts with `OS(Wasi)` declarations. Threads, fibers,
  sockets, TLS and processes are stubs that panic or return `ENOTSUP`.
- **Runtime on iOS and Android.** The target's `os` is `"ios"` or
  `"android"`, and `_os_matches` (`link/platform.pep`) makes `OS(Mac)` hold on iOS and
  `OS(Linux)` on Android (as `TARGET_OS_MAC` and `__linux__` do), so the
  macOS and Linux code serves them; the few declarations that differ add
  `!OS(IOS)` or `!OS(Android)` and a variant: bionic's `__errno`, the
  NDK's `_Unwind_Backtrace` for `debug` (bionic's `backtrace` is API 33),
  and plain
  `stat`/`readdir` on x86_64 iOS, which has no `$INODE64` variants.
  `posix_spawn_file_actions_addchdir_np` (bionic API 34) is looked up
  with `dlsym`, as on Linux. `scripts/mobile-test.sh` runs the docs examples in the simulator and
  the emulator on a Mac (see the book's `language/mobile.md`).

### 4.2 Traits used as types (`sema/traits.pep`, `sema/convert_to_traits.pep`)

A trait name is a type (`Shape s`, `Array<Shape>`, `Iterator<int>`). The
value is a struct reference with its concrete type erased, like a
`shared_ptr` to an abstract base with a virtual destructor.

- **Sema.** `traits.instance` specializes a trait at its type arguments and
  keeps its *dispatchable* methods (instance methods whose signature does not
  name `this` as a type) in declaration order: that order is the vtable's.
  `static_type` knows trait types, so method calls on them type-check and
  infer like struct calls. `convert_to_traits` inserts `ToTrait { value,
  from, to }` at conversion sites; conformance is nominal (`extend S with
  Tr`). Specialization substitutes a struct's declared traits
  (`Box<int>` gets `Getter<int>`).
- **Representation.** `Types.register_trait` maps a trait type to
  `[2 x ptr]`: the object and the vtable. An array rather than a struct
  type keeps trait values out of every "struct type means pointer" path;
  they load, store, pass and return by value. `reference_value_type` gives
  the slot type of any reference, `object_pointer` its object.
- **Vtables** (`vtable`, emitted on first `ToTrait` for a pair):
  `__vtable.<Struct>.<Trait>` = `[S.__release, S.__acquire, S.m1, …]`,
  ending with `S._pep_copy_trait`, the member `copies` adds to every trait
  (see `synthesize_copies` in the pass table). A
  slot of an overloaded name holds the struct's member of that set with the
  slot's parameter types (`StructDesc.method_params`). A
  trait method the struct implements with a struct result where the trait
  returns a trait type goes through `covariant_adapter`, which converts
  the result.
- **Thunks** (`instantiate_trait`): `Trait.__acquire`, `Trait.__release`
  and `Trait.method` are ordinary functions taking the trait value as
  `this`. They null-check (refcount thunks) or assert (method thunks) and
  call through the vtable. Because they are named like struct members,
  every refcount path in §5 (`T.__acquire`/`T.__release` by type name) and
  every method call works on trait values without special cases. The
  release thunk runs the concrete `__release`, so the last release runs the
  concrete destructor.
- **Converting back** (`matches.lower_matches`, codegen
  `codegen_from_trait`). Every vtable ends with its struct's type id
  (`type_id_value`, a hash of the struct's name: a vtable is private to its
  unit, so its address is no identity). A type pattern over a trait value
  (`is Circle`, `Circle(c) =>`, and `as?`, which the builder lowers to a
  `match`) becomes `Expression.FromTrait`: with `test`, whether the id is
  one of `candidates` (the struct named, or each struct that declares both
  traits; false for a null value); without, the binding's value: the
  object, a value struct copied out of its box, or for another trait the
  object paired with the vtable `select`ed by id. The binding reads the
  `match`'s hidden subject, so it is an lvalue read like any other.
- **Weak trait values.** `__weak<Shape>` (inside `Weak<Shape>`) is the
  object's weak reference plus its vtable. Sema synthesizes its weak
  struct as for a struct target (atomic counts, since the object may be
  `[Shared]`), and `convert_to_traits` turns a `__null` flowing into one
  into `Default`. Codegen keeps the struct out (`weak_traits`) and gives
  the type a trait value's `[2 x ptr]` layout with its own
  `__acquire`/`__release` (`emit_weak_trait_thunk`: an atomic step of the
  head's weak count, freeing at 0); `codegen_weak` takes the object out of
  the pair and upgrades to the same pair, or a null one. A value struct's
  box (`box_member`) gives up the strong references' weak reference at
  its last release, as `synthesize` does for a struct, so a weak reference keeps the
  box's memory.
- **Identity.** `==`/`!=` on trait values compare objects, and
  `store_refcount_ops` treats the same object as self-assignment.
  `__address`/`__refcount` read the object. Array slots of a trait type are
  16 bytes, which Array's shifts and swaps move whole as bytes.

### 4.6 Tuples (`sema/destructures.pep`, codegen `register_tuple`)

A tuple is a value, like a `std::tuple` of `shared_ptr`s: no allocation, one
reference held per reference element.

- **Representation.** `register_tuple` maps `__tuple<A, B>` to a literal
  (unnamed) LLVM struct of its elements' slot types (a struct element is its
  pointer, a trait element its `[2 x ptr]`). Named LLVM structs are objects
  used through pointers; `types.is_object` tells the two apart, so
  parameters, returns, slots and array strides keep a tuple by value. The
  sema tuple struct gets no object layout, constructor or methods.
- **Refcounts.** `is_reference_name` includes tuples, and
  `emit_tuple_refcount_thunk` emits `Tuple.__acquire`/`Tuple.__release`,
  which step each reference element. So every §5 path (copies, scope exits,
  stores, temporaries, fields, the destructor's field releases) works on
  tuples by type name. `store_refcount_ops` skips the identity test for a
  tuple: acquiring the new elements before releasing the old ones makes
  self-assignment safe.
- **Literals.** `codegen_tuple` builds the aggregate with `insertvalue`: an
  lvalue-read element is acquired, an owned rvalue moves in, and numbers
  convert to the element type.
- **Element reads.** `t.0` is an `extractvalue`; an owned-rvalue tuple
  (`f().0`) goes on `deferred_temps`.
- **Destructuring** moves: `var a = __tuple_N.k` (`destructured_element`)
  takes element `k` without acquiring and clears it in the hidden tuple, so
  the binding holds the only reference, as a C++ structured binding would;
  `_` elements stay in the hidden tuple until its scope exits.
- **Comparing and hashing.** `codegen_binary` sends a tuple `==`/`!=`
  to `tuple_equal`, which compares element by element (`value_equal`: an
  element's own `==` when its type has one, else by value or identity; of
  an overloaded `==`, the member taking the element's own type, found by
  `equality_method`).
  `Expression.Address` on a tuple (what `hash<T>` uses) is `tuple_hash`,
  which folds each element's `hash<E>` (or its bytes) with FNV-1a, so a tuple
  is a `HashMap` key. Its text comes from the runtime's `to_string<A, B, ...>`
  overloads (runtime/string.pep), which overload resolution prefers to the
  generic `to_string<T>` as more specialized.
- **Generic bases.** A tuple naming a generic parameter (`(K, V)` inside
  `HashMap`) is skipped by `register_tuple`; only its specializations get a
  layout.

### 4.1 Object emission and linking (`driver/build.pep`, `driver/parts.pep`, `driver/linker.pep`)

`build` generates the whole program as one module with the target's
machine (the host's, or `--target`'s; see 2.5), and `codegen.prepare`
splits it into parts: one or more per compilation unit, and one for the
program's entry points (§4.3). A unit larger than `_PART_SIZE` (blocks and
definitions, `codegen.file_sizes`) is split by file into parts of about
that size, which depends on the unit alone, so its objects are the same in
every program. `compile_parts` (`parts.pep`) compiles the parts the cache
does not have: one in this process, more in `pepc --compile-part <dir>
--part <N>=<object>...` children, one per logical CPU at most, given parts of
about the same size. Each reads the bitcode `compile_parts` wrote to
`<build>/<name>.<pid>` (a folder per build, so builds at once do not meet)
once, keeps all its parts (`codegen.keep_parts`), then compiles each but
the last in a copy of the process (`_compile_forked`, `process.fork`),
which keeps its part from the module it shares with no clone (an edit keys
every part, and cloning the module was most of that), and the last in the
child itself. Where processes cannot fork (Windows) it halves them
(`_compile_halves`): the first half's parts kept in a copy, the rest in the
module, each half halved again, so each part is kept from a module about
twice its size, not from all the child's parts. Each part is optimized and
emitted.
A compilation unit's parts, a worker's or the last's, are also cached by
their code (`PartCache`): once a part is kept, its key (`_part_key`) hashes
the compiler, the machine, level and mode, and the part's IR as text (the
module's name, the work folder's, left out). A part whose key the cache
has copies its object and `.defines` from there rather than being
optimized and emitted, so an edit that changes one file of a compilation
unit compiles only the parts its code changed.
Two things keep an edit's change to few parts. A compilation unit's code
is generated with `Build.separate_locations`: the `file:line:col` strings
of checks and `__caller_location()` are weak globals named by their
function and their place in it (`__pep_location.<function hash>.<n>`), in
a part of their own (`codegen.prepare`'s `locations_part`), so a line shift
recompiles that small part, not the code below the edit (a part that uses
one declares it outside its comdat, `keep_parts`: a declaration in a
comdat does not verify, and under `--lto=full` would claim the comdat
from the defining part). Just before a part's object is written
(`driver/parts.pep`, and the in-process LTO object), each definition not
in a comdat goes in a `nodeduplicate` comdat of its own on COFF and ELF,
as the writing machine's triple says (`section_each_definition`, private
ones made internal, as a COFF comdat's symbol must be named), clang's `-ffunction-sections
-fdata-sections`, so the link drops what nothing uses (pepper#155). And a file that
`_split` gave a part alone spreads its symbols over a power of two of
parts (`_spread`, about `_SPREAD_SIZE` each, at most `_MAX_SPREAD`) by its
symbol's hash, so an edit to one function recompiles one of them.
And code outside the file that declares an object struct reaches its
fields by offset, not by layout (`field_address`): it loads the field's
offset from `<struct>.offset.<field>`, an `i64` constant that the
declaring file's part defines and folds (`!invariant.load`, so a loop
hoists the load), and indexes the object by bytes. A field added to a
struct many files use leaves their IR, and so their parts, as they were.
A cold self-build with these loads took 475.0 / 454.2 s against 473.1 /
459.3 s without (4 cloud cores, -O2).
For an ELF target the entry part's static constructors first move from
`llvm.global_ctors` into an `.init_array` section (`place_constructors`,
`use_init_array`): a machine made through the C API emits `.ctors`, which
GNU ld folds into `.init_array` but lld, which cross-linking uses,
ignores. For WebAssembly, `main` is renamed `__main_void` for wasi-libc's
`_start` (`use_wasi_main`).

**Linking** (`driver/linker.pep`). `link` runs clang as the link driver, which
`find_link_driver` looks for in the `PEPPER_LLVM_PREFIX` (else
`LLVM_SYS_201_PREFIX`) LLVM, beside
the running compiler, on the PATH (`clang`, then `clang-<major>`), and in
the folders LLVM's packages install it in off the PATH (`llvm_install_dirs`);
an installed compiler has no prefix variable, and with no clang at all the
link fails naming what to install (`_missing_link_driver`). On a Linux
host it links with `ld.lld` when `find_lld` finds it (`-fuse-ld=lld
--ld-path=...`), much faster than BFD `ld`. For
another platform it adds `--target=<triple>`, LLVM's linker
(`-fuse-ld=lld`, plus `--ld-path=` when `find_lld` finds
`ld.lld`/`ld64.lld`, plain or as `ld.lld-<major>`, beside clang, in the
LLVM prefix or on the PATH; clang needs `-fuse-ld=lld` even then to give
ld64.lld the `-platform_version` it requires, and its MSVC driver ignores
`--ld-path` and runs the `lld-link` beside it or on the PATH), and the
target's system root (`--sysroot`, else `PEPPER_SYSROOT_<TRIPLE>`; passed as
`--sysroot` for ELF and Mach-O, and as lld-link's `/winsysroot` for
Windows), and a failed link ends with a note naming what is missing
(`cross_link_note`). For `wasm32-wasip1` the linker is `wasm-ld`, passed as
`-fuse-ld=<path>` (clang's WebAssembly driver ignores `--ld-path`), and the
root is a wasi-sdk (`WasiSdk.locate`: the SDK or its `share/wasi-sysroot`,
else `WASI_SDK_PATH`), which also gives `-resource-dir` for clang's wasm32
builtins; `wasi-emulated-getpid` is a default library there. iOS links
with `ld64.lld` against an iOS SDK, from `xcrun` on a Mac (`apple_sdk`)
when no root is given, passed as `-isysroot` too. Android links with the
NDK's own clang (`AndroidNdk.locate`: `--sysroot` naming the NDK or its
`sysroot`, else `ANDROID_NDK_HOME`, `ANDROID_NDK_ROOT` or the newest
`$ANDROID_HOME/ndk/<version>`), which brings its lld, compiler-rt and
libunwind. The default system libraries and the debug options
follow the target's OS. Every link drops the sections nothing uses:
`/OPT:REF` on Windows (not with `-g`, whose `/DEBUG` turns it off),
`--gc-sections` on ELF, `-dead_strip` on Apple targets.

**Optimization** (`codegen/target.pep`). `BuildOptions.opt_level` is `-O0` through
`-O3`: `-O<n>`, else `PEPPER_OPT_LEVEL`, else `-O0` (a bare `-O` is `-O2`,
and `-O main.pep` does not read the file as a level). Each part runs LLVM's
`default<On>` pipeline (nothing at `-O0`) before its object is written by
a machine whose codegen level matches. The level is in every cache key.
`--emit-llvm` prints the module unoptimized.

**`[Export]`** (`sema/exports.pep`). Sema's `exports` pass checks each
`[Export]`ed free function (its C symbol, from `[Export(name = ...)]` or the
declared name) and the struct handles it passes, rejecting a type C cannot
hold (`c_type`), and codegen defines its C entry point in the entry part.

**Libraries for C** (`--lib static|shared`, `driver/library.pep`). The
header of `state.exports` (`sema.header_declarations`, `sema.header`) goes
beside the output, naming for a static library the system libraries a
program linking it needs. `--lib shared` links with `-shared` and
`-soname` (`-install_name @rpath/...` on Apple); `--lib static` is an
archive `write_archive` writes itself: GNU (`/` index of big-endian
offsets), Darwin (`#1/` names, `__.SYMDEF`, 8-byte aligned members) or
COFF (both linker members), indexing the global definitions
`defined_symbols` reads from each ELF, Mach-O 64 or COFF (`/bigobj` too)
object, its members named `p<n>.o` since cached objects are all `0.o`.

**Link-time optimization** (`--lto=full|off`, off by default, since it
reruns over the whole program on every build; `driver/lto.pep`). Each part runs LLVM's `lto-pre-link<On>`
and is written, and cached, as bitcode (`0.bc`; the key gains `-lto`);
then the parts are linked into one module (`link_parts`, `LLVMLinkModules2`),
each part's link-once definitions made weak first, since the linker drops
a link-once one that nothing linked before it uses even when a later part
calls it (a compilation unit below defines it, the one above only
declares it); every
definition but `main` and the default-visible C exports is made internal
and leaves its comdat, and `lto<On>` runs over the whole program. Writing
the objects is then split across the CPUs (`lto.split`): the optimized
module is cut into one run of its definitions per logical CPU, its local
definitions made external and hidden, and `compile_parts` writes each
run's object in a `--compile-part` child without optimizing it again (the
plan's mode line says `optimized`); the constructors move to
`.init_array` in part 0. In process (`in_process`), one object is written.

**Target CPU** (`Cpu` in `codegen/generator.pep`). Code is generated for
clang's default CPU of the target triple (`Cpu.default_for`: `x86-64` tuned
for `generic`, `penryn` on Intel macOS, `apple-m1` on Apple arm64, `generic`
on other AArch64), never the build machine's CPU; codegen stamps
`target-cpu` and `target-features` on every defined function as clang does.
`-march`/`-mcpu`/`-mtune`/`-m<feature>` choose another, by clang's rules
(`Cpu.from_options`). The CPU is part of every cache key (`Cpu.key()`:
name, features, tune).

**`--verify-cache`** (or `PEPPER_CACHE_VERIFY`; `driver/verify.pep`) also
sets `BuildOptions.verify_cutoff`, then loads the program again and builds
it with an empty cache of its own in `<build>/verify.<pid>`, and compares
every object that build stores with the one the real cache holds under the
same translation unit (or compilation unit) and key: a stale hit, or a unit whose code changed
because sema skipped the cached units' bodies, differs.

**IR facts** (`codegen/globals.pep`). Generation ends by annotating the
module with what the language guarantees: `nounwind`
on every function and `uwtable` on every definition (plus
`"frame-pointer"="non-leaf"` on Apple targets, whose `backtrace` walks
frame pointers); `noreturn` and `cold`
on `NO_RETURN` (`_pep_panic`, `_pep_exit`, `abort`, `_Exit`); `noalias` on
the result of `ALLOCATORS` (`_pep_malloc`, `_pep_malloc_uninit`, `_pep_realloc`, `_pep_realloc_uninit`); and `!tbaa` on
object memory. The TBAA tree has two types under one root, `reference
counts` and `fields`: a load or store whose address is a field address of
a struct object (`getelementptr %S, ptr, 0, <i>`: `i < 2` is the head) or
a head count address (`head_count_ptr`, found by its name `HEAD_COUNT_NAME`)
gets one; everything else stays untagged and may alias anything. The
module comment says which facts are left out and why.

The link collects libraries in this order: `-l` flags, then `runtime/*.a`
(as `-L<dir> -l<name>`, after the `-L` directories), then the
`[Link("name")]` attributes of externs that survived platform filtering,
deduplicated (`link_inputs`). Search directories go in this order: `-L`,
then `[Link(path = "dir")]`, resolved against the declaring file's folder,
then `$PEPPER_LIBRARY_PATH`, then the runtime's folders. A cached compilation unit
keeps its `[Link]` arguments beside its objects, so a build that skips
sema links the same way. `linker.link` invokes **clang as the link
driver**, preferring `$PEPPER_LLVM_PREFIX/bin/clang` (else
`$LLVM_SYS_201_PREFIX`'s) so the linker matches the LLVM the compiler was
built against, and falling back to `clang` on PATH.
`default_system_libraries` adds `kernel32 user32 shell32` on Windows and `m` on Linux (float `**` calls `pow`). Link
warnings are forwarded. Failures include both stdout and stderr, because
MSVC's link.exe writes unresolved symbols to stdout.

### 4.3 Build cache (`incremental/cache.pep`, `incremental/interface.pep`, `codegen/partition.pep`, `link/translation_units.pep`)

The build cache (`--cache dir`, else `$PEPPER_CACHE_DIR`, else `.pep/cache`;
`--no-cache` skips it) keeps two kinds of results: each checked compilation unit's
record (§8.1), and the objects of each translation unit and compilation
unit. A build checks only
the compilation units an edit reaches, and compiles only the parts whose inputs
changed.

- **Translation units** (`link/translation_units.pep`):
  `translation_units` makes each source file a `TranslationUnit` of its
  own, so each file has its own object as a C translation unit does. In
  the rest of this section, "unit" means a translation unit.
  `unit_inputs` lists the files whose interfaces a unit's objects depend
  on: its imports, extensions and the prelude, transitively; an override
  file is an input by its own text only. Names depend only on paths.
- **Owners.** While generating, `Generator.own` records the file of every
  symbol a declaration defines (`owners`): methods, constructors,
  functions, globals, and each file's global initializer. A method belongs
  to `FunctionDef.owner` when set, else its own location's file, else its
  struct's: a trait's default method copied into a struct
  (`apply_extensions`) is owned by the file that declares the conformance,
  not the trait's file. Instantiations (a name with `<`), the
  `__copy`/`_pep_fix_weak`/`_pep_copy_trait` methods `copy` synthesizes on
  demand (a program has them only for the types it copies), the closures
  made in an instantiation's code, and code with no location have no owner.
- **Parts** (`codegen/partition.pep`). `prepare` splits the program's
  module into one or more parts per unit and one for the program's entry
  points: owned symbols become external and hidden in their unit's part,
  every other definition `linkonce_odr` in each part that uses it (private
  `unnamed_addr` constants stay private copies); `main`,
  `__pep_global_init`, the exports and `llvm.*` stay in the entry part;
  symbols are respelled with `symbol_name` (`link/names.pep`: `_P` and the
  name, `_` doubled and other bytes as `_xx`), except externs' C symbols:
  an extern whose C symbol a Pepper function is named after (`exit`) is
  declared as `__extern.exit` (`EXTERN_PREFIX`, set aside by
  `instantiate_function`) and takes its C symbol after the respelling
  (`restore_extern_names`, which `generate_ir` also runs for
  `--emit-llvm`, respelling only the function it clashes with);
  each part is measured.
  `keep_part` turns the other parts' definitions into declarations and runs
  `globaldce`. Codegen gives every mangled declaration internal linkage
  within its part: no other object can name it, and ELF linkers read the
  `@` of a global symbol as a version.
- **Keys** (`Keys`). A unit's key hashes (BLAKE3) the compiler's identity
  (its executable's path, size and modification time), the target, CPU,
  `-O` level, runtime checks and `-D` options, the unit's name and files,
  and each of its inputs' name, namespace and kind, with its text when the
  input is the unit's own or its unit reaches this one back through the
  units' inputs, else its **interface hash** (`interface.pep`, early
  cutoff): the file's tokens without comments or positions, each
  non-generic body sema settled a link summary for replaced by what other
  units see of it (`sema.function_facts`: its return type as resolved,
  inferred or not, and that summary, trait calls included, without the
  blame's position) and how many `=>` it holds, so a body edit that
  changes neither, or a comment, leaves other units' keys alone. Keys
  resolve bottom up (`reuse`): a unit's key is known once the interfaces of
  the files it reads from other units are, which a hit's record gives; a
  hit whose link summaries were recorded marks its files in
  `Module.cached_files`, so `strip_bodies` skips their bodies and codegen
  only declares them (`Generator.stripped`); never `main`'s, which the
  entry part, compiled every build, defines. A build that checks
  compilation units in workers (`_in_workers`) links only their objects,
  so it and its workers look nothing up here (`nothing_reused`): a body it
  skipped for a translation unit's object, which a whole-program build
  left in the cache, would be defined nowhere. After sema, `reuse_after_sema`
  hashes the other files' interfaces from their tokens and
  `summaries_to_record`, keys the remaining units, and a unit that hits
  then generates no objects. A function whose link summary calls through a
  trait (a dependent summary) has no facts: its body stands in the
  interface instead.
- **The store.** A unit's folder, `<cache>/v3/u/<unit>/<key>/`, holds
  `interfaces`, its files' interface hashes, `summaries`, its functions'
  link summaries (none when the build warned about the unit, so it is
  checked, and warns, again), and `parts`, the list of its parts' objects.
  Each part is cached on its own, `<cache>/v3/u/<unit>#<n>/<key>/0.o`,
  keyed like a C file's object (`Keys.part`): the part's files by their
  text, and every other file the unit reads by its interface hash. So when
  a body edit misses a unit, only the edited file's part is optimized and
  emitted again; the others are linked from the cache. Each folder is
  written to the build folder and moved into place as one. The same key
  gives the same objects, so they never change once there, and builds share
  the cache without locks or copies: a hit is linked where it is. Each
  unit, and each part, keeps its newest eight keys, and none stored or
  reused in the last ten minutes, since a build may be linking it; a unit
  hit marks its parts reused too, so a build storing newer keys of a part
  does not remove one another build is about to link. Pruning reads a
  key's time again just before it moves the folder aside, and moves it
  back when it was reused meanwhile; a build links the objects of a
  compilation unit it found in the cache through `Cache.reused_objects`,
  which looks again for about a second while the folder is away and fails
  the build rather than link without them (a link short of a unit's
  objects fails on undefined symbols, #24). A unit's folder
  spells the `/` of its name as `.` (`u/process.command#0/`), so each
  folder holds only its own keys: nested, the folder of unit `process`
  held the folders of units `process/...`, and its pruning removed them
  whole, objects a build was about to link among them.
- **Short paths.** The cache sits in the project's folder, and Windows
  tools fail on a path over 260 characters, so its paths stay short:
  one-letter folders, a unit's folder cut to 20 characters, the last 9 a
  hash of its whole name (`_unit_folder`), and a key's folder or
  file named by its first 20 hex digits (`_key_name`, 80 bits). No path
  adds more than 72 characters to the cache's folder
  (`keeps_every_path_in_the_cache_short`). The runtime's io also gives a
  Windows path of 248 units or more the `\\?\` prefix
  (`_io_win_path`), so a deeper project still builds.
- **Programs.** A program's key (`Keys.program`) hashes every file and what
  the link takes (output, `-l`, `-L`, the current folder); when
  `p/<hash of the output path>` records that key and the output's
  hash, the build stops before sema (`-T cache` says `up to date`). A build
  that warned records nothing, so the next one warns again.
- `-T time` prints each stage's time and `-T cache` each unit's hit or
  miss. `compiler/build_cache_test.pep` holds the cache to early cutoff,
  reuse and invalidation.

### 4.4 Debug info (`codegen/debug.pep`, `codegen/debug_types.pep`, `codegen/static_debug.pep`)

`-g` (`BuildOptions.debug`, `codegen.Build.debug_info`) is
`codegen/debug.pep`, `debug_types.pep` and `static_debug.pep`. The
generator creates a `DebugInfo` for the program's module: one compile unit
named for it, which every part split from it carries, with the module flags
`Debug Info Version` and `Dwarf Version` 4 (`CodeView` on Windows; DWARF
5's per-object `.debug_names`, which the C API cannot turn off, is
concatenated by GNU ld into one gdb rejects). The externs the `llvm`
package lacks are declared in `debug.pep`.

- **Subprograms.** Each function gets a `DISubprogram` named as written
  (file namespaces dropped: `Point@geo.length` is `Point.length`; a
  closure's `__call` is `closure at main.pep:14`, `closure_name`), with no
  linkage name (a debugger would show the linker spelling instead). A
  method with no location (the synthesized `__acquire`, a constructor) is
  artificial and placed at its struct.
- **Locations.** `enter_location`/`leave_location` stamp what
  `codegen_statement` and `codegen_var_def` emit with their node's `Loc`
  and restore the outer one afterwards, so compiler-inserted code
  (acquires, the releases after a statement) is attributed to the
  statement that caused it. Positioning the builder before an instruction
  takes that instruction's location, so the helpers that put a slot in the
  entry block restore the current one (`keep_location`).
- **Scopes and variables.** `codegen_scoped_block` (a nested block, an
  `if` or `else` arm, a loop body) pushes a `DILexicalBlock` at its first
  statement. `debug_declare` declares each parameter (numbered from 1,
  `this` artificial) and each local that is not hidden or `__`-named, with
  a debug record. Module-scope variables get a
  `DIGlobalVariableExpression` (`declare_global`, from `emit_globals`);
  `keep_parts` drops the `!dbg` of a global a part only declares, and the
  part that defines it describes it. A body `keep_parts` deletes takes its
  debug records with it (pepper-llvm's `delete_body`), so later copies of
  the module and their parts stay valid.
- **Types** (`debug_types.pep`, `Generator.debug_type`): numbers under
  their written names, raw pointers (`__ptr<T>` for `T*`), a plain enum as
  an enumeration, a tuple as a structure of `0`, `1`, ..., a trait value as
  `object` and `vtable`, a struct reference as a pointer to a structure
  with every field, the count head included, and a value struct (such as
  `Optional<T>`) as the structure itself. An enum's payload field
  `Case.value` is the member `Case__value`, which debugger expressions and
  natvis can name. A reference back to a struct or tuple still being built
  is a forward declaration, which debuggers resolve by name.
- **`finish`**, before the module is verified, gives every other defined
  function (thunks, initializers) an artificial subprogram, moves to line 0
  every call without a location in its own function's scope and clears
  other instructions' (codegen emits a thunk in the middle of a caller, and
  LLVM requires a location on every call in a function with a subprogram),
  adds `uwtable` to every definition so debuggers can unwind through it,
  and finalizes the builder.
- **`static` blocks** (`static_debug.pep`). Each pass of an unrolled
  compile-time loop, and the branch a compile-time `if` kept, starts with
  a static pass statement (§2.8), which emits nothing without `-g`. Under
  `-g -O0` it is a `nop` (sideeffect inline asm) at the loop's header: the
  passes' bodies share their lines, and a debugger steps until the line
  changes, so without it every pass ran in one step. Its compile-time
  variables get slots stored in the entry block (so they hold their values
  from the header on) and are declared in the pass's `DILexicalBlock`:
  numbers and `bool` as `long`, `double`, `bool`, a string as a `char*` to
  a constant, and a member, case, function or attribute as a structure of
  what `reflect` reads from it.
- **Locations in another file.** A `DILocation` takes its file from its
  scope, so `location` gives a location in another file than its scope's a
  lexical block of that scope in its file. `--debug-static=expanded`
  relies on it: `place` moves a `static` block's emitted code into the
  expanded copy (§2.8).
- **Optimization** keeps all of it: LLVM's inliner writes the inlined-at
  chains itself, and `tools/pep-doc/examples_test.pep` builds a sample of
  the examples at `-O2 -g`, so the verifier checks them.
- **Cache.** ` -g` joins every key, and `Keys.exact_positions` hashes every
  input by its text: a unit's code holds the line numbers of the generics
  it instantiates from other files, which interface hashes leave out. The
  build checks no compilation units (§8.1): a compilation unit's key
  leaves positions out too.
- **Linking.** `link_objects` passes `-g` to clang: on Windows a `.pdb`
  with the runtime's `pepper.natvis` and the program's enums' visualizers
  (`driver/natvis.pep`, `enum_natvis`, written to the build folder), and
  `dsymutil` on macOS.
- **Enums with payloads.** Their `__tag` is an enumeration of the cases,
  `<enum>.Case` (`_debug_tag`, from `DebugInfo.payload_enums`), so a
  debugger names the case. DWARF's variant parts would show only the
  active case's fields, but the LLVM C API cannot create them; the
  formatters below do it instead.
- **Formatters** for `String`, `Array` and `Optional` live in
  `runtime/debuggers/`. `embed_gdb_printers` puts `gdb_printers.py`
  (`driver.gdb_printers`, from the runtime) in the program module's
  `.debug_gdb_scripts` section on Linux, as an inline script (kind 4),
  kept by `llvm.used`; `--emit-llvm -g` carries it too. Each matches the
  struct and a reference to it, by name, and shows the head counts first
  as `[ref count]` and `[weak count]`; `Optional`, a value enum, has no
  head and shows its case from `__tag` and its value from `Value__value`.
  Any other enum with payloads, recognized by a `__tag` of enumeration type
  (an lldb recognizer function, lldb 16 and later), shows its case and the
  members of that case, `<Case>__<field>`, under their field names. natvis
  has no pattern for every enum, hence `enum_natvis`'s entry per enum.
- **Frame pointers.** `--frame-pointers` puts `"frame-pointer"="all"` on
  every definition, so profilers walk optimized stacks; `pep-profile`
  builds with it.

`compiler/debug_info_test.pep` checks the IR, a `-g` program's DWARF, gdb
breaking, printing and stepping (skipped without gdb), gdb printing an
enum through the printers, the enums' natvis entries, `-O2 -g`, the cache
keeping `-g` objects apart and `--debug-static` both ways.

### 4.5 Value structs (`sema/value_structs.pep`, codegen `values`)

A `[Value]` struct is a tuple with names and methods: no allocation, no
counts of its own, one reference held per reference field.

- **Sema.** `synthesize` gives it no count fields and no `__acquire`,
  `__release` or destructor bodies, and its constructor starts with
  `var this: V = Default(V)` instead of allocating; `zero_for` is
  `Default(V)`. `copies` gives it `_pep_copy_value` (`var __made = this;`
  then each counted field copied), and `check_shared_types` treats it as
  thread-safe when every field is (a fixpoint over value fields).
- **Representation.** Codegen names its LLVM struct `value.<Name>`
  (`types._VALUE_PREFIX`), which `types.is_object` excludes, so slots,
  parameters, returns and array strides keep it by value, as for a tuple.
  `instantiate_struct` records its field types in `values`, and
  `aggregate_elements` answers for tuples and values alike, so equality,
  hashing (`Address`), stores, moves and the field refcount paths share the
  tuple code. `__acquire`/`__release` are `emit_tuple_refcount_thunk`
  thunks over the fields, declared before any tuple thunk is emitted, since
  a tuple or another value can hold a value (`(int, Optional<Box>)`;
  `Generator.generate_items`). Like any instantiation they are
  `linkonce_odr`, kept only in the parts whose code calls them
  (`partition.prepare`, `keep_part`): the runtime's iterators are values,
  and a thunk for every instantiation in the program would make a unit's
  code depend on the rest of it.
- **`this`.** A method's `this` parameter is a pointer to the receiver's
  storage (`value_this`), so a change through it lands in the caller's
  value; a `MethodCall` passes the receiver's address (`value_address`), and
  an rvalue receiver is spilled to a slot and released after the call. In a
  constructor `this` is an ordinary tracked local: `return this` copies it
  and the scope releases it.
- **Fields.** A field of a place is a GEP into it; a field of an rvalue
  (`make().end`) is an `extractvalue`, with the rvalue on `deferred_temps`.
- **Boxing.** `ToTrait` from a value struct copies it into a box,
  `{u32 strong, u32 weak, V}` (`box_type`, `box_value`), acquiring a read
  and moving an owned rvalue; the result is a new object (`is_owned_rvalue`
  true, `is_lvalue_read` false). The vtable's entries are `box_member`
  thunks: `__acquire`/`__release` count the box (the last release calls
  `V.__release` on the value and frees the box), and each method calls
  `V`'s with `this` at the value inside the box. `covariant_adapter` boxes a
  value struct result the same way (`iterate()` returning `ArrayIterator`
  for `Iterator<T>`).
- **`for` in place.** A `for` whose source is a value iterator stored in a
  place (no `iterate()`) binds the hidden iterator to that place's address
  instead of a copy (`codegen_var_def_unlocated`), so `break` and a second
  loop resume it.
- **One layout per type.** `Generator.generate_items` records in
  `Types.canonical` each value struct's name with omitted type arguments
  filled from their defaults (`sema.fill_defaults`); `Types.ensure_value_opaque` keys the LLVM struct by
  it, so `Result<int>` and `Result<int, Error>` (separate specializations)
  store into each other.
- **Value enums.** `builder.reference_enum_def` keeps `[Value]` on the
  lowered struct, so a payload enum becomes a value struct: every case is a
  constructor call (no shared `StaticCase` object), the zero value is the
  first case, and `matches` emits no null assert for its `match` (neither
  a `_pep_assert` before the chain nor a `WithSubject.null_message`). Equality and
  hashing guard each reference field (`unless_null`), since unused case
  fields are null. `Optional` and `Result` are value enums.

### 4.7 SIMD vectors (`codegen/simd.pep`, `runtime/simd/`)

`simd.Vector<T, N>` and `simd.Mask<N>` are `[Value]` structs in the
runtime over one built-in type, so everything a value struct gets (inline
storage, copies, fields, arrays, `copy`, `[Shared]`) comes for free.

- **Number type arguments.** `Parser._type_arguments` in `parse/parser.pep` parses a
  run of decimal digits as a `TypeName` named by the digits, so `N` in
  `Vector<int, 4>` substitutes by name like any type parameter and the
  specialization is `Vector<int,4>`. Nothing evaluates it: only
  `__simd<T, N>` reads it (`types.simd_shape`), and
  `check_simd_shapes` (§3) validates it.
- **`__simd<T, N>`** (`type_name.SIMD`) is LLVM's
  `<N x T>`, a `bool` lane an `i1` (`codegen/types.pep` `scalar_type`).
  It is not a struct, its
  zero is `Default` (`synthesize.zero_for`); `check_shared_types` counts it thread-safe; debug
  info describes it as an array of lanes, or a bool vector as an unsigned
  integer of its bits (`debug_types._debug_vector`).
- **One node.** Every operation is `Expression.Simd { op: SimdOp, ty,
  args, loc }`, from a `__simd_<op><V>(args)` call (`convert_intrinsics`).
  `simd_op_result(op, ty)` types it (a comparison gives `__simd<bool, N>`, a
  reduction or `extract` the lane type, `to_bits` a `ulong`).
  `codegen_simd` lowers each op to LLVM vector instructions or the
  `llvm.vector.reduce.*`, `llvm.smin`/`umin`/`minnum`, `llvm.fshl` (rotates),
  `llvm.sqrt`/`floor`/`ceil` and `llvm.fptosi.sat` intrinsics
  (`simd_intrinsic`), picking signed, unsigned or float forms by the lane
  type (`simd_shape`). A splat is an insert plus a zero shuffle; a shuffle by
  a run-time index vector masks each index by `N - 1`, and LLVM turns a
  constant one into a `shufflevector`. The declarations in
  `runtime/builtins.pep` document each one.
- **The runtime** (`runtime/simd/module.pep`): the traits `Lane`,
  `IntegerLane` and `FloatLane` and their conformances on the number types,
  `Vector<T: Lane, N>` with the operations every lane type has, and two
  constrained extensions (`extend Vector<T: IntegerLane, N>` with checked
  `/ %`, bitwise operators, shifts and rotates; `extend Vector<T: FloatLane,
  N>` with IEEE `/ %` and rounding), so an integer vector's `square_root` is
  a withheld member (`no member named ...`, §3 9c′) rather than a codegen
  error. Comparison operators must return `bool`, so `==` and `!=` compare
  whole vectors and lane comparisons are methods returning `Mask<N>`. Checks
  (division, shifts, lane indexes, array spans, alignment) panic at the
  caller through `__caller_location()` parameters.
- **Inlining.** `Generator.inline_vector_methods`, run at the end of
  `generate` before `annotate_facts`, marks every method and constructor of
  a value struct holding a `__simd` field `alwaysinline` and, at `-O0`,
  runs LLVM's `always-inline` pass, so a vector expression has no calls even
  unoptimized. At `-O0` the inlined code still spills each lane vector
  through its struct, so the runtime's own hot paths call the
  `__simd_*` intrinsics directly: `_pep_ascii_end` in `internals.pep` (the
  ASCII run `_pep_utf8_scan` skips, sixteen bytes per step) does.

## 5. Reference counting: where the shared_ptr model is implemented

The model is defined in AGENTS.md ("Reference counting is
std::shared_ptr<T> passed by value"). This section maps each rule to the
code that implements it. Every rule is emitted in
`codegen/generator.pep` through `acquire_ref` and `release_ref`,
which stand for `T.__acquire` and `T.__release`. Both are synthesized by
`synthesize.apply_synthesized` and are null-safe.

For a struct with the standard counts (`StructDesc.inline_counts`, set
when `standard_release` holds: not a weak view or a function type's object,
whose bodies differ; and not a reference enum with immortal cases
(`immortal_cases`), whose release skips them), codegen inlines
the step instead of calling (`inline_count_step`): a null check and the
increment or decrement, atomic for a `[Shared]` struct (`count_step`, which
`CountStep` also uses). Only a release that reaches 0 makes a call, to
`T.__last_release`, a `cold`, `noinline` function that `last_release`
emits in each unit that needs it (no owner, so `linkonce_odr`): it calls
`__dtor`, drops the strong references' weak reference, and frees the object
when that reached 0, exactly as the zero branch of `__release`.

**Recursive structs** (#65; `codegen/chains.pep`). Released by nested
calls, a chain (a linked list, a deep document) would overflow the stack.
`find_chains` runs after every struct is laid out: Tarjan's algorithm over
the graph of what each struct's fields can hold (a struct, a trait's
conformers, a pointer's or tuple's elements, a function type's closures,
matched by their `__call`'s signature; never a weak reference). A struct
in a cycle is `recursive`. A field that holds structs of its own cycle,
the field's struct and theirs both with a `__release` codegen generates
(the standard one or a function type's), is a chain field (`ChainField`,
`chain_fields`) of one `ChainKind`: a struct reference; a trait value,
whose object is told apart by the vtable's type id; `Array`'s `_data`
buffer of `_size` elements; or a function type's object, a closure told
apart by its `__destroy` (the closure's `__dtor`), whose own chain fields
(its captures) are taken. A recursive struct with chain fields gets a
different `T.__last_release`: one chain field holding only its own type
(a list, through a struct, a trait value, or a closure capturing one;
`_list_field`) is a loop that takes the next link, destroys the current
one and moves on (`emit_list_last_release`); otherwise
`T.__chain_destroy` pushes each taken link with its `__chain_release` on a
list in the `__last_release` frame (32 entries on the stack, then
`_pep_release_list_grow`'s heap buffer) and the frame drains it. Taking a
link (`_chain_claim`) moves the field's reference out and nulls the field
when the struct's destructor only releases fields (`chain_moves`: no
`destruct` body sees the field); otherwise it takes an extra reference,
only when the field alone holds the link. An `Array` buffer's struct
elements always move, and `_size` drops to 0, so `Array`'s destructor
releases none of them; they are pushed last to first, so they are
destroyed in index order. A cycle with any other edge (`deep_recursive`:
through a tuple, a value struct such as `Optional`, or another container's
buffer) cannot be steered from the destructor, which is user code: its
last release is `_pep_release_last(object, T.__last_release)`
(`runtime/internals.pep`), which calls it at once unless this thread's
destructions already nest 16 KiB of stack below the outermost one; a
deeper one goes on a thread-local list the outermost drains. A task that
suspends inside a destruction keeps its floor across the switch
(`_async_suspend` calls `_pep_release_suspend`/`_pep_release_resume`).
A recursive struct's out-of-line `T.__release` (trait thunks, C handles)
comes from `emit_standard_release`, the inline step with the immortal
check when `StructDesc.immortal` (a reference enum's bare cases, a plain
function type's static objects), in place of `synthesize`'s body, so it
reaches the same last release; every other struct keeps that body, and a
struct no cycle runs through compiles exactly as before. The analysis sees
the whole program, so a unit cached before another unit made a type
recursive keeps its plain last release: still correct, only unbounded.
So taking
or dropping a reference costs no call even across units and at `-O0`, and
the cache keys need nothing new: the step depends only on the head layout
and `[Shared]`, which are part of the struct's interface. Tuples and trait
values still call their thunks, which step their elements or object the
same way.

**Folding pairs**. LLVM's own passes remove an acquire and a
release of the same object once both are inlined into one function and
nothing between them can read or change the count, but only if they can
tell the release does not reach 0. Codegen tells them: a copy from a slot
that owns a reference (`acquire_copy`, when `reads_owning_slot`: a local,
parameter, global, field or pointer element, never `this`) loads the count
with `!range [1, 2^31)`, since the slot's own reference keeps it at 1 or
more. GVN and InstCombine then fold the copy's step and its release's test
for 0, and dead-store elimination drops the count stores. Nothing changes
at `-O0`, observable counts stay exact wherever the program reads them
(a `__refcount` read is a load of the count, so the steps around it
stay), and atomic counts are never folded, so no fence is lost. Copies the
model cannot prove live (a constructor's result, `this`, a parameter at
entry, whose caller may pass its only reference) keep both steps.

| shared_ptr construct | Where |
| --- | --- |
| `make_shared` | The constructor's `return this` is an lvalue read of `this`, so the return site acquires (`Statement.Return` → `is_lvalue_read` → `acquire_ref`). The constructor's `this` is a tracked local that owns the object's first reference (`synthesize.finish` starts `__refcount` at 1), so passing `this` on from the constructor copies it and the copy's release cannot destroy the object under construction. Its scope exit releases that reference after the return acquires the caller's, so a constructor result arrives with one reference. |
| `var x = expr` | `codegen_var_def_unlocated`: acquire when `expr` is an lvalue read. An owned rvalue (a call result, see `is_owned_rvalue`) moves in. The slot is registered with `track_scope_local`. |
| `x = y`, field and element stores | `store_refcount_ops`: if the new pointer equals the old one (self-assignment), do nothing; otherwise acquire the new value, store it, then release the old, so a destructor the release runs that reads the slot finds the new value (as `shared_ptr.operator=`). Fields use `field_refcount_ops` and indexed slots use `index_refcount_ops`. |
| By-value parameter | `codegen_function_unlocated`: acquire each struct parameter on entry (`this` excepted) and track it in the function scope. A `[Move]` parameter is not acquired: the caller hands its reference over (`pass_argument`: an owned temporary is not released after the call, an lvalue is acquired for it). |
| `std::construct_at` | `__construct_at(p[i], v)` (`Expression.ConstructAt`): acquire `v` and store it into a raw buffer element that holds no reference, with no load, compare or release of the old occupant (`construct_refcount_ops`). The runtime uses it where a slot is known empty: `Array.append` and `insert`, and `HashMap`'s insert and rehash. A non-empty slot leaks its occupant. |
| `move(x)` | `codegen_move`: load the reference from the place and store null there, with no count step; the result is an owned rvalue (`is_owned_rvalue`). |
| Scope exit | `scopes: Vec<Vec<(name, type, slot)>>`. `release_scope` runs at block fall-through, `release_all_scopes` at `return`, and `codegen_loop_break` releases the scopes a `break` or `continue` leaves. |
| `return` | An lvalue read is acquired before `release_all_scopes`. A call result moves. |
| Discarded temporary | `Statement.Expression` releases `owned_temp_type(expr)`. Arguments that are owned rvalues are released after the call (`owned_arg_temps` in `codegen_call`). The receiver of `f().x` or `f()[i]` goes on `deferred_temps` and is released at the end of the full expression by `flush_deferred_temps`. Ternary arms use `codegen_expr_in_arm`. |
| Tuples | Same rules, same call sites: `Tuple.__acquire`/`Tuple.__release` step each reference element (§4.6). A destructuring binding moves its element out of the hidden tuple. |
| Value structs | Same rules, same call sites, as for tuples: `V.__acquire`/`V.__release` step each reference field (§4.5). A method's `this` is the receiver's address, so it does no count work; a constructor's `this` is a local released at scope exit. |
| Trait values | Same rules, same call sites: `Trait.__acquire`/`Trait.__release` are thunks into the vtable (§4.2), so the concrete type's `__release`, and at zero its `__dtor`, run. `ToTrait` does no refcount work of its own: converting an lvalue read acquires as the read would, and an owned rvalue moves. |
| Destruction | At zero, `__release` calls `__dtor`, which runs the user's `destruct` body, then the field releases added by `release_field_refs`. `__release` then drops the strong references' weak reference and frees the object if `__weakcount` reached 0. |
| Closures | `MakeClosure` is an owned rvalue like the constructor call it wraps (`make_shared`): each captured value is a constructor argument, acquired into its field. The value's type is the function type, so every other row applies through `__function<…>.__acquire`/`__release`. At zero, the function type's `__dtor` calls `__destroy`, the closure's `__dtor`, whose `release_field_refs` releases the captures. |
| `std::weak_ptr<T>` | `__weak<T>` (`sema/function_types.pep`): a synthesized struct that is a view of `T`'s two head fields, so the rows above apply to weak slots through its `__acquire` (`++__weakcount`) and `__release` (`--__weakcount`, free at 0), atomic when `T` is `[Shared]`. `__weak_from<T>`, `__weak_upgrade<T>` and `__weak_expired<T>` are `Expression.Weak` nodes (`codegen_weak`); the first two are owned rvalues. `__weak_upgrade` is a compare-and-swap loop that increments the strong count only while it is non-zero (`weak_ptr.lock`). `check_function_types` rejects implicit `T` ↔ `__weak<T>` conversions. |
| Threads | Counts are plain by default. A `[Shared]` struct and every `shared` function type (`shared (T) => R`) step them atomically (`CountStep`, codegen's `atomic_counts`), like `std::shared_ptr`'s control block; plain function types count plainly. `sema/shared_type_checks.pep` keeps non-thread-safe values (plain function values included) out of shared structs and globals, and `sema/shared_functions.pep` lets a closure become `shared` only when its captures are thread-safe, and wraps a `shared` value used as a plain one in a plain adapter that holds it (a struct holding a `shared_ptr` field). |
| By-value parameter the caller copies | For a parameter listed in `Module.caller_copies` (a `String` parameter the function neither keeps nor changes, `static_strings`), the caller constructs and destroys the copy around the call, as the Itanium C++ ABI does: `copy_argument` (from `pass_argument` and `default_temp`) acquires an lvalue argument before the call and puts it on `owned_arg_temps`, released after; an owned temporary is the copy; a shared string literal (`StaticString`) needs none. The callee neither acquires nor tracks the parameter (`codegen_function_unlocated`, `copied_params`). Passing such a parameter on to another one copies it with `guarded_step`, which leaves a count at or above `STATIC_REFCOUNT` alone, since it may be a shared literal (`guarded_temps` releases it the same way). |

**Empty Arrays are null**. `Array<T>` is `[__Lazy]`
(`Generator.is_lazy`, `StructDesc.lazy`): the model above is unchanged,
but an empty Array has no object until a second name for it exists or it is
written. Codegen implements this in four places:
- `codegen_call` makes a zero-argument constructor call of a lazy struct
  null.
- `codegen_expr` passes a read of a lazy place (a variable, field or buffer
  slot, `lazy_place`) to `materialize`. That function loads the place and,
  when it is null, constructs the object (`fill_lazy`, the real constructor
  with its defaults) and stores it there first.
- The reads that leave the place null set `keep_lazy` for the very next
  `codegen_expr`:
  - the receiver of a `[__Reads]` method (`reads_methods`) or of a count step;
  - the object of a field read;
  - an argument to a `[__Reads]` parameter (`reads_params`: `_Copies.copy<T>`
    and `_copy_object<T>`, so a deep copy of a null Array is null);
  - an operand of a test against `__null`;
  - a returned local, which moves out.
- A field read through a lazy object that may be null reads it through
  `lazy_base`, a `select` of the object or a zeroed private constant of its
  layout (`Array<int>.__empty`). Only `this` in a method that is not
  `[__Reads]` (`this_may_be_null`) skips the select.

A method that is not `[__Reads]`, called on a temporary that is null, gets
an object for the call alone. A tuple (`codegen_tuple`) or a `[Value]`
struct or enum (a field store in `codegen_assignment`) never holds a null
it was given: its copies are bitwise, so a null temporary stored in one is
filled first, and a place read into one materializes rather than moves.
Sharing allocates first, so every name sees
one object. The divergence is `iterate`, which is `[__Reads]` and copies
`this`: an iterator over an empty Array holds null and does not see later
appends. `sema/lazy.pep` keeps a `[__Reads]` method from writing a
field of `this` or calling a method of `this` that is not `[__Reads]`.
`pepc` mirrors all of this (`tools/compiler/codegen/lazy.pep` and the same
call sites, §8).

Debugging aids: set `PEP_CHECK_SYNC` to make every `MutexGuard.exit`
check, before it unlocks, that nothing outside the locked value refers into
it. `exit` calls the `__census<T>(slot, waiting)` intrinsic, which
`copies.synthesize_copies` lowers to `_pep_check_sync<T>` (`copy.pep`) for
a `T` that is not thread-safe and can be copied, and to nothing otherwise.
`_pep_check_sync` copies the value through its own `_Copies` context (installed
like an outermost `copy`'s, and the previous one restored after) whose `_edges`
counts, per original object, the references `_copy_object` passes through
(the slot's included), then compares each object's strong count with its
tally and panics on a difference. Each holder asleep in `Condition.wait`
keeps its `with` binding, one more reference to the root: the Mutex counts
them (`_waiting`, which `wait` and `wait_for` step around the sleep) and the
census adds them to the root's tally. The flag `_PEP_CHECK_SYNC_ON` is read
once, in `internals.pep` (module constants initialize file by file, and
that file's allocation counter must exist before any `String` is built).

`_pep_malloc` serves blocks up to `_pep_small_limit` bytes (128, or
`PEPPER_SMALL_BLOCK_LIMIT` read at start; 0 turns it off; at most 4096)
from the small block allocator in `internals.pep`: 28 size classes,
64 KiB spans cut from one reserved 4 GiB region (so `_pep_free` tells a
small block by a range check, and a span's 96-byte header names its class),
and per-span free lists: each span has an owner, a thread's cache
(`_pep_small_cache`, a `[ThreadLocal]` pointer, so reaching it is one
thread-relative load; it has no exit hook), its own free list and a never-used end. A
thread allocates a class's blocks from its current span; a free on the
owner's thread pushes onto the span's list, and a free on any other thread
onto the span's atomic remote list, which the owner takes over when the
span's own list runs dry. `_pep_small_alloc` and `_pep_small_free` keep only
the common case (pop or bump the current span; push onto an owned span's
list); everything else is in `[Cold]` `_pep_small_alloc_slow` and
`_pep_small_free_slow`, so both stay small enough to inline into callers
such as `__release`. Per class the cache keeps its current span, a
stack of spans with free blocks (a full span joins it when its owner frees
into it) and a ring of full spans. A full span's remote list carries
`_SMALL_NOTIFY`: the first remote free that clears it pushes the span onto
its owner's atomic stack of spans freed into (mimalloc's delayed free; a
`QUEUED` word keeps it there once), which the owner takes before a span
from the class's pool of spans exited threads left (spin lock) or a new
span. Caches are never freed, only reused by new threads
(`_SMALL_SPARE_CACHES`), so a remote freer can always reach the owner. A
thread that `async.Thread.spawn` started calls `_pep_small_thread_exit`
when its body ends, which puts its spans in their pools, ownerless, and
folds its live count into
`_SMALL_RETIRED`; other threads keep their caches. Recycled blocks are zeroed when handed
out, except by `_pep_malloc_uninit` and `_pep_realloc_uninit`, which String, StringBuilder and the growth of a plain-value Array use for bytes they write before reading. The allocator runs before any other global exists, so it uses raw
memory only, and its functions are `[Unsafe("overflow")]`.

`_pep_live_allocs()` counts live
allocations: the sum of 61 atomic counters on separate cache lines, one
picked per thread by its id, so threads allocating concurrently do not
contend for one cache line, plus each small block cache's own count;
every test reads it before and after it runs (the `TestRunner`'s leak
check), and each test runs in a process of its own, so tests run in
parallel with no lock.

## 6. Diagnostics (`diagnostic/diagnostic.pep`)

The standard is in AGENTS.md ("Compiler errors are clang-style
diagnostics"). The mechanics:

- `Loc { file, span }` (`sema/loc.pep`) indexes the program's files and has
  a `Loc.none()` value for nodes the compiler synthesized.
- `Diagnostic` (`diagnostic/diagnostic.pep`) has a severity, a message, a
  location, notes (each a diagnostic of its own) and suggested fixes.
- Rendering spells mangled private names as written
  (`diagnostic.demangle`), so messages may name model
  types and functions directly, **in single quotes**: only quoted names
  are demangled, so a path or string holding an `@` is left alone.
- Rendering goes through `render_all(diagnostics, sources)`, the sources a
  `SourceText` per file (`program.sources()`, in load order, so file `i`
  is `program.files[i]`).
- Each layer reports errors its own way: the parser through
  `_expect`/`_fail`, the builder by returning the `Diagnostic` as a
  `Built<T>`'s error, passes through `state.report`, codegen through an
  `Err` plus `locate`, and linking through `ModuleError` and the
  visibility check's errors, which become diagnostics.
- An error a pass reports inside a specialization's body (the runtime's
  `to_string<T>` made for the user's `expect_equal(mode, ...)`) gets a
  note per `Module.spec_requests` link back to the non-generic code that
  asked for it: the pass runner passes each error through
  `instantiation.with_instantiation`, which finds the specialization
  whose body holds the error's location (narrowed by the types the message
  quotes, since instances share their base's locations) and adds
  `with_requests`' notes.
- Warnings exist only as deprecations, and never stop a compile. Every
  one has the code `deprecated`, and may carry a `Fix` whose `Edit`s replace
  source spans; the renderer prints the fix under the caret, and the
  language server offers it as a quick fix. There are two kinds:
  - Deprecated syntax: the parser records a `SyntaxWarning` in
    `ast.Module.warnings`, which `Program.warnings` turns into
    `Diagnostic.deprecated(what, instead, loc, fix)` (always with a fix). The book lists these in
    `docs/src/language/compiler-errors.md`.
  - Uses of a declaration marked `[Deprecated("message", "replacement")]`
    (`link/deprecation.pep`):
    `Diagnostic.deprecated_declaration(name, message, loc)` plus a note at
    the declaration and, with a replacement, a fix renaming the use. The
    builder validates the attribute (`deprecation_of`; errors at the
    attribute or argument). `deprecation.check_uses` walks the linked ASTs
    (a `ScopeWalk`) for top-level names, as values and types and in import
    lists; `check_deprecated_members` finds member uses on the
    model, which knows receiver types.
- How warnings flow: `Program.warnings()` is the parser's warnings plus
  `check_uses`; the passes collect the member warnings in `state.notes`,
  which the driver adds to them, and it prints
  them sorted by location (`report_warnings`) after the passes, whether or
  not they failed. The language server publishes the ones located in the
  open document.

Several workers (`workers.pep`): `run_with` makes a `[Shared]` `_Runtime` and one `_Worker` per `RuntimeOptions.workers` (the calling thread plus `Thread`s); each worker stores an `_Inbox` (a `Channel<ulong>` of `id * 4 + kind` messages, kind a `_Message` and its driver's `_Doorbell`: eventfd (epoll, io_uring), `EVFILT_USER`, `PostQueuedCompletionStatus`, or a self-pipe / loopback UDP socket rung from a second socket for poll) in the runtime, plus a `_pinned` queue for `spawn_on_each_worker`'s tasks, which a worker takes before the shared queue (and hands to the shared queue if one arrives after it stopped). `spawn<T>` is a free function so that only its callers instantiate `_TaskResult<T>`, whose `__ptr<T>` field makes `check_shared_types` require a thread-safe `T` (the error follows the specialization out to the user's call, `user_use_site`); it queues a `_SharedTask` on the runtime's shared queue and gives the caller a stand-in `_TaskCore` (`_proxy`) that finishes when the running worker sends `_Message.Complete`. Idle workers take unstarted tasks from the queue; started tasks never move. Cancelling a spawned task sets its atomic flag and sends `_Message.Cancel` to the worker running it. A worker about to block sets `_sleeping`, clears `_notified` and re-checks its inbox and the queue; senders ring the doorbell unless `_notified` is set. When the first task returns the runtime stops: every worker cancels its tasks, runs until none are left, and waits for the others (`_leave`) before closing its driver, so no doorbell rings a closed handle. Stream socket receives and sends in a task try the same path first (`io._io_task_socket_transfer`, from `_io_sys_socket_receive`/`_send` on Linux): the worker's `_socket_transfer` asks the driver's `_start_socket` (io_uring: `IORING_OP_RECV`/`SEND`, one per socket and direction, submitted with the next poll's `io_uring_enter`; every other driver declines, and the call falls back to readiness), and parks; a cancel or deadline queues `IORING_OP_ASYNC_CANCEL` and still waits for the completion, which may carry the bytes moved first, and `_forget` cancels a closing socket's transfers (`_IO_TRANSFER_CLOSED`). `_io_socket_read` and `_io_stream_write` pin their array meanwhile. `run_blocking` queues its body on the runtime's `_blocking` channel and parks on a stand-in; `_Runtime._block` claims an idle pool thread or tells the worker to start one (up to `RuntimeOptions.blocking_threads`, joined by that worker when the runtime ends), and the pool thread (`_async_blocking_main`) reports `_Message.Complete` like a worker. |

- **Loading.** Every top-level `runtime/*.pep` is a prelude file. Its
  `export`s are visible in every program without an import. `runtime/io` is
  found as a module because the runtime directory is on the search path.
- **Naming convention for internals.** Names prefixed `_pep_` (core),
  `_io_` (io module), `_async_` (async module), `_process_` (process module), `_regex_` (regex module), `_os_` (os module), `_cli_` (cli module), `_compress_` (compress module), `_tar_` (archive module) and `_digest_` (digest module) are internals. They are `export`ed so other runtime
  files can use them. They are exempt from the documentation standard, and
  a module does not re-export them (`io/module.pep` re-exports only the
  public types).
- **Lowered by name.** Interpolated strings and `String.format` call
  `_pep_interpolate` and `_pep_format*`. A name the compiler synthesizes must be exported:
  linking mangles private names per file. Every constructor calls `_pep_malloc`, and `__release`
  calls `_pep_free` once the weak count reaches 0. Compiler-generated checks (null function and trait
  values) call `_pep_assert`, which takes a raw `char*` message and location.
  Codegen calls these by name after visibility has run, so they
  need not be exported.
- **Intrinsics available to runtime code**: `__ptr<T>` (a raw pointer, the
  only pointer spelling allowed outside `extern`), `__null`, `sizeof(T)`,
  `__default<T>()`, `__is_pod<T>()`, `__refcount<T>(x)`, `__address<T>(x)`,
  `__atomic_load/store/cmpxchg/fetch_{add,sub,and,or,xor}<T>(…)`,
  `__weak<T>` with `__weak_from/upgrade/expired<T>(…)`, `__simd<T, N>`
  with the `__simd_<op><V>(…)` operations (§4.7), and
  `__function_pointer(f)` (a C-callable `__ptr<void>` to a free function or
  a static method of the enclosing struct; also documented for users in the
  book's C chapter).
- **Documentation.** The standard is in AGENTS.md (the library documentation
  section): `##` doc comments with the tags listed above.
  `pep-doc check` enforces it (`tools/pep-doc/checks.pep`). The
  reference pages in `docs/src/reference/` and the reference part of
  `docs/src/SUMMARY.md` are **generated** by `pep-doc reference`. CI fails
  if they are stale (`pep-doc check`). A page's title and place in the
  table of contents come from `pages()` in `tools/pep-doc/reference.pep`,
  which must name every runtime file with public declarations; `check`
  also lints the chapters (`tools/pep-doc/book.pep`). A compiler built-in
  is documented by a `[__BuiltIn]` declaration in the runtime (see
  section 2.5), never by a hand-written page. See
  `docs/src/contributing/docs.md` for the book.

## 8. Language server, tools, and the compiler's modules

**`tools/pep-lsp`** is the language server, `pep-lsp`; releases
(`scripts/release-build.sh`) ship it, and the VS Code extension
(pep-lang/vscode-pepper) runs the toolchain's. It's built
on the `lsp` package (pep-lang/pepper-lsp), a tower-lsp style
framework: `serve_stdio` runs the `LanguageServer` methods on one thread,
in message order. It checks code with the Pepper front end
(`compiler.parse`, `compiler.link`, `compiler.sema`), checking a program
one compilation unit at a time as `pepc` does (`compiler.incremental`, §8.1). So far it does
diagnostics, the document outline, hover, go to definition, completion,
inlay hints, quick fixes and dimmed code for other platforms. A request
slower than 200 ms is logged (`_answered`, "hover took 312 ms"):

- `analysis.pep`: one analysis thread (`analyze_documents`) takes each
  document's newest text once edits settle (250 ms). It loads the
  program rooted at the document, with the editor's text in
  `Setup.sources`, and publishes the diagnostics through the `[Shared]`
  `lsp.Client`. A document edited again while it was analyzed is analyzed
  once more instead of publishing stale diagnostics. The diagnostics come
  from the parse errors (all of them, `parse.parse_recovering`, a missing
  `}` with its `{` as related information), `Program.warnings`, linking errors (unresolved
  imports as warnings; one in another file at the document's start with
  that file's name), `Program.check_diagnostics`, then the first error
  checking finds. The program loads with `Setup.defer_bodies`, and
  `incremental.check_compilation_units` checks it as a build does (§8.1), keyed on
  `Keys(program, units, "pep-lsp")` with the server's own compiler
  identity, in the build cache of the document's project
  (`link.find_project`, else its folder): every compilation unit but the document's
  own loads from its record when its key is there, without reading its
  bodies, so an edit checks the document's compilation unit, and a change on disk
  the compilation units it reaches. The records of a first analysis stay for the
  next session. A cache without the runtime's compilation unit (`_cold`) lacks
  them all: the program is then checked whole, as one compilation unit
  (`check_whole`, `check_compilation_unit` on an empty module), since on an
  empty cache one pass is sooner than ~30 compilation units in sequence, each
  paying the passes' walks over everything it reads; meanwhile a
  `pep-lsp --fill-cache <dir>` child (`fill_cache`) checks the compilation
  units below the document's in workers (`Filling`). `check_whole` keeps the
  whole program's record in the cache, as the compilation unit
  `pep-lsp-whole` keyed by `_whole_inputs` (the runtime unit's key, the
  document, its OS and build options); while the child runs, an analysis
  checks the edit again on that record (`recheck_whole`,
  `incremental.recheck_compilation_unit` with `report`, so the edit's error
  or warnings show rather than give up: the record warned of nothing, so
  they are all the edit's) and waits for the child only when the record
  does not fit the edit. Otherwise the compilation units below the
  document's that the cache lacks are
  checked first in `pep-lsp --compilation-unit-worker <dir>` children
  (`incremental.check_in_workers`, `serve_compilation_units`, `check_for_worker`),
  which load the program `<dir>/program` names, with the document's text
  from `<dir>/root.text`; they only check. The document's own compilation unit is
  checked last, always (`check_compilation_units`' `stop`), and the compilation units after it
  not at all. It then hands a `copy` of the `Analysis` (the text
  it analyzed, the linked `Program`, and the checked `sema.Module` and
  `PassState` when the passes passed) to the server thread through a
  channel and `Client.wake`s it; `woken` keeps the last one per document.
- `symbols.pep`: the outline of declarations and struct members.
- `navigate.pep`: hover and definition. A `Context` is the current text's parse, plus the last
  analysis's program and model when that analysis is of the same text;
  without them, only what the parse says answers (locals, parameters,
  the file's own declarations). `scope.pep` finds names in the syntax
  tree (scopes, the expression or type under the cursor); `imports.pep`
  follows names through imports with `link.FileScope`'s `imported` and
  `named`; `compiler.sema`'s `member_at` and `local_type`
  (`sema/member_lookup.pep`) type a member access's owner and an inferred
  local in the checked model. Hover heads spell a type as written:
  linking's `@namespace` suffixes are stripped. Before the syntax,
  `navigate.pep` asks the model for what only it knows: a call's chosen
  overload (`Module.call_targets`, with "(+N overloads)"), a use of a
  `[__BuiltIn]` declaration (`reflect.name`, `__null`, `sizeof`), an
  enum case's value, and whether a function returns a fresh value
  (`sema.returns_fresh`, from the confinement summaries).
- `infer.pep`: the syntax's own typer (`Typer`), for what the model leaves untyped: generic bodies nothing
  instantiates (sema checks only specializations), the names a `match`
  arm or an `is` test binds, and the members such code reaches. A name's
  type comes from its declaration, else the model's inferred type, else
  its initializer; a member is found in every program file's
  declarations, the owner's type arguments bound to the declaration's
  parameters. `SyntaxWalk` visits a module with an explicit stack, and
  typing gives up past 48 steps. `written.pep` finds what the tree holds
  in no node: tuple labels, a type argument written in a member's name
  (`copy<T>`), and the names of `String.format(...)`, which the parser
  lowers.
- `edits.pep`: requests never wait for sema. The server keeps each
  document's last analysis and the newest one whose sema passed. When the
  text changed since that one, an `EditMap` (the one region where the two
  texts differ, from whole lines) carries the offset to the older text: a
  name on a line the edit left alone is answered from the passed analysis
  at once (a hover notes it may be out of date, and a definition in the
  document moves with the edit), and one inside it from the current
  text's parse.
- `completion.pep`: keywords, the names in scope (`scope_locals`, the
  members of the struct around, the file's declarations and the other
  files of its module), the cases and static methods after `Enum.`, and
  in an argument list the parameter names (and `[Alias]` names, from
  `sema.other_names`) of the functions the call may call. A method's
  receiver is typed from its written type, the passed analysis's
  `sema.local_type`, or a constructor call initializing it. Text that
  does not parse while a name is typed (`Color.`, `f(a, `) is parsed with
  a placeholder `_` at the cursor.
- `hints.pep`: inlay hints from the passed analysis's model:
  `Module.conversions` (an `[Implicit]` constructor's `To(` and `)`
  around the value, also noted in its hover) and `Module.argument_names`
  (`width:` before a literal argument). After an edit, `EditMap`'s
  `line_range_to_current` keeps only hints on lines the edit left alone.
  `initializationOptions.inlayHints` turns each kind off, and a passed
  analysis sends `workspace/inlayHint/refresh` when the client supports
  it.
- `actions.pep`: quick fixes. Each compiler diagnostic in the document
  that carries `fixes` becomes one code action per fix, kept with the
  analysis that found it (`Analysis.actions`) and answered while the text
  is that analysis's; otherwise only the current text's syntax answers (a
  missing `;`, deprecated syntax such as `new`). `missing_arms` adds the
  cases a `match` leaves out. `lsp.CodeAction` is built with its kind
  passed rather than defaulted (the Rust compiler that built the server

  `main.pep` only starts it.

- `smoke-test.mjs` exercises raw JSON-RPC against a built server

**`tools/syntax` and `tools/pep-fmt`** are Pepper programs, built with
`pepper build tools/pep-fmt/main.pep`. They are the project's largest
dogfooding of the language.

- `tools/syntax` (a module: `module.pep` is two `export * from` lines) is
  the lexer (`lexer.pep`, `token.pep`; an interpolated string `$"..."` is
  one `TokenKind.String` token) that `compiler.parse` reads. Each comment
  hangs off the token next to it (a comment on the same line after a token
  is its `trailing_comment`, any other is an entry in `leading_comments` of
  the next token). A `Token` is a `[Value]` struct that points into the
  source (`offset`, `size`): `text(source)` copies its text out, and `is`,
  `is_word` and `spells` compare in place, so the lexer allocates nothing
  for a token without comments, and the parser's keyword and operator
  checks (`is_reserved_word`, `_operator_size`) allocate nothing either.
  `>` is always its own token; the parser joins adjacent ones into `>>`,
  `>=` and `>>=` where the compiler's grammar would read those operators.
- `tools/pep-fmt` lays out the tree `parse.parse_written(source, checked =
  false)` returns (only a lexical or syntax error stops it, as in the
  compiler; errors in nodes that parse, such as a literal out of range, and
  `checks.pep` are left to the compiler, and so is the work only they need:
  the parser's `_layout_only` leaves string literals undecoded and
  interpolated strings and formats without parts, keeping their spans). `format.pep`'s `Formatter` walks
  the tree in source order like `tokens_test.pep`'s `TokenWalk` and takes
  each token of `Module.tokens` where the grammar puts it (`_take`,
  `_type`, `_span`), so every token prints as written with its comments;
  `_leading` and `_token_doc` remove a comment from the table (the
  formatter takes it over; whether a range of tokens was parsed with a
  comment is a lookup in `_commented_before`) once it is laid out. A body's or the module's items are
  `Item`s (`_items`: the tree's members, statements or declarations in
  source order, plus each `;` that ends nothing), which import sorting
  (`_sort_imports`), `# format: off` regions (`_format_off`, copied from
  the source by the comments' offsets) and blank-line rules work on. Where
  the tree keeps less than the source (a second destructor or accessor, a
  property's value before its accessors: code the compiler rejects),
  `Formatter.error` says so and the file is reported, not changed. The
  layout is a Wadler-style document (`doc.pep`: text, soft and hard lines,
  indentation, groups, and a `DocKind.Choice` of layouts tried in order)
  rendered at 120 columns; a token without comments is a bare text, which
  `Doc.add` turns into a sequence if something is added to it; `format.pep` holds the style; a long binary
  expression breaks before each operator, and `_member_chain` breaks a
  chain of three or more calls before each `.`. Trailing comments are
  emitted as line suffixes marked with byte 0x01, which
  `align_trailing_comments` aligns and removes. `tools/pep-fmt/fmt_bench.pep`
  times pep-fmt's phases over `runtime` and `tools` (lex, `parse_written`,
  the layout, `render`, all of `format_source`), each the best of several
  passes and one phase further than the one before.
- `tools/pep-fmt/repository_test.pep` formats every `.pep` file in the
  repository: each must format, be idempotent, and keep its syntax tree;
  `runtime/` and `tools/` must already be formatted. Its formatting cases
  (input and expected output) are in `tools/pep-fmt/format_test.pep`, and
  the program's command line in `cli_test.pep`, all run by
  `scripts/pepper-tests.sh` (`pepper test` in `tools/`).

**The compiler's modules in detail.** Sections 2 to 4 follow a program

- Comments live on tokens, not on nodes. `parse.parse_written` keeps
  every token in `Module.tokens` (`ast.SourceTokens`: the source and the
  `syntax.Token`s, `>`s joined as the parser joined them, ending with
  `End`), each with the comments and line breaks the lexer attached to
  it: a comment after a token on its line is that token's trailing
  comment, any other one a leading comment of the token after it. A
  node's spans locate its tokens, so `leading(span)`, `trailing(span)` and
  `blank_before(span)` read a node's comments; a comment on a token that
  starts or ends no node (a `,`, a `)`, a `}`) is inside the innermost
  node around it. `parse.parse` keeps no tokens and no parentheses, at no
  cost: it lexes without comment text (`lex(source, keep_comments =
  false)`), and only `parse_written` records the `>`s the parser joins
  (`_take_operator`), to build the table at the end
  (`_written_tokens`).

  the skeleton of pep-fmt's `Formatter`), and requires every token taken

### 8.1 pepc's checked compilation units

(`incremental/compilation_units.pep`, `incremental/check.pep`'s
`check_compilation_units`, `incremental/workers.pep`'s `check_in_workers` and
`serve_compilation_units`, `driver/build.pep`'s `_check_in_workers` and
`compilation_unit_worker`, which add the objects, `sema/record.pep`,
`sema/record_codec.pep` generated by `scripts/gen-sema-record.py`,
`sema/checked.pep`)

Sema is the most expensive stage of a build, and most of a program does not
change between builds. So `pepc` checks a program one **compilation unit**
at a time, and the build cache keeps each one's checked result as a
**record**. A build checks only the compilation units an edit reaches and
loads the rest. The objects of §8's translation units (`link.TranslationUnit`,
one per source file) are a separate cache, keyed separately, after codegen.

**Compilation units.** A compilation unit is a group of files checked
together: one file, or the files that import each other in a cycle, plus
any cycles that read each other. The runtime's files are one compilation
unit, the first. Every other compilation unit is checked on the records of
the compilation units it reads, merged, and its own checked result is
cached as a record keyed on its files' text and the interface hashes of
what it reads.

`compilation_units()` builds them in two steps. First it takes the import
cycles of files: the strongly connected components of the import graph
(`_import_cycles`, with `_components`, Tarjan). A module's files are not
joined, since a file sees another file of its module only through an
import, so an edit reaches only the files that import the edited one, not
its whole module. Then it groups the cycles by what they read: "reads"
means imports and the extensions a file sees, plus coherence: a cycle
reading a type's file also reads every file extending that type
(`FileScope.extended_by`), since a specialization made with the type must
see all of its extensions. A cycle whose files only import and re-export (a
module's `module.pep`, most often) declares nothing to check, since the
linker resolved its names: it is no compilation unit, and a cycle reading it
reads what it reads instead. The strongly connected components of the
cycles' reads graph (`_components` again) are the compilation units, in an
order where each comes after every compilation unit it reads. Compilation
units are therefore the nodes of a DAG, and that order is a topological
order of it. `CompilationUnit.reads` is the transitive closure of the
compilation units it reads, the runtime always among them, in ascending
order. A compilation unit is named after its first file's namespace. The
last one holds the program's own files, the root file's: it is checked on
every build and never stored. An entry file inside a module's folder (a
package's example) loads the module's files, which can sort after it, so
the root's compilation unit is moved last; when another compilation unit
reads it, the program is checked whole instead. The language server
passes `root_last = false`: it stops at the document's compilation unit,
so a document other files of its module read keeps its place.

**Keys.** A compilation unit's key (`compilation_unit_key`) hashes:

- its `files_key`: the files' names, namespaces, preludes and texts, after
  the build's base key (compiler identity, target, options);
- and, in the order of `reads`, the **own interface** of each compilation unit it
  reads: its first line, and each line after it whose name the compilation
  unit's code can name (below).

A compilation unit's own interface (`DeltaBase.own_text`) is a hash of what its checked
result adds to, changes in, or drops from the interface of the compilation units it
was checked on. So a compilation unit's key changes only when its files change, or when
a compilation unit in its closure changes its own interface. A body edit, or an edit in
a compilation unit outside the closure, keeps the key, and the record under it is
loaded rather than checked again (**early cutoff**). The own interface is
stored beside the record (`<key>.rec.own`), so computing keys never reads a
record.

**Declarations by name.** The entries of a function, struct or enum that
is not generic (`DeltaBase.name_declarations`: its element, its
`private_functions` entry, its checked name and summary, its recorded
summary; a struct's methods' summaries too) are left out of that hash. Each
such name gets a line of its own after it: the name and the hash of its
entries. Code that does not name such a declaration reaches it only through
other declarations: a function's signature, a struct's field, a generic body
or default value. So a reader's key takes the line only when the reader can
name it (`_names_reached`): a name in its own files
(`CompilationUnit.mentions`), one a file it reads shows every reader
(`CompilationUnit.shown`), and, closing over those, one that a declaration
so named shows (`CompilationUnit.shown_by`). `file_names` splits a file's
identifiers this way: those in a top-level function or struct, outside the
bodies of functions that are not generic and the names of its own and its
methods, are shown by that declaration; the rest, extensions, globals and
imports among them, are shown to every reader. Adding or changing a
function, or a struct's field or method, that no reader can name checks only
its own compilation unit again. A struct's methods (not its constructors)
get lines of their own, the struct's name and the method's apart by a tab
(`DeltaBase.own_method`): each method's element and summaries, the rest of
the struct under its name. A reader that can name the struct takes a
method's line only when it can name the method too, or when code may call
it without naming it (`sema.called_without_naming`: operators, built-in
members such as accessors, and the methods the lowerings, passes and
codegen call, like `to_string` or `enter`); a trait's methods are named in
the trait, which every reader of it reaches. So adding or changing a method
of a struct many units name checks again only the units that call it. The fields of a struct that splits them (`sema.splits_fields`: not
generic, no attributes, not an enum; a value struct lays its fields out in
its readers and an attribute struct takes positional arguments) get lines
the same way, `S\t.f`, and their order one, `S\t.#order`, that no
reader names (so a field inserted keeps the others' lines); the struct's line
keeps the rest, its constructors among them, and `file_names` hides a
field's name like a method's. A reader takes a field's line only when it
names the field. Some checks use a foreign struct's whole field list
without naming the fields: copying it (`copies._plan`, `_contained`),
extending it (`Module.extended_checked`, which a record carries whole) and
`members` reflection. Those structs go to `Module.field_lists_read`, and
`store_checked` keeps their member lines' hashes beside the record
(`.fields`, `member_lines`). A build that finds the record under its key
takes it only when `fields_still_match`: the recorded dependencies of
Salsa's and Bazel's early cutoff. A
reader whose record patches the struct (an extension's methods) merges its
additions after the struct's methods, whatever they are now. The runtime's
lines are always taken: the compiler's own code calls its functions by name
(`_pep_panic`).

**Checking in parallel.** With more than two compilation units and more than one job
(one per logical CPU; `PEPC_COMPILATION_UNIT_JOBS` sets the number), `_check_in_workers`
checks every compilation unit but the last in `pepc --compilation-unit-worker <dir>` children,
started with the build's own command line. A compilation unit is handed to an idle
worker once every compilation unit it reads is done, as its number and key on the
worker's standard input; before each one a worker reads and links the
bodies of its files only (`Program.link_bodies`, which links more files'
bodies each time it is called), since the compilation units it reads come as
records. The
worker first reports the linking errors and the visibility errors in the
compilation unit's own files (`Program.check_diagnostics` given them, as the
build does before the first compilation unit it checks itself; the files of
the compilation units it checked before stay linked, and are not walked
again), so an error in a file a worker checks is not left to
sema, then checks it as below and leaves its record, own interface, what its
object defines, warnings or error in `<dir>` (`<k>.rec`, `<k>.own`,
`<k>.defines`, `<k>.warn`, `<k>.err`), then `<k>.done`; the compilation units it reads
come to it as their `<k>.rec` and `<k>.defines`. A rebuild (its build folder
exists) starts its first worker before loading the program
(`start_compilation_unit_worker`), so the worker loads the program while the build
does, as Gradle and Bazel keep workers ready; a build that checks no compilation unit
in workers stops it.

**Pipelining.** A compilation unit's dependents need its record to be checked, and its
object's `defines` only to compile their own: as a build system starts a
library's dependents on its interface while its code generates, a worker leaves
the record (`<k>.rec`, `<k>.own`, `<k>.warn`) and `<k>.checked` as soon as
the compilation unit is stored, then waits for the `defines` of the compilation units it reads,
leaves `<k>.compiling`, compiles, and leaves `<k>.defines` and `<k>.done`.
The scheduler starts a compilation unit once the compilation units it reads are checked, and
counts toward `jobs` only workers checking or compiling: one waiting for the
objects below uses no processor (there are at most half again as many
workers as jobs, and two more, since each holds the program). Workers' stages
then include `wait`. `<dir>` is `<build>/compilation-units.<pid>`, the build's own: builds
in one folder at once (`pepper test` builds its test programs side by side)
must not share it. It is removed after the build, but kept with `-T time`,
where each worker also leaves the time its compilation unit's stages took
(`<k>.stages`: diagnostics, merge, index, check, finish, store, object), and the build
leaves `schedule`: for each compilation unit a worker checked, its number, name, when
it began and ended (milliseconds from the start) and the compilation units it reads,
as Ninja's `.ninja_log`, to find the chain of compilation units that bounds the
build. `check_compilation_units` then
finds every compilation unit checked, and checks the last one in the build's process.

**Objects per compilation unit.** A worker that checked a compilation unit also compiles it
(`_compile_unit`), as a C compiler compiles one translation unit: it
generates IR for the compilation unit's own files and for what the compilation units below do not
define, and only declares what they do. A compilation unit larger than `_PART_SIZE`
is split into parts as in §4.1 (`_unit_parts`), compiled at once in
`--compile-part` children, so an edit to a large one does not wait on one CPU.
Each part writes the symbols it defines once optimized beside its object
(`<object>.defines`, `parts._write_defines`: not local, so not an instantiation
every use inlined), and the compilation unit's `defines` lists them all (`_defines`); a compilation unit declares exactly the symbols the
objects of the compilation units it reads list (`Generator.declared`, by Pepper
name, which `Partition.names` gives back for each respelled one), and defines any other function it gives a body: an instantiation
the compilation units below made but dropped, or a method a pass of this compilation unit added to
a struct below (`_pep_copy_value`), which has no owner there
(`own_function`), so it is `linkonce_odr`, as C++ emits an implicit special
member in each object that uses it. A declaration keeps an owner (`DECLARED_ONLY` for an
instantiation), so `prepare` gives it the linker spelling of its definition.
The object is cached under the compilation unit's key (`_store_unit`:
`<cache>/v3/u/+<name>/<key>/0.o`, `1.o` and on for its other parts
(`_unit_objects`), `defines`, and `needs`, what it uses of what the objects below
define (`_needs`), after the hashes of their `defines` (`stamp_of`), so a hit
whose objects below are unchanged compares one line; the key already
holds the codegen options), and a compilation unit counts as done from the cache only
when both its record and its object are there, and the object links with the
objects below (`Cache.unit_objects`): a body edit below can stop it defining
an instantiation without changing any key above, and an object that needs it
then failed to link (#24). So the scheduler gives a hit's record to the
compilation units reading it at once, but asks whether its object links
(`usable`) only once the compilation units it reads are done; an object
whose `needs` the objects below no longer all define is passed over for one
under its key with that stamp added (`Cache.store_unit`, which stores there
when the key holds other objects, even another build's stored a moment
before: a key's folder appears by a rename that fails when it is there), and
when there is none the hit is checked again in a worker, which keeps the
record already given out and stores its new object there; a build marks the object
used when it finds it, so no build pruning the cache removes it before this
one links. The last compilation unit is keyed like the others, and its objects, the
last compilation unit's (`0.o` and on) and the entry points' (`entry.o`), are cached under its
key with the program's `[Link]` arguments (`link`, `_link_attributes`) and
its warnings (`_store_last`): a build whose last compilation unit has the same key,
and whose objects link with those below,
checks and generates nothing and links, as Go links a `main` package from
its cache. The link takes the objects of the compilation units the last one
reads, not every one: the module files an entry file never reaches are
checked but not linked, as whole-program code generation leaves them out. Otherwise the build's process checks the last compilation unit, generates
it and the entry points, compiles the two, and stores them. So an edit
generates and optimizes the IR of the compilation units it reaches and nothing else.
Without workers (one job, two compilation units or fewer, a test program) the build
keeps the per-file translation units below.

**Checking a compilation unit.** `check_compilation_units` walks the compilation units in order. For each one
but the last, it computes the key, and loads the record under that key when
the cache has one. Otherwise it checks the compilation unit:

1. The first compilation unit checked links the bodies of every file not loaded from a
   record (`Program.link_bodies`), and runs the program checks.
2. `merged_module` builds the module of the compilation unit's closure: the closure's
   records read in order onto an empty module (see *Merging* below), then
   `sema.settle_merged` and `sema.sort_globals`. The compilation unit is checked on its
   closure only, not on every compilation unit before it in the order. Otherwise its
   result would depend on unrelated compilation units: specializations they made, or
   overloads they added.
3. `sema.index_module` indexes that module into a `DeltaBase`, before the
   compilation unit changes it: it keeps the module's structs, functions and templates
   themselves, and each struct's member lists as they are. The record is
   written as a delta on this index.
4. `check_compilation_unit`: `sema.build_on` adds the compilation unit's files to the module
   (only their declarations are walked as new, `unit_decls`), then every
   sema step runs (`run_steps_with`). The tables a pass builds each round
   take in the compilation unit's own declarations and look a checked one up by name
   only when the compilation unit's code names it (`checked_decls`, built once per
   compilation unit), so a round costs in proportion to the compilation unit, not its closure.
   `SiteTable` works this way, and so do `resolve_implicit_types`' `ImplicitTables`,
   `Callees` and declaration fingerprints: they walk `unit_decls`, whose structs
   include every checked one the compilation unit extended or specialized a method for.
   So do `synthesize_function_types`, the C-signature check of
   `shared_functions`, `lift_closures` and `resolve_type_aliases`: a checked
   declaration's function, tuple and weak types got their structs, its signatures
   their check, its closures their structs and its aliases their expansion with its
   own compilation unit. `restore_bodies` puts back only what `stash_bodies` took
   (`PassState.stashed_from`), and `stash_bodies` run again (before the passes
   that lower bodies) takes out only those of these that a pass put back: a
   method the compilation unit added to a checked struct (a generic method's
   specialization) is lowered with the unit.
5. `sema.finish_checked` makes the `CheckedUnit` (the module, the link
   summaries, the type aliases), and `store_checked` writes its record,
   own interface and warnings, rendered (`<key>.rec.warn`), under the key.
   A build that loads the record prints its warnings again, as incremental
   compilers and ccache replay a unit's diagnostics, so a compilation unit that
   warned is not checked again to warn again.

**Re-checking only the changed bodies.** Each record keeps beside it what
it was checked on and its files' text (`<key>.rec.src`, `recheck_source`):
a hash of the build's key base (the compiler, the target and the build
options, so a record never seeds a build for another target) and of the
records of the compilation units it reads (`inputs_digest`),
then each file's namespace, size and text. When a compilation unit has no
record under its key, `check_unit` looks for its newest record with the
same inputs, no warning, and files that differ from the text kept only
inside the bodies of top-level functions that are not generic, and of the
methods and constructors that are not generic of structs that are not, or in
comments and spacing, or in whole such functions and methods, structs
that are not generic with no properties or attributes, and fields with no
attributes of such structs with no generic methods, that the edit adds
under a name that no other declares and no token of the old text spells
(`find_recheck_base`, `_align`, which compares the two texts' tokens outside
those bodies and added declarations, `_added`). `recheck_compilation_unit` then:

1. reads that record onto the merged closure with its locations moved to
   the edited files (`merged_onto` with a `sema.LocShift`: a kept token's
   offset goes where the same token is now, and anything inside a changed
   body to that body's start);
2. gives each changed function the body `sema.build_file` builds now, and
   drops it from the checked functions and summaries, so the passes walk
   it as the compilation unit's own code again. A changed method's struct
   stays checked: its body is left out of `stash_bodies`
   (`PassState.rechecked_methods`) and the struct counts as extended
   (`extended_checked`), so the passes walk it as a method an extension
   added;
3. puts each added struct, function or method after the one before it in
   its file (`_add`, `_add_struct`): a struct unchecked, so the passes
   check it whole, and a method's struct walked as for a changed method; it
   gives up on a struct its file declares first, and on a function or
   method when
   the name is a trait's method, a member of the struct, a function already
   declared, one code calls without naming (`called_without_naming`), a
   constructor, or the first function of its file;
4. replaces the struct of each added field with the one built now,
   unchecked (`_add_field`), so the passes check it whole: its bodies, the
   members synthesized from its fields (`__dtor`, copies) and its layout.
   Code outside it reads fields by name and their offsets from code
   generation (`S.offset.f`), so nothing else is checked again. It gives
   up when one of the struct's methods or constructors is missing
   afterwards, or its return type or link summary changed;
5. drops the closure structs the old bodies and replaced structs lifted,
   and numbers new ones
   after every closure left in their files (`PassState.closure_counts`);
6. runs every step, which walk only the unchecked bodies and the
   specializations they newly ask for.

It gives up, and `check_compilation_unit` checks the compilation unit from
its files, on an error or a warning (unless given `report`, as pep-lsp's
`recheck_whole` does: then a warning goes there, and an error goes there
before it gives up), or when a changed function's return
type or link summary (`summary_without_place`) came out other than the
record's: code the record keeps was checked against them. Specializations
only the old bodies asked for stay in the record as dead code. A body edit
in `sema/builder.pep` builds in about 12 s instead of 24 s this way.
`Built.rechecked` names the compilation units checked so;
`PEPC_TRACE_COMPILATION_UNITS` says why one was not.

The modules of the closures are rebuilt from bytes for each compilation unit checked.
Loading a record costs a read and a merge, not a check.

**Records.** A record lives at `<cache>/v3/c16/<name>/<key>.rec`. The
folder's number is the format's version: a format change takes a new
number, so old records are never misread. Each compilation unit keeps its newest four
keys. A record starts with the program's files' namespaces, which its file
slots refer to, so it loads into a program whose files sit elsewhere. Then
comes the unit, as a **delta** on the module of its closure (`write_module_delta`
and the rest of `record_codec.pep`, generated from the model by
`gen-sema-record.py`; edit the generator, not the output):

- A list whose elements the compilation unit only appends to (functions, traits,
  extensions, specializations, and most others) is written in **mode 2**: the
  elements not in the base, each with its place. For functions and trait
  functions, a base element that the compilation unit changed in place is also written,
  with its name.
- A list that does not keep the base's elements in order (a few structs'
  constructors) is written whole, in **mode 3**, and replaces the base's.
- A struct the base holds that the compilation unit changed (a method added, a
  specialization made) is written as a **patch**: its member lists, each the
  same way.
- Sets and maps are written as the entries they gained; the checked names
  as the names they lost and gained; the checked summaries as the keys they
  lost and the entries they changed. A settled summary's blame is written
  from its function's start (`settled_text`), so an edit that shifts the
  function in its file leaves the entry, and the error it points at, right.
- `conversions` and `argument_names` are rebuilt by passes over the whole
  module, so each record keeps the compilation unit's own entries: conversions not
  already in the base, and argument names merged by place.

The delta writer finds the base's structs, functions and templates by
identity (`DeltaBase.ref_structs` and the rest), not by encoding and hashing
every declaration of the closure. One the compilation unit still holds is the base's as
it was, unless the compilation unit extended it (`extended_checked`): that one is
written as a patch, its member lists found by identity in turn. An element a
pass replaced with a copy is found by comparing records, only when identity
misses. The other lists and maps are found by the BLAKE3 hash of each
element's own record (`DeltaBase._places`). A non-generic function body read from a record is
not decoded until something needs it (`RecordIn.lazy_bodies`,
`PendingBody`, `full_body`). For hashing, such a body is written as the
bytes it was read from (`RecordOut.pending_as_bytes`), so a body never
decoded costs nothing to compare.

**Merging.** `merged_module` reads each record of a closure with
`RecordIn.merging`, onto a base that is not the one the record was written
on: the module of the compilation units before it in the closure. A mode-2 list's new
elements go after the base's; a changed element and a patched struct are
found by name; a mode-3 list replaces the base's. Lists still written by
reference to a place in the base cannot merge: reading one sets an error,
and the build reports that the compilation units do not merge. After every record is
read, `settle_merged` restores what the passes keep in order across the
whole module: externs sorted by file, trait types by name, each extension
marked applied. When two compilation units both made the same specialization, only the
first is kept: they are the same, made from the same declarations.
`sort_globals` orders globals by their files' initialization order.
Each base is dropped once the next record is read onto it, so the read
changes the base's checked names and summaries in place
(`RecordIn.consumes_base`) rather than copying them: a copy per record made
merging a closure quadratic in its size.

**Locations in other compilation units' files.** A record can hold code from
the files of the compilation units it reads: a specialization of a generic
method, or a member the passes synthesize at a struct. An edit that moves
that code but keeps the record's key would leave those locations pointing at
the old bytes. So a delta writes each location in a file of its base
from the declaration at or before it (`LocAnchors`, from `anchors_of` the
base: its structs, templates, traits and enums, their methods and
constructors, and its functions, each by name), as the declaration's name, its
start then, and the location's offsets from it. Reading the record onto a
base puts it at that declaration's start there, or the start as written when
no one declaration of that name is in that file now.

**Link summaries.** `check_confinement` keeps with each compilation unit the link
summary of every function it summarized (`Checked.summaries`, by summary
key), so a compilation unit above summarizes only its own functions and the checked
ones no summary covers yet, whose bodies come back from the stash
(`_Confinement.restore`). A call through a trait value joins the summaries
of the methods implementing it, and a compilation unit above may add implementations.
So a summary that reaches such a call (a **dependent** one: its own trait
calls, and those of the functions it calls by name) records it
symbolically: after its first line, a line per call,
`trait\tmethod\toperands\tresults`, then a tab and the `classes;taints`
of the joined summary it was made with, never the structs it reached. A
call that comes from a callee by name is recorded with its join as it is
when the caller is summarized (`_Confinement.joined_links`), not as the
callee saw it earlier in the fixed point, so every summary the pass ends
with holds there. A compilation unit uses a dependent summary only
while each of those joins is the same over the implementations its module
holds now (`_stale`, which summarizes first the implementations that have
no summary). One that no longer holds is dropped from the module's checked
summaries, and the pass summarizes and checks again without it, from its
restored body. A new implementation whose summary the join already covers,
such as most new specializations of a generic one (another
`ArrayIterator<T>`), leaves every recorded summary, the record and the own
interface alone. A compilation unit checks only the dependent summaries it uses: one
it leaves may be stale there, and each compilation unit that reads it checks it again,
so a summary merged from a compilation unit that never saw a sibling compilation unit's
implementation is found stale too.

**Own interfaces.** The own interface is computed while the delta is
written (`own_lines` in the generator, `DeltaBase.own`): an entry for each
element, entry or name the delta adds, changes or drops, each hashed with
non-generic bodies blanked (`blank_bodies`) and positions blanked
(`blank_locs`). Generic bodies stay in, because a reader specializes them,
and so do traits' default method bodies, because `apply_extensions` copies
them into each adopting struct, whose compilation unit compiles them.
Left out:

- The fields in `NOT_INTERFACE` (`literal_args`, `call_targets`,
  `argument_names`, `stripped`, `summaries_to_record`, `cached_files`).
  They are what the passes record for codegen and the build, not
  declarations a reader is checked against.
- `recorded_summaries`, the link summaries of the bodies the build cache
  skipped, for the same reason.

When adding a field to the model, decide which side it falls on. If it
can change what a reader of the compilation unit checks or generates, it belongs in
the own interface. Otherwise, adding it there makes keys change on edits
that should be cut off.

**Invariants.** What makes merging and cutoff sound:

- A checked declaration does not change once its compilation unit is stored, except
  by a later compilation unit's patch, which that compilation unit's record carries. A pass that
  changes a checked struct (adds a method, applies an extension) marks it in
  `extended_checked`, as `apply_extensions`, `specialize_methods` and
  `synthesize_copies` do; any other change in place is lost from the
  record, since the delta finds the struct by identity.
  `PEPC_VERIFY_IDENTITY` catches one.
- Two compilation units never make different declarations under one name. Overload
  sets are named by signature, and a specialization two compilation units
  both make is the same.
- A mode-3 list replaces the base's: when two compilation units both rewrite the same
  struct's constructors, the later one's are kept.

**Debugging.** These environment variables are read by `pepc`:

- `PEPC_TRACE_COMPILATION_UNITS`: each compilation unit's own interface, and whether it was loaded
  or checked.
- `PEPC_VERIFY_CUTOFF`: checks every compilation unit loaded by early cutoff again, on
  its closure, and fails the build naming the fields where the result differs
  from the record. This catches a key that leaves out something the
  compilation unit's result depends on, or a record that carries something it should
  not.
- `PEPC_RECORD_STATS`: each record's bytes by field (those of 1 KB or
  more), and how its lists were written (merged, whole, changed).
- `PEPC_TRACE_INTERFACE`: each interface hash by field and by declaration.
- `PEPC_VERIFY_IDENTITY`: also indexes each base by hash, and reports on
  standard error each element the delta found by identity whose record
  changed since (`identity: <list> <place> <name> changed in place`): a pass
  that changed a checked declaration without marking it extended. A
  self-build with it set reports none.
- `PEPC_VERIFY_SUMMARIES`: after `check_confinement`, makes every link
  summary it used again from the bodies, without the dependent summaries
  recorded below, and reports each that differs
  (`verify-summaries: <key> <used> fresh <made>`), then the counts. A
  self-build with it set reports none.
- `PEPC_VERIFY_INJECTED`: after the last sema pass, fails the build at the
  first injected construct left in its placeholder form
  (`injected.verify_injected`, section 3). `scripts/pepper-tests.sh` sets it.
- `PEPC_COMPILATION_UNIT_JOBS`: how many compilation units to check at once; 1
  checks them in the build's process. `PEPC_LAYER_JOBS`, its old name, still
  works; so does `--layer-worker` for `pep-lsp --compilation-unit-worker`.
- `PEPC_NO_COMPILATION_UNITS`: checks the whole program at once, to compare with a
  build in compilation units.
- `PEPC_COMPILER_IDENTITY`: names the compiler in every key instead of its
  executable's path, size and time (`compiler_identity`), as ccache's
  `compiler_check = string:...`, so compilers built while working on one
  share a warm cache. Only for changes that leave the output the same.

When `PEPC_VERIFY_CUTOFF` fails, compare the module's fields by name (the
failure names the first ones) between the record and the check, and find
which pass made the difference. Fix the cause (a key that misses an input, a
record that carries a stale copy) rather than loosening the comparison. A
change to compilation units or records is also checked by building the documentation's
examples and `pepc` itself with compilation units and with `PEPC_NO_COMPILATION_UNITS`, and
comparing the executables.

## 9. Tests

The tests are Pepper `[Test]` functions, run by `pepper test`
(`tools/pep-test`); `scripts/pepper-tests.sh` runs them all, as CI does
(`docs/src/contributing/tests.md`). It builds the tools from the checkout
with the `pep-build` it is given (default: the installed build of main)
into `target/pepper-tests/bin`, puts that folder on the `PATH`, then runs
the runtime's tests in `runtime/` and the tools' in `tools/` (at
`-O1`, 600 s a test). A test fails when it leaks: the `TestRunner` compares
`_pep_live_allocs` before and after it.

| Kind | Where | Notes |
| --- | --- | --- |
| Runtime | `runtime/<module>/test/*_test.pep`, `runtime/test/*_test.pep` (the prelude's) | Also run with `-D USE_ZLIB` (compress) and `-D USE_LIBCRYPTO` (digest). |
| Parser | `compiler/parse_test.pep`, `desugar_test.pep`, `tokens_test.pep`, `recovering_test.pep` | Every source file in the repository parses; written and desugared trees; every token and comment placed once; recovery on three broken forms of every file. |

## 10. Recipes

### Add a syntax form

1. Add the AST node in `ast/ast.pep`, with a `Span` and a `name_span` if it
   names something, and its `to_json()`.
2. Add the grammar rule in `parse/parser.pep`: take tokens with `_advance`,
   fail with `_expect`/`_fail("expected …")`, try an alternative reading
   through a `Mark` (`_mark`/`_restore`), and update `is_reserved_word` for
   a new keyword. If the source form needs lowering that the written tree
   keeps (as interpolated strings do), add it to `compiler.desugar`.
3. Extend the walks that must see the new node: `parse/checks.pep`,
   `link/walk.pep` (the walk linking, visibility and deprecation share, so
   imported names inside it are rewritten and checked, and names it binds
   shadow imports), and the language server's scope and syntax walks
   (`tools/pep-lsp/scope.pep`, `infer.pep`'s `SyntaxWalk`).
4. Lower it in `sema/builder.pep`. Prefer desugaring into existing model
   nodes, as `for` loops are. If you do add a model node, add its fields to
   `sema/model.pep` and rerun `scripts/gen-sema-model.py`, then extend the
   model walks (`sema/walk.pep`), the passes that must understand it, and
   codegen (`codegen/expressions.pep`, `value_sema_type`).
5. Take its tokens in `compiler/tokens_test.pep`'s `TokenWalk` and lay
   them out in `tools/pep-fmt/format.pep`; `tools/pep-fmt/repository_test.pep`
   fails until the formatter keeps a file that uses the form unchanged.
6. Add tests: a curated program in `compiler/passes_test.pep` (or
   `sema_test.pep`, `link_test.pep`) for each error, and a
   `tests/<Feature.Case>/test.pep` program if useful. Update the language
   guide chapter in `docs/src/language/` (with a tested example in
   `docs/examples/`) and the TextMate grammar in pep-lang/vscode-pepper.

### Add a sema pass

1. Create `sema/<name>.pep` with the pass, a function taking the `Module`
   and the `PassState`. Start it with a `##` file comment that says what it
   rewrites or checks.
2. Run it from `sema/passes.pep`: a new case of `_step` at the right point
   (renumbering `PORTED_STEPS` when it runs before the specialization
   loop). Consider whether it must run again after the loop. Import it in
   `passes.pep` only: `state.pep` imports no pass (§8).
3. Report errors with `state.report(diagnostic)` and keep going; keep what
   a later pass needs in the `PassState`, not in a global.
4. Test it with curated programs in `compiler/passes_test.pep`, each with
   the `# expect:` line it must give, and a `tests/` or `docs/examples/`
   program for behaviour.

### Add a compiler error

Follow AGENTS.md ("Compiler errors are clang-style diagnostics"): report at
the exact token and use clang wording. Use the mechanism of the layer the
error belongs to (section 6). If the node has no `Loc`, add one. Add a
curated program whose `# expect:` line is the error's header to the test of
its stage (`link_test.pep`, `sema_test.pep` or `passes_test.pep`).

### Add a runtime API

1. Write it in Pepper in the right `runtime/*.pep` file (or a new top-level
   file, which joins the prelude automatically). Mark it `export`. Put
   internals under `_pep_`/`_io_`.
2. Document it with `##` doc comments per AGENTS.md. Run
   `pep-doc check`.
3. For the `io` module, add it to the implementing file and re-export it
   from `runtime/io/module.pep`.
4. Regenerate the reference: `pep-doc reference`.
   A new file needs a title in `pages()` (`tools/pep-doc/reference.pep`)
   first. Commit the changed `docs/src/reference/*.md` and `docs/src/SUMMARY.md`.
5. Test it with `[Test]` functions in the module's `test/` folder (the
   prelude's in `runtime/test/`). For behaviour the docs show, add a
   `docs/examples/` program.

### Add an attribute

The parser accepts any `[Name]` or `[Name(args)]` on functions, externs,
structs, members, traits, extensions, aliases, globals, imports,
re-exports, and blocks, and sema carries it on `attributes`. An attribute
must be one of `static_blocks.BUILT_IN_ATTRIBUTES` or a struct marked
`[Attribute]` (`check_attributes` reports any other), so a new built-in
attribute goes in that list, and gets a documented `[Attribute]` struct in
`runtime/attributes.pep` describing its value (regenerate the reference).
To give one meaning, read it where it applies:

- `[Link("lib")]`, `[Link(lib = "lib", name = "sym")]` → validated by
  `sema/named_arguments.pep`, read by the driver's `link_inputs` and by
  codegen's extern declarations (the C symbol)
- `[Alias("alias", "parameter")]`, `[Rename("old", "new")]` (functions) →
  `sema/named_arguments.pep`
- `[Target(...)]` → `sema/platform.pep`
- `[Deprecated("message", "replacement")]` → `link/deprecation.pep` (checked by
  the builder, read by `check_uses` and `check_deprecated_members`)
- `[Shared]` → `StructDef.is_shared`
- `[Isolated]` (structs), `[Move]` (parameters; the parser accepts
  attributes before any parameter), `[MoveSource]` (the parameter of the
  runtime's `move<T>`; runtime free functions only) and `[Locked]` (a
  function-value parameter called with a locked value, such as
  `Condition.wait_while`'s predicate; runtime only) →
  `sema/confinement.pep`, which reports any other parameter
  attribute (`check_parameter_attributes`) and wraps each `[MoveSource]`
  argument in `Expression.Move` (`lower_moved_arguments`); codegen reads
  `[Move]` and `[MoveSource]` (`check_confinement.takes_over`,
  `sending_params`)
- `[NotCopyable("why")]` → `sema/copies.pep`
- `[Implicit]` → `StructDef.implicit_from`, checked in `sema/builder.pep` and
  applied by `convert_to_traits`
- `[Equatable]` (structs and reference enums; with `include`/`exclude`,
  their fields) → `sema/equatable.pep` (§2.6), checked again by `check_hash_keys`

An attribute's arguments may be named, as in a call (`[Link(name =
"sym")]`): `ast.Attribute`'s `name()` and `arguments()` read them. Validate the
arguments and report a located error, and add curated programs to the
compiler's tests (`passes_test.pep`).

### Add a platform-specific runtime function

Write twin declarations with the same name and signature, guarded
`[Target(OS(Windows))]` and `[Target(!OS(Windows))]` (see
`runtime/io/path.pep`, `sys_posix.pep`, and `sys_windows.pep`). Dropped
twins are never compiled together. Use `[Link(name = "sym")]` when the
C symbol differs by platform, and `[Link]` for extra libraries. Build the
other platforms' code with `--target` (`compiler/target_test.pep` and
`imports_test.pep` check what platform selection keeps), and run it for
real with the `platform-test` workflow (`.agents/skills/platform-test`).

## 11. CI

Every job in every workflow but `llvm-package.yml` runs on a GitHub-hosted
runner: **`windows-2025`** and **`ubuntu-24.04`** (x64), and **`macos-15`**
(arm64). A new job picks one of those labels. Every job
installs the published build of main (`scripts/ci-install-toolchain.sh`)
and builds and tests with it, except where the compiler changed: a merge
that changes `tools/compiler/` (`changes` classifies it), or a dispatch on
a branch, has each test and
cross-link job build that compiler with the installed one first
(`scripts/ci-build-compiler.sh`, the release's stage 1), and every later
step uses it, so the whole suite tests the changed compiler. The test jobs of `ci.yml` build into a folder beside the checkout
(`PEPPER_TARGET_DIR`).

- **`ci.yml`** (pull requests, pushes to main, and dispatch; main's ruleset
  requires its `test` check before a pull request merges):
  - `test` is the gate: a job that always runs (`if: always()`, so never
    skipped, since a skipped job counts as passing) and passes only when
    `test-windows`, `test-linux` and `test-macos` succeeded or the commit
    is prose only. It fails on a cancelled run.
  - `test-windows` (**`windows-2025`**), `test-macos` (**`macos-15`**)
    and `test-linux` (**`ubuntu-24.04`**) run the suite in two jobs per
    OS (a matrix over `PEPPER_TESTS_PART`: `compiler`, the compiler's
    tests, and `others`), so a run takes six runners. Their setup is the
    composite action
    `.github/actions/prepare-tests`: provision LLVM 20
    (`ci-provision-llvm.sh`, cached on Windows; the compiler's tests link
    it through pepper-llvm) and the libraries the tests link, install the
    newest published toolchain (the `x.y.z-dev` prerelease `release.yml`
    publishes on each merge, or a release with a higher version, through
    `install.sh` / `install.ps1`), name `PEPPER_CACHE_DIR` (one build
    cache every build in the job shares, the tools' tests' own builds
    included; it starts empty, since its keys name the compiler, new in
    nearly every run), and build `tools/compiler` when it changed
    (`ci-build-compiler.sh`, from its own build cache, which actions/cache
    carries between runs keyed on stage 0's contents). Then `scripts/pepper-tests.sh` runs, beside `scripts/ci-monitor.sh`,
    which prints the runner's memory, disk and biggest processes each
    minute; a job that fails, is cancelled or times out ends with its
    `--report` (Diagnostics). The Windows `others` job also runs `pep-doc
    check`, and the Linux `others` job cross-compiles a few examples for Linux arm64
    and runs them under qemu. All three are required, through `test`,
    which fails on a cancelled or timed-out job as on a failed one.
  - `cross-sysroots`, `cross-link` and `cross-run` (not required)
    cross-link from each runner for the other two operating systems and
    run the result on its own runner. `cross-sysroots` packs the Linux

    branch is main.

  section before writing a script for it.
- **`release.yml`**: on each merge into main that changes `runtime/`,

  the version main holds (`0.4.0-dev` in `VERSION`, set with each tool's

  the toolchain for linux-x64 (in a `manylinux_2_28` container on

  `scripts/build-llvm-manylinux.sh`: taken from the published manylinux
  package, or built from source when none is published), macos-arm64
  (`macos-15`) and windows-x64 (`windows-2025`)

  stage 0, then with itself, builds every tool with that, archives an

  the one self-hosted workflow (`pepper-linux`, `pepper-macos`,
  `pepper-windows`), and runs only by hand.

## 12. Conventions and patterns

- **Loc on every naming node.** Synthesized nodes copy the source `Loc`
  they stand for (the `for` iterator uses the iterable's). Use `Loc.none()`
  only when there is no source. Codegen's `locate` attaches these
  locations to its errors.
- **Errors never panic on user input.** Panics that remain are internal
  invariants; a panic in the compiler ends the build, and in the language
  server ends the server, so a user's code must never reach one.
- **State in values, not globals.** The parser's position and errors live
  in its `Parser`, the passes' in the `PassState`, a build's in the
  driver's values, so a compiler module can be used more than once in one
  process (the language server, the compiler's tests).
- **One loader.** The compiler, its tests, pep-doc and the language server
  all load programs through `link.load_program`.
- **Pointers.** Outside `extern` declarations, write `__ptr<T>`
  (`parse/checks.pep` rejects `T*` there). The parser turns C's `T*` into
  `__ptr<T>`, so it is the only pointer type sema and codegen see. Extern
  prototypes mirror C and keep `char*`.
- **Naming.** Language and runtime types are PascalCase (`String`, `Array`,
  `HashMap`, renamed in). Methods and functions are snake_case, with
  whole words preferred (`remove_at`, `read_to_string`, `is_permission_denied`,
  `capacity`). Compiler-synthesized names start with `__` (`__refcount`,
  `__dtor`, `__index_get`, `__for_iterator_N`, `__function`) and cannot be
  reached from source. Methods are mangled as `Struct.method`, and
  specializations as `Name<args>`.
- **Comments explain why.** File comments (`##` at the top) state what a file does
  and what invariant it keeps, and they often cite the bug that motivated a
  choice (see `codegen/target.pep`, `driver/linker.pep`). Keep that style.
- **Commits and PRs.** Branch first. Titles are imperative, sentence case,
  with the PR number appended on merge (`Add for loops and the iterator
  protocol`). Bodies explain the why in prose. Write messages to a
  file (`git commit -F`, `gh pr create --body-file`; see AGENTS.md). The
  `finish-pr` skill covers push → PR → review → merge; it never resolves
  review findings on its own.

## 13. Known limitations and sharp edges

- **Mangled private names.** Every file merges into one `Module`; private
  names are kept apart only by mangling (`helper@io/file`). Anything that
  shows a model name to the user must go through `namespace`:
  `demangle` (single-quoted names in messages; `render_all` and the
  language server's diagnostics). Code that synthesizes a reference by name
  (`_pep_interpolate`) can reach only a declaration that keeps its name, so
  it must be exported by the runtime or the root file, whose exports keep
  their names.
- **Trait values are one level deep.** There are no supertraits, so one
  trait type converts to another only through `as?` or a type pattern,
  which test the struct behind it at run time. `Atomic<T>` of a trait type is rejected (a trait type is not `Shared`): two
  pointers do not swap atomically, and the struct behind it may not be
  thread-safe; the book points to `Mutex<Shape>`. `for` and `with` still choose their
  protocol by the methods a type has (`ForIterator`), statically for a
  struct and through the vtable for a trait value.
- **Constrained bodies are checked, not compiled, against their
  constraints.** `check_bounds` types a generic base's expressions itself
  (best effort: its own scopes, `static_type`, the struct table with each
  generic struct's parameters substituted) and reports only what it can
  type; an expression it cannot type is left to the specializations, which
  still compile each body for its type argument and dispatch statically.
- **Runtime discovery is by location.** The runtime must sit within five
  levels above the current directory or the executable, or be named by
  `PEPPER_RUNTIME`. The compiler reports an error when none is found.
- **Targets.** `--target` names one of the triples `link.Target` accepts
  (x86_64 and AArch64 for Linux, macOS, Windows, iOS and Android, and
  `wasm32-wasip1`); 32-bit x86 is not one.
- **No nesting limit.** The parser and every pass recurse over the tree,
  and nothing bounds its depth: a deeply enough nested program can
  overflow the compiler's stack.
- Some passes leave unresolved nodes for codegen to report as
  `unknown …`.
- **Sync types.** `Lazy<T>` relies on `check_shared_types` to reject a
  non-thread-safe `T`. `Mutex<T>` holds any struct, confined by
  `check_confinement`; its constructor and `replace` take their `[Move]`
  value without a copy (the caller hands its reference over) and `move` it
  into the slot under the lock. `Channel<T>` takes any `T`: its buffer
  field is `__ptr<__ptr<void>>`, `send` and `try_send` take a `[Move]`
  value and `_push` moves it into its slot under the lock, and `_pop` moves
  it out.
- **Confinement and raw memory.** Raw pointers, `extern` code and
  Array's raw slot moves are the code's own promise. A reference read through a
  pointer the walk cannot follow to its owner (one an `extern` returned,
  such as a thread-local slot, or one a `[Shared]` struct's field holds,
  such as a `Channel`'s buffer) is tainted, never fresh. The runtime's
  `move(p[i])` (`Channel._pop`, `Mutex.replace`) promises instead that the
  slot held the only reference; the promise is unchecked, so only runtime
  files may make it.
- **Confinement is flow-insensitive** within a function, and a variable
  declared outside a `with` block is an outside value whatever it holds, so
  a value received into a variable needs `copy` (or `move`, when the
  variable is its only holder) to move into a locked value.
- **`copy` of a trait value** cannot be checked at compile time: one that
  holds a struct that cannot be copied panics at run time.
- **Only the first sema error is reported** per compile
  (`PassState.report`).
- **Unused CLI flags**: `-v`, and `-T` channels other than `time` and
  `cache`. Only the first source file is compiled (except under `--test`).
