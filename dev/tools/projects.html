The Pepper Programming Language

Projects: pep.toml

A pep.toml file marks the root of a project. It names the project, says how pepper build builds it, and lists the packages it depends on, so a project builds with pepper build and nothing else:

cd my_app
pepper build          # builds the program pep.toml describes
./my_app

pepper new my_app starts a project with a pep.toml, a main.pep and a test, and pepper new my_lib --lib a package (see Starting a project: pep-new and pep-init). A pep.toml can say more:

[package]
name = "my_app"
version = "0.1.0"
description = "Draws shapes"
authors = ["Ada <ada@example.com>"]
license = "MIT"
repository = "https://github.com/me/my_app"

[build]
entry = "src/main.pep"

[dependencies]
geometry  = { github = "someone/geometry", version = "1.2" }
json      = { gitlab = "group/pepper-json", version = "0.4.x" }
fast_json = { github = "other/json", version = "2" }   # renamed: 'json' was taken
http      = { codeberg = "someone/http", branch = "main" }
shapes    = { path = "../shapes" }

[dev-dependencies]
fixtures  = { github = "someone/fixtures", version = "1" }   # only tests and examples import it

[target.'OS(Windows)'.dependencies]
winapi    = { github = "someone/winapi", version = "1" }     # only builds for Windows see it

[features]
default   = ["tls"]
tls       = ["dep:openssl"]          # a build with it defines 'my_app_tls' and uses openssl

A package is a project other projects depend on: a repository (or folder) with a pep.toml at its root. Its root module.pep is the module its dependency name imports, and any folder inside it holding a module.pep is a module of the package too.

[package]

KeyWhat it is

Unlike toolchain, which picks the toolchain the project itself builds with, it says what the package's users need

[build]

pepper build with no file builds the project: it finds the nearest pep.toml in the current folder or a folder above it, and builds the [build] table's entry file into its output. Every path is relative to the folder holding pep.toml, and the build's intermediate files and cache go in that folder's .pep, wherever pepper build runs.

KeyWhat it isDefault
entryThe file that holds mainmain.pep
outputThe executable; building for Windows adds .exe to a name with no extensionthe package's name
includeAn array of extra folders to search for modules, as -I addsnone
linkAn array of C libraries to link, as -l addsnone

Options on the command line still apply: pepper build -O builds the project optimized, and -o names another output. A file argument builds that file instead (pepper build tools/gen.pep); the project's dependencies, include folders and link libraries still apply to it, since it is in the project.

[dependencies]

Each key is the name source code imports, and its value says where the package comes from and which revision to use:

[dependencies]
geometry = { github = "someone/geometry", version = "1.2" }

import geometry;
import geometry.solids;     # the module in the package's solids/ folder

main(): int {
    print("{0} {1}", geometry.area(3, 4), solids.volume(2));
    return 0;
}
KeyWhat it is
github, gitlab, codebergThe repository, owner/name (on GitLab, group/subgroup/name too)
pathA folder on disk, relative to this pep.toml, instead of a repository
packageWith a repository: the member of the repository's workspace it is, by its [package] name (see A member as a Git dependency)
versionA semver range of the repository's version tags: 1.2, 0.4.x, >=1.0, <2
branchA branch
tagA tag
commitA commit
optionaltrue: a build uses it only when a feature turns it on
featuresAn array of the dependency's features to turn on
default-featuresfalse leaves the dependency's default feature off
workspacetrue: its source and revision are its workspace's

A dependency has exactly one source, and at most one of version, branch, tag and commit; with none, it follows the repository's default branch. A path dependency takes only a version, which a build ignores and publish asks for.

Imports

import geometry imports the package's root module, its module.pep. import geometry.solids imports the module in its solids folder, and binds the last name, so its declarations are solids.volume; as names it otherwise (import geometry.solids as s). A dotted import whose first name is not a dependency looks for the nested folder on the search paths: import a.b finds a/b/module.pep.

Because the name lives only in pep.toml, a package that moves to another host or organization, or a switch to a fork, changes one line of pep.toml and no source file. Two packages whose repositories share a name get different keys:

json      = { gitlab = "group/pepper-json" }
fast_json = { github = "other/json" }

Where dependencies live

A dependency from a Git host lives in the project's .pep/deps/<host>/<owner>/<name>, such as .pep/deps/github.com/someone/geometry. One copy serves the whole project: each package's own pep.toml names the packages it needs under its own keys, and an import in one of its files resolves against those keys, to the same copies.

pepper package fetches them there and records the commit of each, the dependencies' dependencies included, in pep.lock beside pep.toml; commit pep.lock with pep.toml. pepper build fetches what pep.lock lists and .pep/deps lacks or holds at another commit, so a fresh clone builds with pepper build alone, with git or, where git is missing, by downloading each locked commit's archive over HTTPS and checking it against the checksum pep.lock records. See The package manager: pep-package, which also says how versions are chosen when several packages need one.

pepper package add someone/geometry       # adds it to pep.toml and fetches it
pepper build

In CI, pepper build --locked and pepper test --locked fail when pep.lock is out of date with pep.toml instead of updating it, and --offline builds with only what .pep/deps and the shared download cache hold (--frozen is both; PEPPER_LOCKED=1 and PEPPER_OFFLINE=1 do the same). See Reproducible builds. They apply to dev-dependencies as to the rest.

A project that sets [fetch] vendor (pepper package vendor does) keeps its dependencies in that folder of the repository instead, and builds with no network and no download cache; see [fetch].

[dev-dependencies]

A package the project's tests and examples use but its code does not, such as a test helper, goes in [dev-dependencies], written as in [dependencies]:

[dev-dependencies]
fixtures = { github = "someone/fixtures", version = "1" }
  • Who sees them: a test build (pepper test, which builds with pep-build --test) and a build of a file in the project's examples folder, or a folder below it. Any other build of the project, such as pepper build, does not: an import of one there is an error that says to move it to [dependencies].
  • Not part of the package: a project that depends on this package neither fetches nor resolves its dev-dependencies, so one that conflicts with the dependent's own dependencies does no harm.
  • Locked with the rest: pep.lock records them beside the other packages, each that only dev-dependencies lead to marked dev = true, and pepper build fetches them with the rest.
  • Needs toolchain 0.11.0: an older toolchain rejects a pep.toml with [dev-dependencies] as an unknown table, a dependency's included. So a package that has one sets minimum_toolchain = "0.11.0" (or later) in [package], and pepper package on an older toolchain skips its versions instead of failing to build them. pepper package publish checks it (see pep-package).

pepper package add --dev adds one, and pepper package remove removes one from either table (see pep-package). A name may be in only one of the two tables.

main.pep:1:8: error: 'fixtures' is a dev-dependency, which only tests and the files in examples/ import; move it to '[dependencies]' to import it here
    1 | import fixtures;
      |        ^~~~~~~~

[target.'<condition>'.dependencies]

A package only some platforms need, such as a binding to a Windows API, goes in a [target] table whose key is the condition, written as in [dependencies]:

[target.'OS(Windows)'.dependencies]
winapi = { github = "someone/winapi", version = "1" }

[target.'OS(Linux) && Arch(x64)'.dependencies]
epoll = { github = "someone/epoll", version = "0.3" }

  • The condition is what [Target(...)] takes, OS(...), Arch(...) and BuildOption(...) with &&, || and ! (see Platform selection), and it is checked the same way: OS(Darwin) is an error at the key.

  • Who sees them: a build whose target the condition selects: the machine building, or the platform --target names in a cross build. Guard the import the same way, so other targets skip it:

    [Target(OS(Windows))]
import winapi;

    An import a build for another target reaches is an error:

    main.pep:1:8: error: 'winapi' is a dependency only for targets where 'OS(Windows)' holds, which this build's does not; put '[Target(OS(Windows))]' on the import
    1 | import winapi;
      |        ^~~~~~

  • Locked for every platform: pep.lock lists every platform's packages, so it is the same on each, and marks those only some need with their target (see pep.lock). A build fetches only what its target needs; resolving a change to pep.toml, or checking the lock with --locked, reads every package's pep.toml, so it fetches every platform's.

  • In a package: a dependency's [target] tables apply to the projects that use it, for their build's target.

  • Needs toolchain 0.11.0: an older toolchain rejects a pep.toml with a [target] table as an unknown table, so a package that has one sets minimum_toolchain = "0.11.0" (or later) in [package], as for [dev-dependencies]; pepper package publish checks it.

pepper package add --target 'OS(Windows)' adds one, and pepper package remove removes one (see pep-package). A name may be in only one of the dependency tables, and a [target] table holds only dependencies.

[features]

A package with optional parts, such as TLS support in a client, names them in [features], so a project that does not want one neither builds its code nor its dependencies. Each key is a feature, and its value lists what turning it on turns on:

[package]
name = "http"

[dependencies]
openssl = { github = "someone/openssl", version = "3", optional = true }
zlib    = { github = "someone/zlib", version = "1", optional = true }

[features]
default = ["tls"]
tls     = ["dep:openssl"]                  # the optional dependency openssl
gzip    = ["dep:zlib", "zlib/simd"]        # zlib, and zlib's feature 'simd'
full    = ["tls", "gzip"]                  # other features of this package

  • Code reads a feature as a build option: a feature that is on defines the build option <package>_<feature>, the package's name and the feature joined with _ (http_tls), so [Target(BuildOption(...))], [BuildOption("...")] and reflect.build_option select code by it, as for a -D option (see Build options). A feature name is an identifier. The names join with a bare _, so two packages of one build should not share a name: their features would define the same options.

  • What a feature lists: another feature of the package (tls); an optional dependency, dep:<name>; or a feature of a dependency, <name>/<feature>, which turns the dependency on too when it is optional. Each is checked against the package's own pep.toml.

  • default is the feature a package has on unless it is asked not to: --no-default-features on pepper build and pepper test for the project's package, default-features = false in a dependency's entry for that dependency.

  • Turning features on: pepper build --features tls,gzip (and pepper test --features) for the project's package; a dependency's entry, features = ["gzip"], for that package. Features are additive and unified across the graph, as in Cargo: a package that two others depend on has every feature either turns on, and there is one copy of it in the build.

  • Optional dependencies (optional = true) are seen only by a build with a feature that turns them on; guard the import with the feature's build option, so a build without it skips the import:

    [Target(BuildOption(http_tls))]
import openssl;

    An import of one that no feature this build turns on lists is an error:

    module.pep:1:8: error: 'openssl' is an optional dependency, which no feature this build turns on lists; put the '[BuildOption(...)]' of a feature that lists 'dep:openssl' on the import

    A dev-dependency cannot be optional.

  • Locked whatever the features: pep.lock records optional dependencies like the rest, and a build fetches them whether or not a feature turns them on, so the lock does not depend on which features a build picks, as it does not on the platform.

  • Needs toolchain 0.11.0: an older toolchain rejects [features], and a dependency's optional, features and default-features, so a package that uses them sets minimum_toolchain = "0.11.0" (or later), as for [dev-dependencies]; pepper package publish checks it.

pepper package add --optional, --features and --no-default-features write a dependency's optional, features and default-features (see pep-package).

Workspaces: [workspace]

A repository holding several related packages, such as a library with its examples or a client and a server, makes them one workspace: a pep.toml at the root lists them, and they share one pep.lock and one .pep/deps, so every member builds with the same revision of each dependency.

shapes/
  pep.toml            [workspace]
  pep.lock            one lock for every member
  app/pep.toml        [package] name = "app"
  libs/geo/pep.toml   [package] name = "geo"
  libs/draw/pep.toml  [package] name = "draw"

# shapes/pep.toml
[workspace]
members = ["app", "libs/*"]

[workspace.dependencies]
numbers = { github = "someone/numbers", version = "1.2" }
geo     = { path = "libs/geo", version = "0.3" }

# shapes/app/pep.toml
[package]
name = "app"

[dependencies]
numbers = { workspace = true }                   # someone/numbers 1.2
geo     = { workspace = true, features = ["3d"] }
draw    = { path = "../libs/draw", version = "0.1" }
  • members lists the member folders, relative to the root: a folder (app), or a glob of folders (libs/*, see io.glob). Each holds a package's pep.toml. The root may be a package too, with a [package] of its own: it is then a member without being listed. A root without one only holds the workspace.
  • One lock: pepper package and pepper build, run in the root or any member, resolve every member's dependencies together into the root's pep.lock, and fetch into the root's .pep/deps. The members' own dependencies count as the project's, so when two ask for one package, both ranges must hold (see Resolving versions).
  • [workspace.dependencies] gives a source and revision once, for each member to inherit with workspace = true. A member's entry adds optional, features and default-features, and nothing else; a path there is relative to the root.
  • Members depend on each other with path. A version beside the path is for publish, which refuses a path without one, and checks the sibling is published at a version it accepts; a build in the workspace uses the folder. A project outside the workspace that fetches the member reads it as the sibling of the same repository at that version (see below).
  • Building: pepper build in a member builds that member; in a root with no [package], every member. --all builds every member, and -p <name> (repeated for more) the members by package name, from the root or any member, each into its own output; a member with no entry file, a library, is skipped. pepper test --all and pepper test -p <name> test them the same way (see pep-build and pep-test).
  • Features are unified across the members a build selects, as in Cargo: each member's default and its dependencies' features are on in every one of them, and --features turns a feature on in each member that has it.
  • [overrides] belong in the root, and apply to every member; a member's own are ignored.
  • One level: a member cannot be a workspace itself, and a package is in the workspace of the nearest pep.toml above it with [workspace], when that lists it. A package in .pep/deps is in none of the project's.
  • Needs toolchain 0.11.0, as for [dev-dependencies]: [workspace] and a dependency's workspace and package are unknown to older toolchains.

A member as a Git dependency

A project outside the workspace depends on one of its members by the repository and package, the member's [package] name, as Cargo does with a package inside a Git repository's workspace:

[dependencies]
geo = { github = "someone/shapes", package = "geo", version = "0.3" }

pepper package add someone/shapes --package geo writes that entry (see pep-package).

  • Found through the root's members: the member is the package of that name among the folders the root's [workspace] members lists, so it may move between folders without its dependents changing. Without package, a dependency is the repository's root package.
  • Tagged on its own: publish in a member tags <name>-v<version> (geo-v0.3.1), and a member's version range reads only its own tags, so each member is released at its own pace. The root package keeps v<version>, as a single-package repository does. A package name is an identifier, with no -, so the tags cannot clash.
  • Its own checkout and lock entry: it is locked as github:someone/shapes#geo (see pep.lock), and checked out at its own commit in .pep/deps/github.com/someone/shapes#geo, from the same repository in the download cache as every other member. [overrides] name it by that source too.
  • Its siblings: a path with a version in the member's pep.toml names another package of its workspace, so the project depends on that member (or the root) of the same repository, at the newest of its own tags the version accepts, not at the commit the member was fetched at.

A package with a path, which names a member's folder itself, or one that is not an identifier, is an error at the key. A package the workspace lacks is an error at its value when pepper package fetches it:

pep.toml:5:43: error: someone/shapes has no workspace member 'gem'; its members are 'geo', 'draw'
    5 | geo = { github = "someone/shapes", package = "gem" }
      |                                              ^~~~~

Workspace errors

The problems of a workspace are errors at the member in the root's members, or at the dependency that inherits:

pep.toml:2:19: error: workspace member 'app' is listed twice
    2 | members = ["app", "app"]
      |                   ^~~~~
  • a member that is not a package (no pep.toml), one listed twice, or one that is a workspace itself;
  • workspace = true with a source or revision of its own, in a package no workspace lists, or naming what [workspace.dependencies] lacks;
  • optional, features, default-features or workspace in [workspace.dependencies].

[overrides]

To try a fix in a package deep in the graph, or to use a fork until the fix is released, the project replaces the package wherever the graph reaches it, without editing the pep.toml of each package on the way:

[overrides]
"github:other/numbers" = { github = "me/numbers", branch = "fix-overflow" }
"github:someone/geometry" = { path = "../geometry" }

  • The key is the source of the package it replaces, as pep.lock writes it: the host's key, :, and the repository (github:owner/name, and # and the member for a workspace member). One table keyed by the source is enough, since a source is what makes two dependencies the same package in the graph; the name each dependent imports it by does not.

  • The value is the package that replaces it, written as a dependency is: a repository (github, gitlab, codeberg) with at most one of version, branch, tag and commit, or a path, relative to this pep.toml. It takes no optional, features or default-features; those stay on each dependency.

  • Everywhere, whatever is asked: every package that depends on the source gets the replacement, the project included, whatever version range or branch each asks for. A fork is checked out in the original's folder, .pep/deps/<host>/<owner>/<name>, and a path override's folder is read in its place, its own dependencies included. Imports do not change.

  • Locked: pep.lock records the replacement in the package's override, with the fork's commit (see pep.lock), so --locked and --offline builds stay reproducible, and adding, changing or removing an override changes the lock.

  • Only the project's own: a dependency's [overrides] do not apply to the projects that use it, and pepper package publish refuses a package with any (see publish). In a workspace, only the root's apply, to every member; a member's are ignored, which pepper package warns about.

  • Checked by pepper package: an override that matches no package in the graph is a warning at its key, and a replacement whose [package] name differs from the name pep.lock records for the package it replaces is an error there:

    pep.toml:9:1: error: 'github:someone/geometry' is the package 'geometry', not 'numbers', which it overrides; name a fork or copy of 'numbers'
    9 | "github:other/numbers" = { github = "someone/geometry", tag = "v1.0.0" }
      | ^~~~~~~~~~~~~~~~~~~~~~

  • Needs toolchain 0.11.0: an older toolchain rejects a pep.toml with [overrides] as an unknown table.

[fetch]

[fetch]
hosts = ["codeberg", "github"]
vendor = "vendor"

hostsThe hosts pepper package add owner/name looks a repository up on, in order, when the argument names none; it adds the first that has it["github", "gitlab", "codeberg"]

Builds then read each dependency from <vendor>/<host>/<owner>/<name> instead of .pep/deps, fetch nothing, and fail when a package is missing, at another commit than pep.lock's, or edited. [retract]

A package withdraws its own broken releases, as Go's retract does: each key is a version, or a range as dependencies write it, and its value says why.

[retract]
"1.1.0" = "loses data on Windows"
">=1.2.0, <1.2.3" = "PEP-2026-0001"

A key that is a version names that version alone, not the ^ range a dependency's version = "1.1.0" means; keys are quoted, as TOML reads 1.1.0 unquoted as three nested keys. Release the table in a newer version (a workspace member's newest release by its own tags, read from the member's pep.toml): the [retract] of a package's newest release speaks for every version, so a range no longer picks a retracted one, pepper package outdated flags one pep.lock holds, and update moves off it (see Retracted versions). A key that is neither a version nor a range is an error at the key in the project's own pep.toml (a dependency's retracts nothing, so its dependents still resolve):

pep.toml:8:1: error: '1.x.q' in '[retract]' is not a version or range: ...
  • Needs toolchain 0.11.0: an older toolchain rejects a pep.toml with [retract] as an unknown table, so a package that has one sets minimum_toolchain = "0.11.0" (or later), which pepper package publish checks.

[audit]

[audit]
ignore = ["PEP-2026-0001"]   # its code is never called here
KeyWhat it isDefault
ignoreThe advisories, by id, that pepper package audit reports but does not fail on, with --ignore[]

Only the project's own (in a workspace, its root's) [audit] applies. An older toolchain than 0.11.0 rejects the table.

Errors

A problem in pep.toml is an error located at the key or value to change:

pep.toml:9:1: error: dependency 'io' has the name of the runtime module 'io'; give it another name, which source code then imports
    9 | io = { github = "someone/io" }
      | ^~
  • Two dependencies with the same name (in one table, or in two of [dependencies], [dev-dependencies] and the [target] tables), or a dependency named like a runtime module (io, async), which it would otherwise hide.
  • A [target] condition [Target(...)] would reject.
  • A feature that lists a feature the package lacks, a dep: that names no optional dependency, or a <name>/<feature> whose dependency does not exist; a dependency's features asking for one its package lacks (package 'zlib' has no feature 'smid'), which a build reports once the package is fetched.
  • A dependency name that is not an identifier (fast-json): it is the name import uses.
  • A dependency with no source or two, a repository not written owner/name, or more than one of version, branch, tag and commit; a package with a path, or one that is not an identifier.
  • An [overrides] key that is not a source (github:owner/name), or an override with optional, features or default-features.
  • A table or key pep.toml does not have, or a value of the wrong type.

An import of a dependency that is not on disk says which folder is missing:

main.pep:1:8: error: dependency 'geometry' is not fetched: no /home/you/my_app/.pep/deps/github.com/someone/geometry; run 'pepper package fetch'
    1 | import geometry;
      |        ^~~~~~~~

The language server reads pep.toml the same way, so imports of fetched dependencies resolve in the editor with no -I.
