The Pepper Programming Language

The compiler: pep-build

pep-build compiles a Pepper program into an executable, or into a library for C code to link. pepper build runs it with the same arguments, so everything on this page applies to both spellings:

pepper build main.pep -o main          # the same as: pep-build main.pep -o main

pep-build [OPTIONS] [<entry.pep>]

This page lists every option. pep-build --help prints the same list in short, and pepper help build runs it.

Short options that take no value combine (-gv is -g -v). Options may come before or after the entry file, and every argument after -- is a file. An unknown option is an error, and the compiler exits with status 2 after a short usage message.

Inputs and imports

The entry file

pepper build main.pep

The file that holds main. The compiler finds the files it imports on its own (see Modules and imports), so a program of many files is compiled by naming its entry file alone. Only the first file named is compiled; any others are ignored.

With no file, the compiler builds the project whose pep.toml is in the current folder or the nearest folder above it: its [build] table names the entry file and the output, and the build goes in the project's .pep (see Projects: pep.toml). With no file and no pep.toml, it stops with error: no source files provided, and no pep.toml in <folder> or a folder above it.

cd my_app/src
pepper build              # builds my_app/pep.toml's program into my_app/

An entry file inside a project (under a folder with a pep.toml) imports the project's dependencies, and its [build] table's include folders and link libraries apply to it as well.

Before compiling a program in a project, the compiler fetches whatever pep.lock lists and the project's .pep/deps lacks or holds at another commit, and the Git dependencies that pep.toml, or the pep.toml of a path dependency it reaches, names and pep.lock does not list yet, by running pep-package fetch (beside pep-build, else on the PATH). Without pep-package, it checks the missing commits out with git itself, and asks for pepper package fetch to move a checkout at another commit. A dependency checked out on a branch is left as it is. See The package manager: pep-package.

--locked, --offline, --frozen

These make the fetch reproducible, for CI (see Reproducible builds):

  • --locked (or PEPPER_LOCKED=1) fails when pep.lock is out of date with pep.toml, instead of updating it. A Git dependency pep.toml names that pep.lock does not list is an error before anything is fetched; otherwise the build runs pep-package fetch --locked, even when nothing is missing, so a changed range is caught too.
  • --offline (or PEPPER_OFFLINE=1) fetches nothing over the network: a locked package .pep/deps lacks is an error that names it, and pep-package runs with --offline.
  • --frozen is both.
$ pepper build --offline
--offline, and app/.pep/deps lacks github:someone/geometry 0582024b9cd7; run 'pepper package fetch' without --offline first

-I <dir>

Adds a folder to search for modules imported by name (import geometry; looks for geometry/module.pep). The -I folders are searched in the order given, then a project's [build] include folders, then the runtime's folder. A project's dependencies are found through its pep.toml instead. See Dependencies and search paths.

pepper build tools/pep-fmt/main.pep -o pep-fmt

--import <name>

Loads a module (<name>/module.pep) or a file (<name>.pep), found on the search paths, into every file of the program, the way the standard library's prelude is loaded. Its definitions come ahead of the runtime's, so one that redefines a runtime export wins. Repeat it for more modules. A name that cannot be found is an error that lists the folders searched. See The runtime prelude and --import.

--no-runtime

Compiles without the standard library: the runtime is neither looked for nor loaded, so only the program's own files and what -I reaches are compiled. For testing the compiler; ordinary programs need the runtime (print, String and Array all live there).

Without this option the compiler finds the runtime as Getting started describes, and PEPPER_RUNTIME names its folder outright.

Output

-o <file>

The path of the executable, or with --lib of the library. Without it, the output goes to the current folder, named after the entry file with no extension (main for main.pep); with --lib, the library's usual file name for that stem (libmain.a). Building a project with no file, it is the [build] table's output, else the package's name in the project's folder (libname.a with --lib), with .exe added when building for Windows and the name has no extension. Windows runs only files ending in .exe, so otherwise name the output there: -o main.exe.

With --emit-static, it is the folder the expanded source goes into.

--lib static, --lib shared

Builds a library for C code to link instead of an executable, with a C header beside it that declares the program's [Export]ed functions. No main is needed.

  • --lib static writes an archive: libname.a (name.lib on Windows), holding the objects of the whole program, the runtime's included, with the index of their symbols that linkers search. The compiler writes it itself in the target's format (GNU's for Linux and Android, the BSD format Apple's linkers read for macOS and iOS, the COFF archive for Windows), so no archiver needs to be installed, and building one for another platform needs no system root: nothing is linked. A program linking it also links the libraries the program does, which the header names in a comment (/* Link the static library with: -lm */).
  • --lib shared links a shared library: libname.so, libname.dylib on macOS, name.dll (and its import library name.lib) on Windows. Its soname is its file name; on macOS and iOS its install name is @rpath/<file name>, so a program that links it finds it on its run path. Linking one for another platform needs its system root, as an executable does (--sysroot).

The header goes beside the library, named for it without the lib prefix (libname.a has name.h). A library that exports nothing is built with a warning. See Calling Pepper from C.

--test

Builds the entry file's tests into a test program, which pep-test runs. A build without it leaves every [Test] function out. With it:

  • the [Test] functions are kept, and the build option TEST is defined (as by -D TEST), for code only tests use ([BuildOption("TEST")]);
  • the runtime's testing module is loaded into every file (as by --import testing);
  • the entry file's main is replaced by one that answers --list (one line per test: name, file:line, returns or panics, and the text a [ShouldPanic] panic must contain, separated by tabs) and --run NAME [--timeout SECONDS] (run that test; a test still running after the timeout ends the program with exit status 124).

Only the entry file's [Test] functions become tests. Given several files of one folder (pep-build --test a_test.pep b_test.pep), it builds the tests of them all into one program: a generated entry file in that folder (_pep_test_main.pep, never written to disk) imports each file and registers its tests, and each file keeps the scope it has in any program. --list then gives each test's own file, and --run also takes FILE::NAME, as --list spells the file, to tell apart tests of one name in two files. It cannot be combined with --lib. See Unit tests.

--build <dir>

The folder for intermediate files: the program's objects and, with --emit-llvm, its IR. The default is .pep/build in the current folder, or in the project's folder when building a project with no file.

--emit-llvm

Writes the whole program's LLVM IR to <build>/<name>.ll (.pep/build/main.ll for main.pep), optimized at the -O level, and stops there: nothing is linked and no executable is written.

pepper build main.pep -O --emit-llvm      # .pep/build/main.ll

--emit-static, --emit-static=keep

Writes a copy of the program's source with each static block replaced by the code it emits, like a C compiler's -E, and stops there: nothing is compiled to code. Use it to see what a reflection loop, a serializer or a library's block does to the program (see Seeing what a static block emits).

pepper build main.pep --emit-static              # main.static/main.pep
pepper build main.pep --emit-static -o expanded  # expanded/main.pep
pepper build expanded/main.pep -o main           # the same program
  • Every file of the program in the entry file's folder (and the folders under it) is written into the output folder at the same relative path, so the folder builds as a whole program; files with no block are copied unchanged. The runtime and libraries found elsewhere are not copied. The originals are never overwritten.
  • The folder is -o's, else <entry stem>.static in the current folder.
  • Each expansion is a { ... } block between # static (out, value) expanded from main.pep:12:5 and # end static. --emit-static=keep also keeps the block as written, as # comments above it; --emit-static=expand is the default, the same as --emit-static.
  • A block in a generic function expands once per specialization. The generic function stays as written, and after it comes a concrete override for each type the program uses it with (describe<Point>(value: Point)), its blocks expanded, so the copy still builds into the same program. A block in a method of a generic struct, or in a generic method, stays, with each specialization's expansion above it as # comments.
  • When pep-fmt is next to the compiler or on PATH, it formats the copies, wrapping long lines.
  • Errors a block reports stop it, as they stop a build. Errors in the code a block emits are found when the copy is built, at the copy's line.

--emit-ast

Parses the entry file only and prints its syntax tree to standard output, instead of compiling. Imports are not followed and nothing is checked.

--emit-ast and --emit-ast=text print the tree as source-like text. --emit-ast=json prints it as one line of JSON: each node an object with its fields in declaration order, each enum case an object with the case's name as its one key, and each span {"start": ..., "end": ...} in bytes. The compiler's parser written in Pepper (tools/compiler) prints the same JSON, and its test compares the two over every source file in the repository.

--emit-linked

Loads the program as a build does (the entry file, every file its imports reach, and the runtime), links it, and prints it to standard output as one line of JSON instead of compiling. Nothing after linking is checked, so a program with type errors prints too; a file that cannot be read or parsed stops it, as it stops a build.

The JSON is an object with three keys:

  • files: every file in load order (the entry file first), each with its name as the program reached it, its namespace, its module_root folder (or null), whether it is part of the prelude (the runtime and --import files) or a prelude_part (another file of a forced module), the index of the file each of its imports names (or null when one did not resolve), which of them are folder_imports (a local import of a module folder), and its module, the syntax tree as --emit-ast=json prints it after linking renamed what the file imports and gave its private declarations their program-wide names (helper@io/file).
  • errors: the linking errors, by file and position, each with its file index, span, message, whether it is an unresolved import, and its note ([span, message], or null).
  • overload_unions: each overload set that spans files, by name, with its functions grouped by module.

-I, --import, --no-runtime, -D and --test apply as for a build. The compiler's linker written in Pepper (tools/compiler) prints the same JSON, and its test compares the two.

--emit-checked

Loads and links the program as --emit-linked does, runs the checks that come before type checking, and prints what they report instead of compiling: the errors, rendered as a build reports them, then the warnings. The errors are the linking errors; when there are none, a [__BuiltIn] declaration outside the runtime; when there is none of those either, every use of a declaration another file keeps private or this file does not import. The warnings are deprecated syntax, comparisons with a build option -D does not define, and uses of declarations marked [Deprecated]. A program with neither prints an empty line.

-I, --import, --no-runtime, -D and --test apply as for a build. The compiler written in Pepper (tools/compiler) prints the same text, and its test compares the two.

--emit-model

Loads, links and checks the program as --emit-checked does, builds the sema model of each file and joins them, and prints the model as one line of JSON instead of compiling: what the sema builder made of the syntax trees (for, with, match, ?, destructuring, ranges, collection literals and properties lowered), before any sema pass runs. Object keys are sorted, and so are the sets (private_functions and the extension_scopes). When the checks or the builder reject the program, it prints the rendered error and fails.

-I, --import, --no-runtime, -D and --test apply as for a build. The compiler written in Pepper (tools/compiler) prints the same JSON, and its test compares the two.

--emit-model-step <N>

With --emit-model, runs the first N steps of the sema passes before printing the model. A step is one pass run, in the order the compiler runs them (platform filters first, then [Equatable], closure lifting and the rest); --emit-steps lists them. When a step rejects the program, it prints the rendered error and fails. The compiler written in Pepper runs the same steps, and its test compares the model after each.

--emit-steps

Loads, links, checks and builds the program as --emit-model does, runs every sema pass, and prints the name of each step run, one per line, instead of compiling: the numbering --emit-model-step uses.

Optimization and code generation

-O, -O<level>

The optimization level: -O0 (no optimization, the default), -O1, -O2 or -O3. -O alone is -O2, and it does not take the next argument as its level, so pepper build -O main.pep works. Each level runs the pipeline clang runs at that level. Without the option, the level is PEPPER_OPT_LEVEL (0 to 3) when that is set and not empty.

At -O0 a panic prints a backtrace after its message; at any other level it prints the message alone, unless the program runs with PEPPER_BACKTRACE=1 (see Backtraces on panic).

--lto=full, --lto=off

Link-time optimization. With --lto=full, once every file is compiled the whole program is optimized again as one module, so a call into another file (the runtime included) can be inlined. --lto=off optimizes each file alone, which links sooner. The default is off: full optimizes the whole program again on every build, an edit's too, so it suits a release build. --lto=full at -O0 is an error that asks for -O.

With it, each file is optimized by LLVM's pre-link pipeline and kept as bitcode (in the build cache, as an object is), then the compiler links them into one module, makes every symbol internal but main and the C exports of [Export] functions, runs LLVM's link-time pipeline over the whole program, and writes its objects, one per logical CPU in parallel, which link as usual. No linker plugin is involved, so it works on every target. It applies to a library too (--lib).

-march=<cpu>, -mcpu=<cpu>, -mtune=<cpu>, -m<feature>, -mno-<feature>

The -m options choose the CPU the code is generated for, with clang's names and meanings (-m <option>, with a space, is the same as -m<option>):

  • On x86-64, -march=<cpu> names the CPU: x86-64-v3, znver4, or native for the machine compiling.
  • On AArch64, -mcpu=<cpu> names the CPU (apple-m2, native) and -march=<arch> the architecture (armv8.2-a+crypto).
  • -mtune=<cpu> changes only how instructions are scheduled.
  • -m<feature> adds a CPU feature (-mavx2), and -mno-<feature> removes one (-mno-avx2).

Without them the program runs on any machine of its kind: clang's default CPU for the target (x86-64; apple-m1 on Apple arm64). An option the target's architecture does not take is an error worded as clang words it: -mcpu= on x86-64 (unsupported option '-mcpu=' for target ...; use '-march' or '-mtune'), -march= on WebAssembly, an AArch64 -march= that is not armv<version>-a (invalid arch name), native for another platform's target, or an empty value. A CPU or feature name LLVM does not know is passed on, and LLVM warns about it. The last of each option wins; the features come after those the CPU implies. The chosen CPU, its features and its tuning are part of the build cache's key.

-g, --emit-debug

Emits debug info for gdb, lldb, Visual Studio and WinDbg: DWARF 4 in the executable on Linux and macOS, and CodeView on Windows, where the linker writes <output>.pdb beside the executable. On macOS it also runs dsymutil to write <output>.dSYM beside the executable, when the program is built for the Mac it runs on. It works with -O. See Debugging.

A Windows build without -g also writes <output>.pdb, holding only the program's function names, which is where backtraces read them.

Every link leaves out the functions and data nothing uses, except a Windows build with -g: its linker keeps them all, so the program is larger.

--debug-static=source, --debug-static=expanded

With -g, chooses which source the debugger shows for the code a static block emits (see Stepping through a static block):

  • source, the default: the block as written. Stepping stops on a compile-time loop's header once per pass, then on its body.
  • expanded: a copy of each file with its blocks expanded, as --emit-static writes it (unformatted), saved beside the output as <name>.static.pep (main.static.pep for main.pep; a file in a folder under the entry's keeps that folder). The debugger steps through the expanded statements, sum = sum + p.y;, and a breakpoint on one of its lines stops in that pass. The rest of the program stays in its own files. A build with it does not use the build cache.
pepper build -g --debug-static=expanded main.pep -o main   # main, main.static.pep

--frame-pointers

Keeps the frame pointer in every function, even when optimizing, as clang's -fno-omit-frame-pointer does. A sampling profiler then walks the stack of each sample by following frame pointers, which is fast and finds every frame of Pepper code; without them, optimized code reuses the register and a profiler loses the callers of whatever was running. It costs a register and a few instructions per call. pep-profile builds with it, -O and -g. It is part of the build cache's key.

Targets and cross-compiling

--target <triple>

Compiles for another platform, named by an LLVM target triple: x86_64-unknown-linux-gnu, aarch64-unknown-linux-gnu, aarch64-apple-darwin, x86_64-apple-darwin, x86_64-pc-windows-msvc, aarch64-pc-windows-msvc, wasm32-wasip1, aarch64-apple-ios, aarch64-apple-ios-simulator, x86_64-apple-ios-simulator, aarch64-linux-android or x86_64-linux-android, with a version allowed where clang allows one (arm64-apple-macosx14.0, aarch64-apple-ios17.0, aarch64-linux-android33). An unsupported triple is an error that lists the supported ones. [Target(...)] selects code for the target. The default is the machine the compiler runs on. See Cross-compiling and iOS and Android.

--sysroot <dir>

The folder that holds the target's system headers and libraries, passed to the link driver, for linking with --target. Without it, the folder named by PEPPER_SYSROOT_<TRIPLE> when that is set: the triple in capitals, with _ for each character that is not a letter or digit (PEPPER_SYSROOT_AARCH64_APPLE_DARWIN for aarch64-apple-darwin). An iOS or Android triple's variable leaves out the OS version (PEPPER_SYSROOT_AARCH64_APPLE_IOS_SIMULATOR for aarch64-apple-ios17.0-simulator). For iOS it is an iOS SDK, which on a Mac defaults to the one xcrun names; for Android it is the NDK (see ANDROID_NDK_HOME below).

Linking

-l <lib>

Links a C library, as -l does for clang: -l m links libm. Repeat it for more libraries. A project's [build] table adds its link libraries. A program's [Link] attributes name libraries from the source instead. See Linking.

-L <dir>

Adds a folder the linker searches for libraries. Folders given with -L come first, then those of [Link(path = ...)], then those in PEPPER_LIBRARY_PATH (separated like PATH: :, or ; on Windows). See Library search directories.

pepper build main.pep -L libs -l foo        # links libs/libfoo

--MSVC

Reserved for linking with Microsoft's linker. It is not ported, so it is an error on every platform; Windows executables link with clang and lld.

The link driver is clang. When PEPPER_LLVM_PREFIX, else LLVM_SYS_<major>1_PREFIX (for the LLVM the compiler was built with, such as LLVM_SYS_201_PREFIX for LLVM 20), names an LLVM install, its bin/clang and lld are used; else a clang beside pep-build, then one on the PATH (clang, then clang-<major>), then one where LLVM's packages install it off the PATH. With none, the link fails with an error naming what to install. Installing Pepper lists the folders searched.

Build options

-D <name>, -D <name>=<value>

Defines a build option. A bare name is name=1, as in C. [BuildOption] and [Target(BuildOption(...))] select code by it, and static blocks read it with reflect.build_option. Repeat it for more options; of two that name the same option, the later wins. A name must be an identifier (-D 2FAST is an error). Build options are part of the build cache's key. See Build options.

pepper build main.pep -D USE_ZLIB -D LOG_LEVEL=2

Runtime checks

--no-runtime-checks=<list>

Integer overflow, division by zero, an oversized shift, an index out of range and a call through a null reference panic at run time, at every optimization level. This option removes the kinds of check it names, as a comma-separated list, from an optimized build:

KindWhat is no longer checkedWhat happens instead
overflowInteger overflowArithmetic wraps
divideDivision by zero and MIN / -1Undefined behavior
shiftA shift count of at least the widthThe count is masked
boundsArray and string indexingUndefined behavior
nullCalls and matches through a null referenceUndefined behavior
allAll of the above

Removing bounds or null gives up memory safety. At -O0 the option has no effect and prints warning: '--no-runtime-checks' has no effect at -O0. To remove checks from one function at every level, mark it [Unsafe("overflow,bounds")] instead. See Integer overflow.

pepper build -O main.pep --no-runtime-checks=overflow,shift

The build cache

The compiler checks a program one compilation unit at a time: a file, or the files that import each other in a cycle, with the runtime as one. The build cache keeps each compilation unit's checked result and object, and each file's own object: a file whose sources, and whose imports' declarations, did not change is not compiled or checked again. PEPC_COMPILATION_UNIT_JOBS sets how many compilation units are checked at once (one per processor by default; PEPC_LAYER_JOBS, its old name, still works). The optimization level, link-time optimization, debug info, CPU, removed runtime checks and build options are part of each object's key. Deleting the cache folder is always safe.

--no-cache

Compiles every file without reading or writing the build cache.

--cache <dir>

Keeps the build cache in <dir>. Without it, the folder named by PEPPER_CACHE_DIR when that is set and not empty, else .pep/cache in the current folder, or in the project's folder when building a project with no file.

No path in the cache adds more than 72 characters to <dir>'s, so a project folder can sit deep without the cache passing Windows' 260-character path limit. The folder holds one subfolder per layout version (v3); a build ignores the others, so an old version's folder can be deleted.

--verify-cache, --no-verify-cache

--verify-cache checks the cache, for testing the compiler: every file the cache would reuse is compiled anyway, and the build fails if its code differs from the cached object's, or if skipping the reused files' bodies changes another file's code. Setting PEPPER_CACHE_VERIFY to anything but empty or 0 does the same. --no-verify-cache turns it off even when PEPPER_CACHE_VERIFY is set. The two options cannot be combined. It builds the program a second time, with an empty cache of its own in the build folder, and compares each object that build makes with the one the cache holds under the same key, so a check costs about a build from scratch. A failure names the cached objects that differ.

Tracing and diagnostics

-T <channel>, --Tall

-T turns on a trace channel, which prints to standard error. Repeat it for more channels; --Tall turns on every one.

  • -T time prints how long each stage of the compile took (time: check and build 470.763 ms).
  • -T passes prints how long each pass of the checker took, summed over its runs, slowest first (pass: 3116.171 ms 16x resolve_implicit_types), the passes run checking the runtime and each module included.
  • -T cache prints how the build cache supplied each object: hit (its sources, and its imports' declarations, are unchanged), hit (same code) (compiled again, to the same code), or miss; and whether linking was skipped.

Any other channel name is accepted and ignored.

-v, --verbose

Accepted for compatibility with other compilers; it prints nothing more yet.

Errors and warnings are printed like clang's, colored when standard error is a terminal; set NO_COLOR to turn color off. See Compiler errors.

Internal options

A build starts copies of the compiler to work side by side, and gives them these options; they are listed so a failed child's command line can be rerun by hand (the build prints it).

  • --compile-part <dir> --part <N>=<object>... compiles parts of the program a build split into <dir>: each --part names a part by its number and the object to write it to. Nothing else is read.
  • --compilation-unit-worker <dir>, after the build's own arguments, checks the compilation units the build passes through <dir> and compiles their objects.

Help and version

  • -h, --help prints every option with a line of description.
  • -V, --version prints pep-build and its version.

PEPPER_RUNTIMEThe folder holding the standard library; nothing else is searched--no-runtime skips the runtime
PEPPER_OPT_LEVELThe optimization level (0 to 3) without -O; also the level the test suite's JIT uses-O<level>
PEPPER_LIBRARY_PATHMore folders the linker searches, after -L and [Link(path = ...)]-L comes first
PEPPER_SYSROOT_<TRIPLE>The system libraries for linking with --target <triple>--sysroot
ANDROID_NDK_HOME, ANDROID_NDK_ROOTThe Android NDK for linking with an Android --target, when neither --sysroot nor PEPPER_SYSROOT_<TRIPLE> names one--sysroot
ANDROID_HOME, ANDROID_SDK_ROOTThe Android SDK, whose newest ndk/<version> links an Android --target when nothing above names an NDK--sysroot
WASI_SDK_PATHThe wasi-sdk for linking with --target wasm32-wasip1, when neither --sysroot nor PEPPER_SYSROOT_WASM32_WASIP1 names one--sysroot
PEPPER_CACHE_DIRThe build cache folder--cache, --no-cache
PEPPER_CACHE_VERIFYAnything but empty or 0 checks the build cache--no-verify-cache
PEPPER_LOCKEDAnything but empty or 0: the same as --locked
PEPPER_OFFLINEAnything but empty or 0: the same as --offline
PEPPER_LLVM_PREFIXThe LLVM install whose clang and lld link the program
LLVM_SYS_<major>1_PREFIXThe same, when PEPPER_LLVM_PREFIX is not set (LLVM_SYS_201_PREFIX for LLVM 20)
PEPPER_PACKAGE_GITHUB_URL, PEPPER_PACKAGE_GITLAB_URL, PEPPER_PACKAGE_CODEBERG_URLWhere a build fetching a project's locked dependencies clones that host's repositories from, when pep-package is not installed (see pep-package)
NO_COLORSet and not empty: errors are not colored

Exit status

pep-build exits with 0 when the program compiled, 1 when it did not (the errors are on standard error), and 2 for a command line it cannot parse. A crash of the compiler itself exits with 101 after printing what went wrong; please report it.
