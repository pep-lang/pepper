The Pepper Programming Language

Unit tests

A unit test is a function marked [Test]: it takes no parameters, returns nothing, and passes when it returns. It checks what the code under test does with expect_equal and the other expect_* functions, which are in the prelude, so a test file needs no import:

# Counts the words in `text`: the runs of characters between spaces.
word_count(text: String): ulong {
    ulong count = 0;
    for (var word in text.split(" ")) {
        if (!word.is_empty) {
            count += 1;
        }
    }
    return count;
}

[Test]
counts_the_words() {
    expect_equal(word_count("salt and pepper"), 3);
    expect_equal(word_count("  spaced   out "), 2);
}

[Test]
an_empty_string_has_no_words() {
    expect_equal(word_count(""), 0);
    expect_true(word_count(" ") == 0);
}

[Test]
[ShouldPanic("out of bounds")]
reading_past_the_last_word_panics() {
    var words = "salt pepper".split(" ");
    var third = words[2];
}

# A normal build leaves the tests out and runs this.
main(): int {
    print(word_count("salt and pepper"));
    return 0;
}

pepper test (the pep-test tool) builds the tests and runs them:

$ pepper test words_test.pep
running 3 tests
test counts_the_words ... ok (4 ms)
test an_empty_string_has_no_words ... ok (3 ms)
test reading_past_the_last_word_panics ... ok (5 ms)
3 passed, 0 failed

Given a folder, or nothing (the current folder), it runs every test in the .pep files under it. Its exit status is 0 only when every test passes.

Checks

Each check panics when it fails, as assert does, and reports what it compared at the line of the call, so a failing test says where and why:

words_test.pep:14:5: panic: expect_equal failed
  actual:   2
  expected: 3
CheckFails when
expect_equal(actual, expected)actual == expected is false; prints both
expect_not_equal(actual, unexpected)the two are equal; prints the value
expect_true(condition)condition is false
expect_false(condition)condition is true

expect_equal and expect_not_equal take two values of one type that has == and a text form (see to_string in String interpolation). assert and panic fail a test too: any panic does.

Tests that should panic

[ShouldPanic] turns a test around: it passes only when it panics. With a message, [ShouldPanic("out of bounds")], the panic's message must also contain that text, so a test does not pass on some other panic. A [ShouldPanic] test that returns fails.

How tests run

Each test runs in a child process of its own, so a panic, a crash or a test that never ends fails only that test, and the others carry on. Tests run in parallel, one per logical CPU (--jobs 1 runs them one at a time, in order), and a test still running after 60 seconds fails (--timeout changes the limit). Tests share no state: each process starts fresh.

A test also fails when it leaks: the test program counts the live allocations before and after the test, and a test that returns with more (or fewer) than it started with fails, saying how many it left behind:

error: test 'counts_the_words' left 1 allocation behind

What a program makes once and keeps until it ends, such as a global made on first use, is not a leak. A test that is first to use it wraps that use in keep_for_the_program, which runs it and leaves what it allocates out of the count:

keep_for_the_program(() => {
    tls.TlsConnector.create();   # loads the TLS library, which stays loaded
});

There is no setup or teardown: a fixture is a plain function that a test calls, and what it makes is released when the test's scope ends, as everywhere else. A struct whose destructor cleans up makes a fixture that tears itself down. TempFolder, which every test file can use, is one: a fresh folder under the system's temporary folder, removed with what is in it when the test returns:

import io;

[Test]
writes_a_file() {
    var folder = TempFolder("writes_a_file");
    var path = folder.path.join("notes.txt");
    io.File.write_text(path, "hello");
    expect_equal(io.File.read_to_string(path).value(), "hello");
}

Where tests live

A test can sit beside the code it tests, where it can call the file's private functions, as above. Or tests can live in their own files, such as a module's tests/ folder, where they import the module and see its public API; pepper test -I <dir> adds the folder that holds the module to the import path:

geometry/
  module.pep
  shapes.pep
  tests/
    area_test.pep      # import geometry; [Test] functions

pepper test -I . geometry/tests

pep-test looks at each .pep file under the folders it is given and builds those with a line that starts with [Test]. The test files of one folder build into one test program, whose tests are their [Test] functions. Folders whose names start with . are skipped.

Each file keeps the scope it has in any program. A folder inside a module (a test/ folder below its module.pep, say) holds files of that module, which see each other's names: two of them that declare the same helper, or the same test name, collide (redefinition of 'helper'). Mark such a declaration private in each file, or rename it. Test files outside a module see only each other's exports, so their names never collide.

Test builds

A normal build leaves [Test] functions out, so they cost nothing, and a file of tests can keep a main of its own. pep-build --test, which pep-test uses, builds the test program instead:

  • it keeps the [Test] functions and defines the build option TEST, so code only the tests use (a fixture that would be unused otherwise) can be marked [BuildOption("TEST")];
  • it replaces the entry file's main with one that answers --list (each test, one per line) and --run NAME (run one test), which is how pep-test drives it. Given several files of one folder, it builds the tests of them all into one program, and --run FILE::NAME tells apart two tests of one name.

A [Test] function that platform selection leaves out ([Target(OS(Linux))] in a build for Windows) is not part of the test program: --list does not show it.

A [Test] function that takes parameters, returns a value or is generic is an error, as are [Test] on a method and [ShouldPanic] without [Test]:

main.pep:2:8: error: test 'checks' must take no parameters
    2 | checks(x: int) {}
      |        ^

The language server checks a file that declares a [Test] function as a test build does: with the build option TEST and testing loaded, so errors, hover and go-to-definition work inside test bodies with no setting (see pep-lsp).

Tests that compare a program's printed output with an expected file are not supported yet.
