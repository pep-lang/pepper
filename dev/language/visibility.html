The Pepper Programming Language

Visibility

Visibility decides which declarations other files may use. Every top-level declaration is private to the file that declares it unless you mark it with export. This lets a file keep its helpers to itself and offer a small, clear surface to the files that import it.

Exporting declarations

Put export in front of a declaration to make it usable from other files that import this one (see Modules and imports for how to import). You can export every kind of top-level declaration:

  • functions, including extern declarations of C functions
  • structs
  • type aliases
  • traits
  • extensions
  • module-scope variables, which are always const and thread-safe (see Module-scope variables)

Here is a library file with a mix of exported and private declarations, and a program that uses it:

# Everything here is private to lib.pep unless it says `export`.

export struct Point {
    var x: int;
    var y: int;
}

export type Points = Point[];

export trait Describe {
    describe(): String;
}

# A module-scope variable is `const` and thread-safe: change it through
# an Atomic.
export const points_made = Atomic<int>(0);

export origin(): Point {
    return make(0, 0);
}

export at(x: int, y: int): Point {
    return make(x, y);
}

# Private: only lib.pep can call make().
make(x: int, y: int): Point {
    var p = Point();
    p.x = x;
    p.y = y;
    points_made.fetch_add(1);
    return p;
}

# An exported extension: its methods are usable wherever Point is.
export extend Point with Describe {
    describe(): String {
        return "point";
    }
}

# A private extension: only lib.pep can call p.norm().
extend Point {
    norm(): int {
        return x * x + y * y;
    }
}

export norm_of(p: Point): int {
    return p.norm();
}

# `export` goes after attributes, directly before the declaration.
[Target(OS(Windows))] export platform_name(): String { return "Windows"; }
[Target(!OS(Windows))] export platform_name(): String { return "not Windows"; }

import "lib";

main(): int {
    var p = at(3, 4);             # exported function
    var o: Point = origin();      # exported struct, used as a type
    Points list = Points();       # exported type alias
    list.append(p);
    list.append(o);

    assert(p.x == 3, "fields are as visible as their struct");
    assert(p.describe() == "point", "method from an exported extension");
    assert(norm_of(p) == 25, "an exported function may use private helpers");
    assert(points_made.load() == 2, "exported module variable");
    assert(platform_name().length() > 0, "exported, with an attribute");
    return 0;
}

main.pep can call at, origin, and norm_of, use Point and Points as types, and read the counter in points_made, an exported const Atomic<int>. It cannot use make or call p.norm(). Trying to is an error that tells you how to fix it:

import "lib";

main(): int {
    var q = make(1, 2);
    return 0;
}

main.pep:4:13: error: 'make' is private to lib.pep; declare it with 'export' to use it from another file
    4 |     var q = make(1, 2);
      |             ^~~~
lib.pep:27:1: note: declared here
   27 | make(x: int, y: int): Point {
      | ^~~~

The same applies to private structs, type aliases, traits, and variables: naming one from another file reports 'name' is private to file.pep.

Members of structs and extensions

Fields and methods declared inside a struct’s body are reached through the struct, so they share the struct’s visibility: if you can use the struct, you can use all of its members.

Methods added by an extension share the extension’s visibility instead. In the example, norm() is added by a private extension, so only lib.pep can call it, even though Point itself is exported:

main.pep:4:14: error: 'norm' is declared in a private extension in lib.pep; declare the extension with 'export' to use it from another file
    4 |     return p.norm();
      |              ^~~~
lib.pep:42:5: note: declared here
   42 |     norm(): int {
      |     ^~~~

An exported extension’s methods are usable where its file is imported, not everywhere: a file sees the extensions it declares itself, the exported extensions of the files it imports, the exported extensions of every file of a module it imports (import geo reaches geo/ext.pep’s), and those of the runtime, which every file sees. Here measure.pep adds manhattan() to Point, and main.pep imports it to call it:

import "point";

# An exported extension: files that import measure.pep can call these.
export extend Point {
    manhattan(): int {
        return abs(x) + abs(y);
    }
}

# Private to this file.
abs(v: int): int {
    if (v < 0) { return -v; }
    return v;
}

import "point";
import "measure";                      # brings Point's manhattan() into scope

main(): int {
    var p = Point();
    p.x = 3;
    p.y = -4;
    assert(p.manhattan() == 7, "an extension from an imported file");
    return 0;
}

Without import "measure";, the call is an error. If no file of the program imports measure.pep, the method does not exist at all (no member named 'manhattan' in 'Point'); if another file does, the error says which import is missing:

main.pep:8:14: error: 'manhattan' is declared in an extension in measure.pep, which this file does not import; add an import for it
    8 |     assert(p.manhattan() == 7, "an extension from an imported file");
      |              ^~~~~~~~~
measure.pep:5:5: note: declared here
    5 |     manhattan(): int {
      |     ^~~~~~~~~

Two kinds of call are checked where they take effect rather than here:

  • A method of a trait you can see (s.area() where area is a method of a trait Shape you declare, import, or get from the standard library): the call may go through a value of that trait, which works whatever file declares the conformance. A file can return a Shape whose struct and conformance stay private, and callers still call area on it.
  • A call on a receiver whose type is not known in this file: this.m() in a trait’s default method, or x.m() (or x.f().m()) where x is a parameter typed by a type parameter, the function’s or its struct’s (measure<X>(x: X)). Such a call resolves where the generic is used, with that file’s imports.

When the extension is in a file of another module, the error names the module to import instead (import its module 'geo'), since a file of another module is reached only through its module.

Inside a struct’s methods (and a trait’s default methods), a bare call to a name that an extension you cannot see adds as a method is an error too, rather than a call to the top-level function of that name: the compiler would otherwise bind it to the method. Rename one of them, or import the extension’s file if the method is what you meant. That import may point back at a file that imports this one (a struct’s file importing the file that extends it); such cycles are allowed.

Extending a struct does not make a private struct visible to other files.

Visibility is checked before types are known, so members are matched by name: a call x.m() is accepted if any struct body visible to the file (its own, or exported) or any extension visible to it, as above, declares a member named m.

Where export goes

export goes directly before the declaration’s keyword or name, after any attributes:

[Target(OS(Windows))] export platform_name(): String { return "Windows"; }

Writing it before the attributes is a parse error:

main.pep:2:8: error: unexpected '['
    2 | export [Target(OS(Windows))] f(): int { return 1; }
      |        ^

export controls visibility between Pepper files only. Making a function callable from C with C linkage is a separate matter, handled by the [Export] attribute described in Calling C.

The runtime’s exports

The runtime’s public surface (String, Array, HashMap, HashSet, Atomic, Result, Error, hash, assert, panic, and the rest of the standard library reference) is exported the same way, and is visible in every file without an import. The runtime’s own helpers are private, so calling one, such as the integer formatter dec, reports 'dec' is private to followed by the path of the runtime’s internals.pep.

Each file has its own namespace

A private declaration belongs to its file alone, so two files may each declare a private name without clashing. Here main.pep and lib.pep each have their own Counter and make, and each file’s code reaches its own:

# lib.pep's private helpers: no other file can see them, and no other
# file's names can clash with them.
struct Counter { var n: int; }

make(): Counter {
    var c = Counter();
    c.n = 10;
    return c;
}

export lib_total(): int {
    return make().n;
}

import "lib";

# main.pep has its own private Counter and make(), unrelated to lib.pep's.
struct Counter { var n: int; var step: int; }

make(): Counter {
    var c = Counter();
    c.n = 1;
    c.step = 2;
    return c;
}

main(): int {
    var c = make();                    # main.pep's make()
    assert(c.n + c.step == 3, "main's own Counter");
    assert(lib_total() == 10, "lib's make() is its own");
    return 0;
}

This holds across modules too: two modules may each have a util.pep with a private helper. Files are told apart by their path inside their module (io/file.pep), not by their file name alone.

Exported names are different: they share one namespace across the whole program, because importers reach them by name. Two files may not export the same name, even from modules reached through different qualifiers: exported 'f' is also declared in b/module.pep. A private name may repeat an exported one from another file; in the file that declares it, the file’s own declaration is the one that name refers to.

A few kinds of declaration are not private in this sense:

  • extern declarations name a C function, which is the same function in every file. Several files may declare the same extern.
  • Concrete overrides of a generic function, such as hash<int> alongside hash<T>, take the generic function’s name: they replace its version for those types wherever it is called. So each override may be declared in only one file (override 'hash<int>' is also declared in b.pep), and overriding one the runtime already provides, such as hash<String>, is also an error. An override must be for a generic function you can see: overriding another file’s private generic function reports that it is private. An override may be for a struct, such as hash<Point> (see Generics).
  • Declarations that a [Target(...)] attribute drops for the platform being compiled (see Platform selection) are never compiled. This is why the first lib.pep above can declare platform_name twice.
