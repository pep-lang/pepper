The Pepper Programming Language

Backtraces and the debugger

The debug module walks the call stack and talks to a debugger. Bring it in with import debug.

FunctionDoes
debug.capture()Records the call stack as a Backtrace: the return address of each call, innermost first.
trace.frames()Resolves the addresses to StackFrames: function, file, line, column, address and inlined.
debug.print_backtrace()Writes the current stack to standard error, as a panic does.
debug.output(text)Writes to the platform's debugger channel.
debug.is_debugger_attached()Whether a debugger is attached.
debug.breakpoint()Stops in the debugger, as a breakpoint on that line would.
# Capturing the call stack and resolving it to functions and lines.
import debug;

struct Parser {
    var depth: int;

    construct() {
        depth = 0;
    }

    # Records where it was called from, as an error report might.
    where(): debug.Backtrace {
        return debug.capture();
    }
}

main(): int {
    var parser = Parser();
    var trace = parser.where();
    var frames = trace.frames();
    for (var frame in frames) {
        print(frame.to_string());
    }
    # The outermost frame is main. (With -O and no -g, `where` is inlined
    # into main and has no frame of its own; WebAssembly cannot walk its
    # stack, so there a backtrace is empty.)
    if (frames.count > 0) {
        assert(frames[frames.count - 1].function == "main", "the outermost call");
    }
    debug.output("done");
    return 0;
}

Built with -g on Linux or macOS, this prints:

Parser.where at debug-backtrace.pep:13:16
main at debug-backtrace.pep:19:24
done

The two frames go to standard output. done goes to the debugger channel: standard error on Linux and macOS, and on Windows only a debugger's output window, so a console there shows just the frames. A frame names its file as the build was given it (pepper build D:\work\debug-backtrace.pep prints that full path), and on Windows it has no column (debug-backtrace.pep:13).

Built with -g -O2, the optimizer inlines where into main, and the backtrace still shows it, marked as inlined:

Parser.where at debug-backtrace.pep:13:16 (inlined)
main at debug-backtrace.pep:19:24
done

Capturing is cheap; resolving is not

capture() only records addresses, so a program can capture a stack whenever it might want to report one later, such as when it creates an error value. The work happens in frames() and to_string(), which read the program's symbol table and line table each time they are called.

A function name needs the program's symbol table, which every build keeps unless the executable is stripped. A file, line and column need the debug info a -g build carries:

WindowsDbgHelp, from the .pdb every build writes beside the executableDbgHelp, from the .pdb of a -g build (no columns)
WASInonenone

A WebAssembly program cannot walk its own stack, so on WASI a backtrace is empty.

Inlined calls

A function the optimizer inlined into its caller has no frame of its own on the stack. In a -g build, frames() puts it back: it expands each address into the chain of inlined calls it is inside, as addr2line -i and debuggers do, with one StackFrame per call, innermost first. Each of these frames has inlined set and is at the line of its own call, and the frame after them, which is not inlined, is the real one. All of them share its address. Linux and macOS read the inlined calls from the DWARF debug info, and Windows asks DbgHelp. On Windows an inlined call to a generic function is named without its type arguments (helper, not helper<int>), since the .pdb records inlined calls that way.

Without -g there is no record of what was inlined, so an optimized build's backtrace shows only the real frames, each named after the function the code was inlined into.

Which frames are left out

frames() leaves out, at the top of the stack, the frames of capture itself and of the runtime's panic code, and the runtime's operator methods a panic came through: a panic in a[i] starts at the line with a[i], not in Array<int>.__index_get. It also leaves out the C runtime's frames below main. frames(full = true) keeps them all.

Backtraces on panic

A panic prints the stack after its message in a build without -O:

main.pep:3:9: panic: index out of range
backtrace:
  0: inner at main.pep:3:9
  1: main at main.pep:8:12

An optimized build prints the message alone. The PEPPER_BACKTRACE environment variable overrides the build: PEPPER_BACKTRACE=1 prints a backtrace in any build, PEPPER_BACKTRACE=full also prints the frames frames() leaves out, and PEPPER_BACKTRACE=0 never prints one. Without -g, each frame shows its function but no file or line.

Only the first panic in a process prints a backtrace. If a second thread panics at the same time, it prints just its message.

The debugger channel

debug.output(text) writes a line where a debugger shows it:

  • Windows: OutputDebugStringW. Visual Studio's Output window and WinDbg show it, and so does DebugView when no debugger is attached. It goes nowhere else.
  • Linux, macOS and WASI: standard error. These systems have no separate channel, and debuggers show the program's own output.

debug.is_debugger_attached() reads TracerPid in /proc/self/status on Linux, P_TRACED on macOS, and IsDebuggerPresent on Windows. It is always false on WASI.

debug.breakpoint() executes the processor's debug trap. A debugger stops there and can continue the program. With no debugger attached, the trap ends the program, so guard it:

if (debug.is_debugger_attached()) {
    debug.breakpoint();
}

break is a keyword, so the function is called breakpoint.
