The Pepper Programming Language

Building Pepper from source

Pepper is written in Pepper. The compiler, pep-build, is the Pepper program in tools/compiler (also called pepc), and every other tool is a Pepper program under tools/. Building them takes a Pepper compiler, so the first one comes from a published toolchain, the build of main (stage 0), the same way CI and the release build get theirs. The Rust compiler that once bootstrapped Pepper plays no part.

You need this to work on Pepper itself, or on a platform with no prebuilt binaries. To use Pepper, install it instead.

Setting up

Four steps, on every platform:

  1. The build of main. Every merge into main that changes the compiler, the runtime or the tools publishes it as a prerelease named x.y.z-dev, which pepper install list --available lists. Install it and make it the default, with the install script on a new machine or with pepper install:

    sh scripts/install.sh --version 0.4.0-dev    # the -dev version listed
pepper install add 0.4.0-dev && pepper install use 0.4.0-dev

    A prerelease is picked only by its exact name, never by update or latest. pepper install add --force <version> refreshes it.

  2. Platform prerequisites, for linking:

    • Windows: Visual Studio 2022 or newer with the C++ workload (or the standalone Build Tools), which clang links through; PowerShell (pwsh 7.x is what the setup script is tested with; Windows PowerShell 5.1 also works); and 7-Zip, only for -DevTools, which extracts lldb from the llvm.org installer rather than running it.
    • macOS: the Xcode Command Line Tools (xcode-select --install), for the SDK, system headers and ld. The clang that drives the link comes from the LLVM prefix when it has one, which it does on macOS.
    • Linux (Debian/Ubuntu names): sudo apt install build-essential clang curl xz-utils. clang is the link driver, and on Linux nothing else provides one: llvm-20-dev installs no bin/clang into its prefix.

  3. LLVM 20. The compiler links LLVM through the pepper-llvm package, which binds LLVM 20, so building it needs an LLVM 20 development install. One command provisions it (every option is in Setting up LLVM):

    ./scripts/setup-llvm.sh --devtools            # macOS / Linux
pwsh -File scripts/setup-llvm.ps1 -DevTools   # Windows

  4. The private packages. tools/compiler depends on justinboswell/pepper-llvm and tools/pep-lsp on justinboswell/pepper-lsp. The first build of each fetches its package with git into the tool’s .pep/deps, so your git needs read access to those repositories.

Where LLVM comes from

On macOS and Linux your package manager has an LLVM 20 and the script uses it:

platformwhere LLVM comes fromcost
Linuxapt install llvm-20-dev (plus libpolly-20-dev)4–8s, 400–750 MB
macOSbrew install llvm@2013–17s
Windowsthe official release archive896 MB download

Windows needs the archive because nothing else on the platform works: the llvm.org installer and the winget, scoop and chocolatey packages ship neither llvm-config nor the component libraries. The script falls back to the archive on Linux and macOS too, but only when the package manager has no LLVM 20.

That fallback is sound on Linux but usually unusable on macOS: the release tarballs are LTO builds, so their static libraries are LLVM bitcode, and Apple’s linker rejects bitcode produced by a newer LLVM than its own (could not parse bitcode object file … Unknown attribute kind). Homebrew’s llvm@20 is not LTO-built and works, so on macOS install it with brew and re-run the script. It warns about this when it takes the archive path there.

The script records the prefix it settled on in .pep/llvm-prefix (gitignored), which the test, release and CI scripts read (a git worktree reads its main checkout’s). Re-run it on a new machine rather than copying that file. With a valid install present it only rewrites the file, and ./scripts/setup-llvm.sh --check reports what it would use, changing nothing.

Only the Windows archive path is large: budget roughly 5 GB of disk for the tree plus its cached archive, and a few minutes for the first run. Everything lands outside the repository, under %LOCALAPPDATA%\pepper or ~/.local/share/pepper, except a package-manager prefix, which stays wherever apt or brew put it.

The debugger

--devtools sets up the lldb debugger, and is worth it: a compiler that generates and links native code fails in native ways, an access violation or SIGSEGV from inside LLVM or the code it generated, and lldb turns that into a symbolized stack. On Windows it installs lldb, lldb-dap and lldb-server into the LLVM prefix (an extra 335–434 MB), extracting them from the llvm.org installer with 7-Zip and placing the embeddable Python that liblldb.dll needs beside them. On macOS and Linux it checks for a usable lldb and says how to install one if there is none. PEPPER_SETUP_DEVTOOLS=1 turns it on for every run.

Build the compiler with -g for its own frames, then:

lldb --batch -o run -k "thread backtrace" -- target/bin/pep-build tests/hello.pep

On Windows the setup script leaves the PATH alone, so run "$env:LOCALAPPDATA\pepper\llvm\20.1.8\bin\lldb.exe" by its full path. Debugging covers debugging Pepper programs.

Building

Build the compiler from tools/compiler with the installed toolchain, against this checkout’s runtime, then every tool with the compiler you built. Each tool is a project: its tools/<tool>/pep.toml adds tools/ to the import search path, for the modules the tools share, and names the packages it depends on. On macOS and Windows the compiler’s link needs LLVM’s library folder (-L), and on Windows its LLVM-C.dll beside it:

export PEPPER_RUNTIME="$PWD/runtime"
llvm="$(head -1 .pep/llvm-prefix)"
mkdir -p target/bin
pepper build -O tools/compiler/main.pep -o target/bin/pep-build    # + -L "$llvm/lib" on macOS and Windows
# Windows: cp "$llvm/bin/LLVM-C.dll" target/bin/
for tool in pepper pep-fmt pep-test pep-package pep-profile pep-run pep-install pep-doc pep-lsp; do
  target/bin/pep-build -O "tools/$tool/main.pep" -o "target/bin/$tool"
done

(.exe names on Windows.) The release build (scripts/release-build.sh) does the same, then builds the compiler once more with itself, and ships that one. A cold build of the compiler takes several minutes; the build cache makes a rebuild after an edit take seconds.

Testing

The tests are Pepper [Test] functions, run by scripts/pepper-tests.sh as CI runs them; there is no cargo test.

scripts/pepper-tests.sh                      # with the installed build of main
scripts/pepper-tests.sh target/bin           # with the compiler you built
PEPPER_OPT_LEVEL=2 scripts/pepper-tests.sh   # every build the tests make at -O2
WASI_SDK_PATH=/opt/wasi-sdk WASMTIME=/opt/wasmtime/wasmtime scripts/pepper-tests.sh

The last also builds the docs examples and the corpus for wasm32-wasip1 and runs them under wasmtime, except those that need threads, tasks, sockets or processes; without a wasi-sdk those tests say they skipped and pass. Testing the runtime and the compiler says what runs and where new tests go. Before a pull request, also run what CI checks:

target/pepper-tests/bin/pep-doc check        # the reference and the tools' pages are current
target/pepper-tests/bin/pep-fmt --check runtime tools

AGENTS.md, at the repository’s root, holds the rules every change follows, for people and agents alike: the reference-counting model, how errors are reported, naming, formatting, and which docs a change must update. INTERNALS.md is the map of the compiler: where each stage lives and the patterns it follows. .agents/skills/ holds step-by-step workflows (build, test, finish a PR, test another platform), and its build and test skills carry the failure signatures this project has hit, such as LLVM discovery and link failures and the private packages’ fetch. Start there before diagnosing a failure from scratch.

The VS Code extension from a branch

The released extension comes from the vsix-v* GitHub release. To run the extension and language server from the branch checked out, before it merges:

scripts/install-vscode-extension.ps1          # build pep-lsp + vsix, install into VS Code
scripts/install-vscode-extension.ps1 -Watch   # follow the branch: pull and reinstall on change

The extension restarts its language server by itself when the installed server changes; a change to the extension’s own code needs Developer: Reload Window. When editing the server, setting pepper.lspPath to a pep-lsp you build skips the install (see The language server: pep-lsp). Packaging (vsce package, run by the script and the VSIX workflow) bundles tools/vscode-pepper/src and its dependencies into one file with esbuild (npm run bundle).

Platforms

  • Windows x64, Linux x64 and macOS arm64 build and pass the suite; CI runs it on all three.
  • Cross-compiling (--target): CI links from each of Linux x64, macOS arm64 and Windows x64 for the other two with lld and their system roots and runs the programs on their own OS. Other pairs emit their objects; their links are untested.
  • WebAssembly (--target wasm32-wasip1) and iOS and Android: see Platform selection and iOS and Android.
  • macOS x86_64 is untested. LLVM 20 publishes no macOS-X64 archive, so it needs Homebrew’s llvm@20.

To exercise another platform from the machine you are on, run the platform-test workflow (gh workflow run platform-test.yml -f platforms=linux); the platform-test skill in .agents/skills/ describes it.
