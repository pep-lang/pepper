The Pepper Programming Language

Cryptographic hashes

The digest module computes SHA-256, SHA-1 and BLAKE3 digests: fixed-size fingerprints of data, used to check that a download arrived intact, to name content by its hash, or to key a cache. It also computes message authentication codes with HMAC or BLAKE3's keyed mode, and derives keys. Bring it in with import digest; the full API is in the reference.

# Cryptographic hashes: one-shot, incremental, and as hexadecimal text.
import digest;

main(): int {
    # One call hashes a whole input, bytes or a String's UTF-8 bytes.
    var id = digest.to_hex(digest.sha256("hello"));
    assert(id == "2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824", "SHA-256");

    # A hasher takes the input in pieces, such as the blocks of a file as
    # they are read; the digest does not depend on how it was split.
    var hasher = digest.Blake3();
    hasher.update("hel");
    hasher.update("lo");
    var whole = digest.blake3("hello");
    assert(hasher.finish() == whole, "same digest");
    assert(whole.count == 32, "32 bytes");

    # git names a file's content by the SHA-1 of a header and the bytes.
    u8[] nul = [0];
    var git = digest.Sha1();
    git.update("blob 6");
    git.update(nul);
    git.update("hello\n");
    assert(git.finish_hex() == "ce013625030ba8dba906f756967f9e9ca394464a", "git blob id");
    return 0;
}

One-shot and incremental

Each hash has a one-shot function and a hasher type:

HashFunctionHasherDigest size
SHA-256digest.sha256(input)digest.Sha25632 bytes
SHA-1digest.sha1(input)digest.Sha120 bytes
BLAKE3digest.blake3(input)digest.Blake332 bytes
  • The input is a u8[], or a String, which hashes its UTF-8 bytes (without a terminating NUL).
  • A hasher takes the input in pieces: call update any number of times, then finish for the digest. Splitting the input differently gives the same digest. finish also resets the hasher, so it can hash another input; reset discards the input so far.
  • A digest is a u8[]. digest.to_hex(bytes) writes it as lowercase hexadecimal, the way checksums are usually shown, and each hasher's finish_hex() does both steps; digest.from_hex(text) reads hexadecimal back into bytes.
  • An array literal passed straight to update is ambiguous between its u8[] and String overloads; give it a type first (u8[] nul = [0]; hasher.update(nul);).

Which hash

  • SHA-256 is the common choice for published checksums and anything that must interoperate.
  • BLAKE3 is faster and as strong; the compiler's build cache keys its objects with it.
  • SHA-1 is broken for collision resistance: someone can make two inputs with the same digest. Use it only where a format requires it, such as git object ids.

None of these is the hash for a hash table: HashMap and HashSet use hash<T>, which is much faster but neither cryptographic nor stable between versions.

Message authentication

A message authentication code (MAC) is a digest that only someone with a secret key can compute, so a receiver that shares the key can check that a message is authentic and unchanged. Webhook signatures, JWTs (HS256) and S3-style request signing all use HMAC.

# Message authentication: HMAC, BLAKE3's keyed mode and key derivation.
import digest;

main(): int {
    # A webhook signs its body with HMAC-SHA-256 under a shared secret;
    # the receiver computes the MAC again and compares in constant time.
    var body = "{\"event\":\"push\"}";
    var received = digest.hmac_sha256("webhook secret", body);
    var signature = "493db758cb288b3801a0084bcdd27bd565ca0fb9b0a149404d2b4442c9d79bcd";
    assert(digest.to_hex(received) == signature, "HMAC-SHA-256");
    var expected = digest.Hmac<digest.Sha256>("webhook secret");
    expected.update(body);
    assert(digest.equal_constant_time(expected.finish(), received), "authentic");

    # Derive a 32-byte key for one purpose from a shared secret, then use
    # it for BLAKE3's keyed mode.
    var derive = digest.Blake3.derive_key("example.com 2026-10-16 webhook MACs v1");
    derive.update("a shared secret");
    var mac = digest.Blake3.keyed(derive.finish());
    mac.update(body);
    assert(mac.finish().count == 32, "a 32-byte MAC");

    # BLAKE3 gives output of any length; the first 32 bytes are the digest.
    var hasher = digest.Blake3();
    hasher.update(body);
    var long_output = hasher.finish(64);
    assert(long_output.count == 64, "64 bytes");
    assert(digest.to_hex(long_output).starts_with(digest.to_hex(digest.blake3(body))), "a prefix");
    return 0;
}
  • HMAC (RFC 2104) works over SHA-256 or SHA-1: digest.hmac_sha256(key, message) and digest.hmac_sha1(key, message) are one-shot, both arguments u8[] or both String, and digest.Hmac<digest.Sha256>(key) is the incremental hasher, with the same update, finish, finish_hex and reset as the hashes. finish and reset keep the key. A key longer than 64 bytes is hashed first.
  • Check a MAC with digest.equal_constant_time(a, b), not ==: == stops at the first byte that differs, and timing it lets an attacker find a valid MAC a byte at a time.
  • BLAKE3's keyed mode, digest.Blake3.keyed(key), is a MAC with a 32-byte key; it panics on a key of any other length.
  • Key derivation: digest.Blake3.derive_key(context) returns a hasher whose digest is a key, derived from the input (a shared secret, say) for the purpose context names. Make context a hard-coded string unique to the application and purpose; different contexts give unrelated keys.
  • Extended output: every Blake3 hasher's finish(length) returns length bytes, in any of the three modes. The first 32 are the digest finish() returns.
  • PBKDF2 (RFC 8018): digest.pbkdf2_sha256(password, salt, rounds, length) derives length bytes from a password (u8[] or String) and a u8[] salt, with rounds iterations of HMAC-SHA-256 per 32-byte block. It is SCRAM's Hi(), as PostgreSQL, MongoDB and SASL logins use. To store new passwords, use Argon2id (pepper-crypto's crypto.hash_password) instead, which costs an attacker's GPUs memory as well as time. It panics when rounds is 0 or length is over RFC 8018's limit.

Using the system's crypto library

By default the hashes are written in Pepper, so a program that uses them links no extra library. Building with -D USE_LIBCRYPTO (see Build options) makes SHA-256 and SHA-1 call the platform's crypto library instead, which uses the CPU's SHA instructions where it has them: several times faster (about 1.7 GB/s instead of 250 MB/s for SHA-256 on an x86-64 with SHA-NI).

pep-build main.pep -D USE_LIBCRYPTO -o app
PlatformLibraryWhat it needs
LinuxOpenSSL's libcrypto (EVP_Digest*), linked as -lcryptothe development package (libssl-dev, openssl-devel)
macOSOpenSSL's libcrypto, linked as -lcryptoHomebrew's openssl@3, and its lib folder named with -L or PEPPER_LIBRARY_PATH (-L $(brew --prefix openssl@3)/lib)
WindowsCNG (BCryptHash*), linked as bcrypt.libnothing: CNG is part of Windows 10 and later

The API and the digests are the same either way. Blake3 stays portable Pepper, since libcrypto has no BLAKE3.

Limitations

  • Without USE_LIBCRYPTO, SHA-256 and SHA-1 run at a few hundred megabytes per second. BLAKE3 is always the portable code, below the official BLAKE3, which uses SIMD and threads.
  • The hashes have no secret-dependent branches or table lookups, but they have not been audited for timing side channels, which matter only when hashing secrets. Copies of an HMAC key stay in memory until the hasher is freed; nothing wipes them.
  • HMAC works over SHA-256 and SHA-1; there is no SHA-512 to put under it.
